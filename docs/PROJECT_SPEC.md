## 1. プロジェクト概要

### 1.1 目的

**運営するパーソナル英語スクールの、レッスンと宿題の循環を支える道具をつくる。**

スクールの運営は次の形をとっている。

```
週2回のレッスン
  ↓ 宿題を出す
生徒が自宅で取り組む
  ↓
次のレッスンで達成度を確認し、良かった点を伝え、弱点を指摘する
  ↓ その弱点に対応した宿題を出す      ← ここが要
週2回のレッスン(以下くりかえし)
```

**このシステムが解く問題は「弱点を指摘した直後に、それに対応した教材を
すぐ用意できないこと」である。** 用意に時間がかかると、弱点に対する
練習量が確保できず、克服につながらない。

したがって本システムの中心機能は、学習記録でも発音採点でもなく、
**トレーナーが弱点から教材を作り、指定した生徒に配信する仕組み**である。
学習記録・発音練習・グラフは、その循環を支える補助機能と位置づける。

副次的な目的として、生徒が自宅で取り組んだ量と内容を、
次のレッスン前にトレーナーが把握できるようにする。

### 1.2 想定ユーザー

**当面はスクールの既存生徒に限定して提供する(クローズド)。**
一般公開はしない。アカウントはトレーナーが発行し、自由登録は設けない。

| ロール | 人物 | できること |
|---|---|---|
| 生徒 (learner) | スクールの既存生徒 | 配信された宿題に取り組む、学習記録、発音練習、履歴の確認 |
| トレーナー (admin) | スクール運営者(開発者本人) | 教材の作成・配信、生徒の取り組み状況の確認、フィードバックの記録 |

**教材を作れるのはトレーナーだけである。** 生徒は自分で教材を作れない。
作った教材は、トレーナーが指定した生徒にだけ配信される。

#### 対応環境について

生徒の端末は選べない。**どの環境から来ても正しく動くことを要件とする。**
この点はクローズド化しても変わらない。生徒が iPhone を使っていれば
iOS Safari で動く必要があり、第 3.3 節で調べた制約はそのまま効き続ける。

一方で、**発音スコアの端末差(第 5.1 節)の重みは下がった。**
達成度の評価はトレーナーがレッスンで行うため、
アプリのスコアが端末間で厳密に比較できる必要はなくなった。
これは第 5.1 節の判断を大きく変える(同節の 2026-08 追記を参照)。

### 2.3 教材の作成と配信(中心機能・未実装)

**本システムの中心機能。** トレーナーだけが操作でき、生徒側には作成画面を出さない。

#### トレーナー側のながれ

```
① レッスン中/直後に、生徒と「弱点」を選ぶ
      例: /l/ と /r/ の区別、語尾の子音、冠詞、前置詞、時制、リズム
   ↓
② 教材ライブラリから、その弱点タグの付いた既存教材が提示される
      あればそのまま選ぶ ── ここが最速。生成も音声作成も要らない
   ↓
③ 無ければ AI に生成させる(数十秒)
   ↓
④ トレーナーが画面上で英文を直す ── ここが品質の担保
   ↓
⑤「発行」を押すと、同時に3つが出来上がる
      ・アプリで取り組む形(音声再生・録音・取り組み記録つき)
      ・印刷用の PDF(書き込み・オフライン用)
      ・お手本音声の MP3(第 5.2 節の事前生成の仕組みを流用)
   ↓
⑥ 指定した生徒に配信される。教材はライブラリに残る
```

**⑥ でライブラリに残ることが効いてくる。**
同じ弱点を持つ生徒が次に現れたとき、②で終わる。
運用を続けるほど「生成せずに即座に出せる」割合が増えていく。
最初の数か月はライブラリを育てる期間と考える。

#### 生徒側のながれ

```
「今週の宿題」に配信された教材が並ぶ
  ├ アプリで取り組む : お手本を聞く / 音読して録音する / 聞き比べる
  ├ PDF をダウンロード: 印刷して書き込む、オフラインで読む
  └「やった」を記録する
```

取り組んだ回数・録音・自己申告は自動で記録され、
次のレッスン前にトレーナーが管理画面で確認できる。

#### PDF とアプリの両方を出す理由(重要)

要望としては「PDF が最高」だが、**PDF だけにしてはいけない。**
PDF には次のことができない。

| できないこと | なぜ困るか |
|---|---|
| 取り組んだかどうかを記録する | **レッスンでの達成度確認ができなくなる。** 目的(第 1.1 節)そのものが失われる |
| 音声を再生する | お手本を聞けない。MP3 を別に配る手間が生じ、生徒側で紐付けが崩れる |
| 発音を録音する | 音読の練習ができない |

そこで **1つの教材データから2つの形を出す。** PDF はなくさない。
印刷して書き込みたい生徒、オフラインで取り組みたい生徒には PDF が最適であり、
アプリはそれを置き換えるものではなく、記録と音声を足すものと位置づける。

#### 弱点タグ(2026-08 確定)

教材の検索と再利用は、このタグで行う。**トレーナーが実際のレッスンで生徒に
指摘している言葉**をそのまま採用した。実装は
[`../src/data/weaknessTags.js`](../src/data/weaknessTags.js)。

| 分類 | タグ |
|---|---|
| 発音(子音) | /l/ と /r/、/s/ と /th/、/b/ と /v/、語尾の子音、子音連続、**全子音の基本練習** |
| 発音(母音) | 短母音と長母音、あいまい母音 |
| リズム | 強勢の位置、文全体のリズム、リンキング、脱落 |
| 文法 | 冠詞、前置詞、時制、単数複数、数の表現、数字、関係代名詞、仮定法、比較表現、to不定詞、分詞構文、分詞(ing/ed)、分詞形容詞、接続詞、省略表現、語順 |
| 表現 | つなぎ言葉、言い換え、決まり文句、句動詞、イディオム、コロケーション |
| 流暢さ | 言いよどみ、間の取り方、速さ、要約 |

計 38 個。1つの教材に複数のタグを付けられる。

##### タグには2種類ある(`kind`)

| kind | 意味 | 弱点の選択肢に出すか |
|---|---|---|
| `weakness` | レッスンで「弱点」として指摘するもの(37個) | **出す** |
| `drill` | 弱点ではなく、網羅的に反復するための基礎練習(1個) | **出さない** |

「全子音の基本練習」だけが `drill` である。
これは弱点ではなく**網羅型のドリル**であり、粒度が他と違う。
同じ扱いにすると、レッスンで弱点を選ぶ画面に
「全子音の基本練習」が混ざって選びにくくなる。
教材の分類には使うが、弱点の選択肢からは外す。

##### `id` は変えてはならない

`label`(画面に出す日本語)はあとから自由に変えてよいが、
`id` は教材との紐付けに使うため、一度使い始めたら変えてはならない。
変えると、その id が付いていた過去の教材が行方不明になる。

##### `hint`(取り違え防止の覚え書き)

名前が似ているタグがあるため、各タグに例を添えてある。
トレーナーが後から見て取り違えないためであり、
AI に教材の下書きを作らせるとき(第 2.3 節③)にもそのまま渡す。

| 紛らわしい組 | 区別 |
|---|---|
| 数の表現 | much / many / a few — **量をあらわす語** |
| 数字 | 金額・日付・桁・小数・パーセント — **読み上げ**。ビジネスで必須 |
| 分詞構文 | `Walking down the street, I saw ...` の構文 |
| 分詞(ing/ed) | 名詞を後ろから修飾する形。`the man standing there` |
| 分詞形容詞 | 感情をあらわす形。`interesting / interested` |

##### タグはあとから足せる

DB のテーブルに1行足すだけで、アプリの作り直しは要らない。
**最初から完璧を目指す必要はない。** 運用しながら過不足を直す。

`要検討`(いま入れていないが、運用しはじめて必要を感じたら足すもの):

| 候補 | 分類 | 補足 |
|---|---|---|
| 二重母音 | 発音(母音) | day / die、no / now |
| /æ/ と /ʌ/ | 発音(母音) | cat / cut |
| 文末イントネーション | リズム | 疑問・確認・列挙での上げ下げ。強勢とは別 |
| 聞き取り(音) | (新設) | 現在のタグはすべて**話す側**の弱点。 聞き取りの弱点を記録するなら分類ごと新設が要る |
| 語彙不足(分野別) | 表現 | 句動詞・イディオムでは拾えない、話題ごとの語彙 |

## 3. 技術構成(決定事項)

### 3.1 バックエンド: Supabase を採用

**採用理由**

- 認証・DB・ストレージ・ホスティングが 1 つのサービスで揃い、個人開発の運用負荷が小さい
- PostgreSQL なので、学習ログの集計・分析クエリを SQL でそのまま書ける
- Row Level Security (RLS) により「学習者は自分のデータのみ、管理者は担当学習者のデータのみ」
  というアクセス制御を DB 層で担保できる
- 無料枠が実用的で、プロトタイプから本番まで同じ構成で進められる

**利用するサービス**

| 機能 | Supabase の該当機能 |
|---|---|
| ユーザー認証 | Supabase Auth(メール + パスワード想定、`要確認`: マジックリンク/OAuth の要否) |
| 学習ログの保存 | Postgres Database |
| アクセス制御 | Row Level Security |
| 集計 | Postgres View / RPC (SQL 関数) |

### 3.2 音声データは端末内に保存する(サーバーに上げない)

**決定内容**: 録音した音声ファイルは Supabase Storage 等にアップロードせず、
利用者の端末内(ブラウザの IndexedDB / ネイティブアプリならローカルストレージ)に保存する。

**理由**

- 音声は生体情報に近い機微なデータであり、学習者に未成年が含まれる可能性を考えると
  サーバー保管はプライバシー上のリスクとコンプライアンス負担が大きい
- ストレージ課金と転送量課金を抑えられる
- 発音スコアの算出はクライアント側または API へのその場送信で完結し、
  音声そのものを保持し続ける必要がない

> **補足(第 5.1 節を参照):** 「サーバーに保存しない」ことと
> 「外部に送信しない」ことは別である。発音採点をブラウザの音声認識で行う場合も、
> 音声はブラウザメーカーのサーバーに送信される。この方針が担保するのは
> **保存しないこと**であり、送信しないことではない。

**端末に保存するかどうかは、利用者が選べる(実装済み)**

| 設定 | 動作 |
|---|---|
| 残す(既定) | 直近 20 件をこの端末に保存し、あとから聞き返せる |
| 残さない | 保存しない。**ただし直前の録音はその場で聞き返せる** |

どちらを選んでも、直前に録音したものは必ずその場で再生できる。
録り直しの判断に必要なためであり、この再生用の音声は画面を離れると消える。

保存先はブラウザの IndexedDB(`src/lib/recordings.js`)。
別の端末では聞けず、ブラウザのサイトデータを削除すると消える。
利用者はいつでも「保存した録音をすべて削除する」を実行できる。

**サーバーに保存するのはスコアとメタデータのみ**

保存する: 発音スコア、練習した文章、練習日時、練習回数
保存しない: 音声ファイル本体、音声の波形データ

**この決定に伴う制約**

- 端末を変えると過去の録音は聞き返せない(スコアの履歴は残る)
- ブラウザのストレージ上限に達した場合は古い録音から削除する必要がある
  → `要確認`: 端末内に何日分保持するか(既定案: 直近 30 日 or 100 件)

### 3.3 フロントエンド

- React + Vite

**対応プラットフォーム(要件)**

一般に公開する以上、利用者の端末は選べない。以下すべてで正しく動くことを要件とする。

| 環境 | 対象 |
|---|---|
| デスクトップ | Windows / macOS の Chrome・Edge・Safari・Firefox |
| スマートフォン | iPhone (Safari および iOS 上の全ブラウザ)、Android (Chrome・Samsung Internet・Firefox) |
| タブレット | iPad、Android タブレット |
| アプリ内ブラウザ | LINE・X・Instagram などから開かれた場合 |

> **iOS の重要な性質:** iPhone / iPad では Chrome も Firefox も、
> 中身は Safari と同じ WebKit である。したがって
> **「iOS で Chrome を使えば回避できる」という手は存在しない。**
> iOS Safari で動かないものは、iOS のどのブラウザでも動かない。

**開発者本人の利用環境**

| 端末 | 用途 | 制約 |
|---|---|---|
| 会社PC | 閲覧・動作確認 | **アプリのインストール不可**。ブラウザで開くことしかできない |
| Mac(自宅) | 開発・閲覧 | 制約なし |
| iPhone(移動中) | 閲覧・発音練習 | — |

**この要件から導かれる方針**

- **ウェブアプリとして作り、URL を開くだけで使える形にする**(ネイティブアプリを作らない)
- **画面は狭い幅を前提に設計する**(実装済み)
- **端末ごとに結果が変わる仕組みに依存しない** ← 第 5.1 節の判断を決定づける
- 使えない機能がある環境では、その機能だけを隠し、
  **アプリ全体が壊れないようにする**(機能の有無を実行時に判定する)

### 3.3.2 録音まわりで踏んだ落とし穴(実機で確認済み)

利用者は納得いくまで**何度も録り直す**。この繰り返しが壊れやすい箇所である。

| 落とし穴 | 症状 | 対処 |
|---|---|---|
| マイクの接続を使い回す | **2回目以降の録音がすべて失敗する**(iPhone Safari で実機確認) | 録音のたびに `getUserMedia` を呼び直す |
| 録音後にマイクを解放しない | 録音マークが消えない。次の録音が開始できない | 停止時に必ず全トラックを `stop()` する |
| `recorder.mimeType` を信用する | 空文字を返す環境がある(Chromium で確認) | `isTypeSupported` で自分で選び、その値を使う |
| 録音中に画面を離れる | マイクが掴まれたままになる | 画面の後片付けで録音を中止する |
| 前の録音のURLを破棄しない | 録り直すほどメモリを消費する | 新しい録音の開始時に `revokeObjectURL` する |

### 3.3.2.1 検証の進め方についての教訓

実機での確認を何度か繰り返すなかで、**古い内容がブラウザに残っていて
「直したはずの不具合が直っていない」ように見える**ことが複数回あった。
そのたびに原因の切り分けからやり直しており、無駄が大きい。

対処として、診断ページに**版を表示**するようにした。
公開時に日時とコミットの識別子が埋め込まれ、結果のコピーにも含まれる。
報告を受けた側が、どの版で確認されたものかを判断できる。

同種の作業では、**確認する対象がどの版かを機械的に分かるようにしてから
確認を依頼する**こと。

### 3.3.3 実機(iOS 18.7)で判明したこと

実機の診断結果から、公開情報だけでは分からない挙動が3つ判明した。

**1. 音声認識は動くが、「確定」の合図を返さないことがある**

認識自体は完璧に成功していた(`I usually walk to the station in the morning` を
正しく聞き取っていた)にもかかわらず、`isFinal` が一度も真にならないまま
`onend` を迎えた。確定結果だけを見ていると
**「認識されませんでした」と誤表示される。**
→ 確定が来ない場合は、確定前(interim)の結果を採用する。

**2. ネタ声の名前は端末の言語に翻訳される**

日本語環境では Bells が「ベル」、Jester が「道化」、Whisper が「ささやき声」
として現れた。**英語名だけの除外リストは機能しない。**
→ `voiceURI`(`com.apple.speech.synthesis.voice.*`)で判定する。

**3. 同じ声が二重に現れる — 除く順序に注意**

英語の声39個のうち12個が重複していた(iOS の Chrome)。
一方 Safari は22個で重複がなかった。**同じ端末でもブラウザによって
返る一覧が違う。**

重複を除く際、**先に品質順へ並べてから除かなければならない。**
同じ表示名で簡易版と高品質版の両方が返る可能性があり、
並べる前に除くと簡易版のほうを残してしまう。
当初この順序が逆になっており、高品質版を捨てる恐れがあった。

**4. 2つ目の MediaRecorder を作れない(Safari)**

「録音のたびにマイクを取り直す」対処では Safari の再録音が直らなかった。
より確からしい原因は、**同じページで2つ目の `MediaRecorder` を作ること**
そのものが失敗する点にある。
→ 録音器とマイクを保持し、2回目以降は同じ録音器を `start()` し直す。
　 練習画面を離れるときに `releaseMicrophone()` で解放する。

**6. Chrome では通信を使う高品質な音声が使える**

同じ利用者が Chrome で開いたところ、音声の品質が明確に良かった
(イギリス英語)。Chrome には Google の通信型ニューラル音声
(`Google US English` / `Google UK English Female・Male`)が入っており、
端末内蔵の簡易な音声とは別物である。

ここから2つの修正を行った。

- **通信を使う音声(`localService === false`)を「高品質」に分類する。**
  Google の音声は名前に Premium などの語を含まないため、
  当初は「標準」と誤分類していた
- **「毎回おまかせ」は、その端末で最も良い品質の段階からのみ選ぶ。**
  従来は使える声すべてから無差別に選んでおり、
  高品質な音声がある端末でも簡易な音声が当たり得た

> **この体験は、音声の事前生成で得られるものと同じである。**
> Chrome で良かったのは通信先で生成された音声だからであり、
> 事前生成に切り替えれば **iPhone を含む全端末で同じ品質**になる。
> 第 5.2 節の方針を裏づける実例といえる。

**5. この端末には高品質音声が1つも入っていなかった**

英語の声39個すべてが標準品質か簡易版で、Enhanced / Premium は皆無だった。
初期状態の端末ではこれが普通と考えられる。第 5.2 節の判断根拠となる。

### 3.3.4 実機 Safari(iOS 18.7)で判明した決定的な事実

**1. ダウンロードした高品質音声は、ブラウザから使えない(確定)**

> **全件を確認しての決着(2026-08)**
> 診断ページに加工前の一覧を出す機能を入れ、iOS の Chrome が返す
> **47個すべて**の `voiceURI` を確認した。
>
> ```
> com.apple.voice.compact.*          6個(標準的な話者の簡易版)
> com.apple.eloquence.*             16個(簡易版)
> com.apple.speech.synthesis.voice.* 19個(古い系統・ネタ声)
> 重複                                6個
> ────────────────────────────
> enhanced / premium                 0個   ← 1つも無い
> ```
>
> 利用者は設定から高品質音声をすべてダウンロード済みである。
> それでも **Web Speech API からは1つも見えない。**
> Apple の制限であり、アプリ側の工夫では回避できないことが、
> 推測ではなく全件の確認によって確定した。
>
> なお当初 39個の一覧をもとに数を突き合わせて「一致した」と述べたが、
> その一覧自体が一部絞り込まれた後のものであった。
> 実際の総数は47個である。結論は変わらない。
>
> 重複を除く処理は正しく働いている(47個 → 表示22個)。

**2. MediaRecorder は iOS Safari で2回目以降まともに動かない**

| 試した方式 | 結果 |
|---|---|
| 録音のたびに新しい MediaRecorder を作る | 2回目が失敗 |
| 同じ MediaRecorder を start() し直す | エラーは出ないが**音声が空(5バイト)** |

→ MediaRecorder の使用をやめ、**Web Audio API で生の音声を集めて
　 自分で WAV に組み立てる方式**に変更した。
　 副次的な利点として、出力形式が全端末で WAV に統一され、
　 端末ごとに webm / mp4 と分かれる問題も消えた。

**3. マイクを掴んだままだと、音声認識が失敗する**

録り直しを速くするためマイクを保持する実装にしたところ、
音声認識が毎回 `aborted` で失敗した。
→ 録音が終わったら**マイクを完全に解放する**。

**5. AudioContext は作り直してはいけない**

MediaRecorder をやめて Web Audio 方式にしたあと、
**2回目以降の録音がすべて無音(音量0)**になった。エラーは出ないため
気づきにくい。さらにその後、音声認識まで `aborted` で失敗するようになった。

```
録音1回目: 音量=100% サイズ=131116B   ← 成功
録音2回目: 無音 音量=0.000
録音3回目: 無音 音量=0.000
→ 以降、音声認識も aborted / audio-capture
```

原因は、録音のたびに `AudioContext` を作り、終了時に `close()` していたこと。
iOS では音声の入出力が端末全体で1つの資源として扱われており、
作っては壊すとその資源が壊れると考えられる。

対処:
- **`AudioContext` はページに1つだけ作り、`close()` しない**
- 録音していない間は `suspend()` して資源を明け渡す
- **音声認識を始める前に必ず `suspend()` する**

この3点を守らないと、録音と音声認識が互いを壊し合う。

**6. マイクへの接続部品も作り直してはいけない**

AudioContext を使い回すようにしても、まだ足りなかった。
録音のたびに `getUserMedia` と `createMediaStreamSource` をやり直していると、
**数回〜十数回で、やはりエラーを出さないまま無音になる。**

```
1周目の録音7回: すべて成功(音量83〜100%)
音声認識6回: すべて成功
2周目の録音: 2回成功したあと、3回目から音量0
```

対処: **マイクと接続部品は最初の1回だけ作り、そのまま保持する。**
録音の開始・停止は「音を集めるかどうか」の切り替えだけで行う。

引き換えに練習中はマイクを掴んだままになるため、
練習画面を離れるとき、および音声認識を使う前に
`releaseMicrophone()` で必ず手放すこと。

**7. Bluetooth のマイクを考慮する**

実機での検証中、いくつかの異常が Bluetooth マイクの使用時に起きていた
(音量20%の録音、音声認識の中断)。

英語学習では **Bluetooth のイヤホンで音読練習をする利用者が多い**と想定される。
接続を保持する設計にしたため、練習の途中で機器を繋いだ・外した場合、
すでに存在しない機器を掴んだままになる。

対処:
- `devicechange` を監視し、機器が入れ替わったら次の録音で接続を作り直す
  (録音中は中断させず、印だけ付けて次回に反映する)
- 使用中のマイク名を画面に表示し、機器の取り違えに気づけるようにする
- 音量が極端に小さい場合(8%未満)は警告を出す。
  Bluetooth 機器では音質が落ちるため、端末内蔵マイクを勧める

`要確認`: 発音採点の精度が Bluetooth マイクでどの程度落ちるか。
著しく落ちるなら、採点時は内蔵マイクを促す案内が必要になる。

**8. 無音は「壊れた合図」として扱う**

上記をすべて守っても、iOS 側の事情で経路が壊れる可能性は残る。
録音結果が無音だった場合は接続を解体し、次回に組み立て直す。
**無音のまま採点してはいけない** — 意味のない数字が出るだけで、
利用者は録音できていないことに気づけない。

**4. 読み上げの `canceled` はエラーではない**

別の声を試聴した際、前の読み上げが止められて `canceled` が返る。
これを異常として表示していた。→ 中断は正常系として扱う。

いずれも `src/lib/speech.js` に集約して対処済み。
検証には Chromium の擬似マイク機能を使い、**4回連続の録音**が
すべて成功し、データの大きさが安定することを確認している。

### 5.1 発音スコアは現在シミュレーション

> **【2026-08 追記】スクール限定への方向転換で、この節の重みは下がった。**

> **達成度の評価をトレーナーがレッスンで行う運用になったため、この根拠は消えた。**
>
> あわせて、生徒の端末はトレーナーが把握できる(入会時に確認できる)ため、
> 「Firefox やアプリ内ブラウザから来るかもしれない」という不確実性も小さい。
>
> したがって当面の方針は次のとおりとする。
>
> 1. **見せかけのスコアは出さない。** 根拠のない数値は、生徒にもトレーナーにも害になる。
>    実装を入れるまでは点数表示を止める。
> 2. 代わりに **「音声認識が何と聞き取ったか」をそのまま見せる。**
>    これは実際に起きたことであり、嘘がない。
>    自分の発音が意図した単語として聞き取られたかどうかは、
>    生徒が自宅で1人で確認できる情報として十分に有用である。
> 3. 案2(サーバー側評価)は**やめるのではなく後ろに回す。**
>    音素単位のフィードバックは弱点の特定に直結するため、
>    教材の作成・配信(第 2.3 節)が動いたあとに改めて検討する。
>
> 以下の比較表は、将来の判断のために残す。

`EnglishStudyLog.jsx` に表示される発音スコアは、
**実際の音声を解析した結果ではなく、ランダム値または固定ロジックで生成した見せかけの数値**です。

- UI とデータフローを確認するためのダミー実装
- 「録音 → スコア表示」という体験の流れを検証する目的で入れたもの
- **本実装では、実際の音声認識・発音評価に置き換える必要がある**

**検討すべき選択肢**

3案の詳細な比較、費用の概算は
[`PRONUNCIATION_OPTIONS.md`](PRONUNCIATION_OPTIONS.md) にまとめた。要約は以下。

| | 案1 ブラウザの音声認識 | 案2 発音評価サービス | 案3 端末内で解析 |
|---|---|---|---|
| 費用 | 無料 | 従量課金 | 無料 |
| 音素単位の評価 | ✕ | ◎ | △(精度不明) |
| 実装の手間 | 小(1〜2日) | 中(3〜5日) | 大(2週間〜) |
| Firefox で動くか | **✕ 既定で無効** | ○ | ○ |
| アプリ内ブラウザ | **△ 動かない場合が多い** | ○ | △ |
| **端末間でスコアが揃うか** | **✕ 揃わない** | **○ 揃う** | ✕ |

> ### 一般公開を前提とした場合の推奨は「案2」である
>
> 開発者本人の3台だけで使うなら案1で十分だったが、
> **不特定多数が様々な端末から使う前提では案1は成立しない。** 理由は2つ。
>
> **1. 一部の利用者がスコアを得られない**
> Firefox は音声認識が既定で無効。LINE や SNS のアプリ内ブラウザからも
> 動かない場合が多い。「一部の人だけ機能が使えない」状態になる。
>
> **2. これが決定的 — 端末が違うとスコアの意味が変わる**
> ブラウザの音声認識は、Chrome なら Google、Safari なら Apple と、
> **端末ごとに別の認識エンジンが動く。** 同じ発音でも認識結果が変わるため、
> 出てくるスコアは端末間で比較できない。
>
> 管理者画面は複数の学習者のスコアを並べて比較する画面である。
> A さんが iPhone、B さんが Android で練習していた場合、
> **その比較は意味をなさない。** これは機能の欠落ではなく、
> 数値としての正しさの問題であり、管理者機能の前提を壊す。
>
> 案2はサーバー側で採点するため、どの端末から録音しても同じ基準で採点される。
> 端末側に必要なのは録音機能だけで、これは Firefox を含め全環境が対応している。

`要確認`: 案2を採る場合、**どのサービスを使うか**と**利用量の上限をどう設ける**か。
不特定多数が使う以上、従量課金は青天井になり得るため、
「1人1日あたり N 回まで」といった制限が必須となる。

`参考`: 案1は、実機確認の結果しだいでは
**「案2が使えない環境向けの補助」**として残す選択肢はある。
ただし2つの採点方式が混在するとスコアの意味がさらに揃わなくなるため、
採用するなら案1のスコアは別枠(参考値)として扱う必要がある。

> ### ⚠️ 3.2 の前提に対する訂正
>
> 当初「案1なら音声が端末外に出ない」と想定していたが、これは**誤り**である。
> ブラウザの音声認識は音声をブラウザメーカーのサーバー(Chrome なら Google、
> Safari なら Apple)に送信して処理する。
>
> したがって **「音声を外部に送信しない」が成立するのは案3のみ**。
> 一方 **「音声をサーバーに保存しない」という方針は3案とも維持できる**
> (採点結果とメタデータのみを保存すればよいため)。
>
> どの案を選んでも、利用規約・プライバシーポリシーに
> 「発音採点のために音声を外部サービスへ送信すること」の記載が必要。

### 5.2 TTS のアクセント・自然さの限界

お手本音声にブラウザ内蔵の Web Speech API を使っているため、以下の制約があります。

- **利用できる音声(声質・アクセント)が OS とブラウザに依存する**
  同じコードでも Windows / macOS / iOS / Android で読み上げの声が変わる
- **アメリカ英語・イギリス英語などのアクセントを確実に指定できない**
  端末にその音声がインストールされていなければフォールバックされる
- 抑揚・リズムが機械的で、シャドーイングのお手本としては物足りない場面がある
- 音声の読み込みタイミングにブラウザ差があり、
  `speechSynthesis.getVoices()` が初回は空配列を返す端末がある(実装時の既知の落とし穴)

**すでに実施した改善(2026-08)**

「お手本の音声の質が悪すぎる」との指摘を受け、声の選び方を作り直した。

原因は、**英語の声のうち最初に見つかったものを無条件に選んでいた**こと。
端末には品質の異なる声が複数入っており、`getVoices()` の並び順は品質順ではない。
macOS には Bells / Zarvox といった学習用途に耐えないネタ声まで含まれる。

対処:

- 名前から品質を推定して並べ替え、**最も品質の高い声を既定にする**
  (Premium / Enhanced / Neural / Natural / Siri、提供元、`localService` を評価)
- **ネタ声を一覧から除外する**
- 簡易版(Compact)と癖の強い声の優先度を下げる
- 利用者が声を選び直せるようにし、**選択を記憶する**
- 読み上げの速さを選べるようにする(学習用に既定はやや遅め)
- 端末に良い声が無い場合は、**追加する手順を画面で案内する**
- 声の指定に失敗しても読み上げ自体は止まらないようにする

**それでも残る限界**

上記は「その端末にある声の中から最善を選ぶ」だけであり、
**端末に良い声が入っていなければ、品質は上がらない。**
また同じ英文でも、利用者ごとに聞こえる声が違う状態は変わらない。

| 環境 | 期待できる品質 |
|---|---|
| 高品質音声をダウンロード済みの iPhone / Mac | 良い |
| 初期状態の iPhone / Android | 端末による。簡易な声しかない場合がある |
| アプリ内ブラウザ | 声が1つも取得できない場合がある |

**対応の選択肢**

| | 内容 | 品質 | 費用 | 端末差 |
|---|---|---|---|---|
| 1 | 端末内蔵の音声のまま(現状) | 端末次第 | 無料 | **大きい** |
| 2 | **音声を事前に生成して配信する** | 高い | 生成時のみ | **なし** |
| 3 | ネイティブ話者の録音を用意する | 最高 | 制作コスト大 | なし |

> ### 一般公開を前提とすると「2」は選択肢ではなく必須である
>
> **お手本の音声は、この教材の中身そのものである。**
> 利用者ごとに品質が変わる状態は、教材として成立しない。
>
> 発音採点で案2(サーバー側で採点)を選んだのと**同じ理由**である。
> 端末に依存する仕組みは、不特定多数に配る前提と両立しない。
>
> **練習用の英文は固定の一覧である**ため、事前に音声を生成して
> 音声ファイルとして配信すれば、全端末で同一の品質になる。
> 例文が数百件程度なら生成費用は一度きりで済み、
> 配信は静的ファイルなので追加費用はほぼ発生しない。
>
> 端末内蔵の音声は、**事前生成した音声を用意できていない文章のための
> 予備**として残す。
>
> **2026-08 追記:** iOS では利用者が高品質音声をダウンロードしても
> ブラウザからは使えないことが実機で確認された(第 3.3.4 節)。
> 「利用者に良い音声を入れてもらう」という回避策は成立しない。
> したがってこれは推奨ではなく、**品質を確保する唯一の方法**である。

**話者(決定)**

| id | アクセント | 性別 |
|---|---|---|
| `us-female` | アメリカ英語 | 女性 |
| `us-male` | アメリカ英語 | 男性 |
| `uk-female` | イギリス英語 | 女性 |
| `uk-male` | イギリス英語 | 男性 |

選定の理由は「質と人間らしさ」である。利用者が Chrome の
Google 音声(通信型ニューラル音声)を聞いて明確に良いと判断した。
アクセントの好みではなく、音声そのものの自然さが基準となる。

地域訛り(スコットランド英語など)は後回しとする(第 7.1 節)。

`要確認`: 事前生成に使う音声サービス。Azure AI Speech を想定しているが、
利用開始にはアカウントと鍵が必要。

**運用(実装済み)**

英文を追加したら、足りない音声だけが自動で作られる。
GitHub に鍵を登録しておけば、英文を変更してプッシュするだけでよく、
手元でコマンドを実行する必要はない
(`.github/workflows/generate-audio.yml`)。

| 例文の数 | 文字数 | 費用 | 音声の容量 |
|---|---|---|---|
| 100件 | 約2万 | $0 | 約10MB |
| 500件 | 約10万 | $0 | 約48MB |
| 2,000件 | 約40万 | $0 | 約190MB |

費用は2,000件でも無料枠に収まる。ただし容量の観点から、
**500件を大きく超える場合は音声をリポジトリではなく
ストレージに置くべきである。** 同時に、英文の一覧も
JavaScript のファイルからデータベースへ移すのが自然である。

> **2026-08 追記:** この「要確認」には答えが出た。
> 週2回の自動更新を行う方針が決まったため、**年 約9,400件・約1.4GB** になる。
> 500件は初年度の1か月で超える。したがって
> **音声はストレージへ、例文はデータベースへ移すことが確定した。**
> 見積りの根拠は第 5.4 節。

### 5.3 その他の未実装

## 5.4 【将来・保留】学習コンテンツの規模と自動更新(2026-08 検討)

> **2026-08 の方向転換により、この節の内容は保留とする。**
> 「各レベル・各学習方法で週2回、自動でコンテンツが増える」仕組みは、
> **一般公開を前提とした設計**だった。
> スクールの既存生徒に限定した現在の方針では、教材は
> **トレーナーが弱点に応じて必要なときに作る**(第 2.3 節)ため、
> 定期的な自動生成は必要ない。
>
> 削除せずに残すのは、以下がスクール向けでもそのまま使える結論だからである。
>
> - 音読・オーバーラッピング・シャドーイング・リピーティングは
>   **同じ長文素材を共用できる**(第 5.4.3 節)。教材を4回作る必要はない
> - 速度違いは `audio.playbackRate` で対応し、**音声ファイルを増やさない**(第 5.4.3 節)
> - 音声は Git リポジトリではなく **ストレージに置く**(第 5.4.4 節)
> - 業界は階層ではなく **素材の属性(列1つ)として持つ**(第 5.4.8 節)。
>   スクール向けでも、生徒の職種に合わせた教材を作るときに同じ形が使える
>
> 規模の見積り(年 1.4GB など)は一般公開時の数字であり、
> スクール限定での見積りは第 5.5 節に置く。


アプリに載せる学習方法は **音読・オーバーラッピング・シャドーイング・
リピーティング・単語学習・フレーズ学習** の6種類。
そのすべてに音声を付け、**各レベル・各学習方法で週2回ほど自動で
コンテンツが増える**仕組みを作りたい、という要望が出た。

これは設計の前提を変える話なので、規模を先に見積もった。

### 5.4.1 見積りの前提

| 項目 | 値 |
|---|---|
| レベル | 3 |
| 1回の更新で増える件数 | 10 件 |
| 更新の頻度 | 週2回 |
| お手本の話者 | 4人(米女・米男・英女・英男) |
| 音声形式 | 48kbps モノラル MP3(1秒 ≒ 6KB) |

素材1件あたりの目安は、長文 120文字・15秒、単語 8文字・1秒、
フレーズ 25文字・3秒とした。

### 5.4.2 案A(学習方法6種を別々に作る)

| 項目 | 年間 |
|---|---|
| 素材 | 18,720 件(週 360 件) |
| 音声ファイル | 74,880 個 |
| 容量 | **約 4.6 GB** |
| 音声生成の文字数 | **月 約 53万文字** |

Azure TTS の無料枠は月50万文字なので、**案Aは初年度から無料枠を超える**。
容量 4.6GB/年 も Git リポジトリに置ける量ではない。

### 5.4.3 案B(長文を4つの学習方法で共用する) ← 採用

音読・オーバーラッピング・シャドーイング・リピーティングは、
**同じ英文素材に対してやり方が違うだけ**である。
素材を4回作る必要はなく、1つの長文素材を4つの学習方法から参照すればよい。

したがって作るべき素材の型は3つだけになる。

| 素材の型 | 使う学習方法 |
|---|---|
| 長文(passage) | 音読 / オーバーラッピング / シャドーイング / リピーティング |
| 単語(word) | 単語学習 |
| フレーズ(phrase) | フレーズ学習 |

| 項目 | 年間 |
|---|---|
| 素材 | 9,360 件(週 180 件) |
| 音声ファイル | 37,440 個 |
| 容量 | **約 1.4 GB** |
| 音声生成の文字数 | **月 約 16万文字**(無料枠 50万文字の 3分の1) |

案Aの約 1/3 に収まる。**案Bを採用する。**

> **再生速度は音声ファイルを増やさずに変えられる。**
> シャドーイングで「ゆっくり版」が欲しくなっても、
> ブラウザの `audio.playbackRate` で速度を変えられるので、
> 速度違いの音声ファイルを別に生成する必要はない。
> ここでファイルを増やすと容量が一気に倍増するため、必ず再生速度で対応する。

### 5.4.4 この規模から出てくる結論(重要)

**(1) 音声ファイルは Git リポジトリに置けない**

年 1.4GB は Git で扱う量ではない。Git は履歴をすべて保持するため、
一度入れたファイルは消しても容量が減らない。
**Supabase Storage(オブジェクトストレージ)に置く**必要がある。

`public/audio/` に置く現在のやり方は、
第 5.2 節に書いたとおり **例文500件程度まで**の暫定策である。

**(2) 例文の一覧は `src/data/practicePhrases.js` に置けない**

週180件増えるものを JavaScript のソースコードに書き続けることはできない。
アプリを作り直さないと内容が更新できない、という状態になる。
**データベース(Supabase の `materials` テーブル)に置く**必要がある。

**(3) したがって Supabase の接続が先になる**

以前は「発音評価 → 音声品質」の順を勧めたが、**この順序を変える**。
上の (1)(2) はどちらも Supabase がないと着手できない。
Supabase を先に用意しないと、あとから全部作り直すことになる。

**(4) 例文の自動生成そのものは安い**

素材の型3種 × レベル3 × 週2回 = 年936回の生成リクエストで済む。
Claude API(`claude-opus-5`)で見積もると **月 約 $3.7**、
即時性の要らない生成なので Batch API を使えば **月 約 $1.9**。
費用は問題にならない。**問題になるのは品質管理のほう**(次項)。

### 5.4.5 自動更新の設計方針

自動生成した英文をそのまま学習者に出すのは危険である。
不自然な英語・レベル不一致・重複・不適切な話題が混ざりうる。
そのため **「下書き → 確認 → 公開」の3段階**にする。

```
週2回 (GitHub Actions の定期実行)
  ↓
① Claude API で素材を生成       → status = 'draft'
  ↓
② 自動チェック                   → 重複・語数・禁止語・レベル判定
  ↓
③ 管理画面で人が確認して公開      → status = 'published'
  ↓
④ 公開されたものだけ Azure TTS で音声生成 → Supabase Storage
  ↓
⑤ 学習者アプリは published のみ取得
```

- ③ を通らないものは学習者に出ない。最初のうちは全件を目で見る。
  慣れてきたら「自動チェックを通ったものは自動公開」に緩めればよい。
- ④ を ③ の後に置くのは、**没にした素材の音声を作らないため**。
  先に音声を作ると、無料枠と容量を無駄に使う。

`要確認`: 生成する素材の題材(日常会話 / ビジネス / 学校教科書準拠 など)。
既存の教材や書籍から文章を取り込むと著作権の問題が出るため、
**素材はすべて新規生成し、既存教材からの転載はしない**方針とする。

### 5.4.8 業界(分野)を軸に加えるか(2026-08 検討)

「各レベル・各学習コンテンツについて、さらに業界を分けられるか」という
要望が出た。医療、IT、接客など、利用者の仕事に合わせた教材を出したい、という趣旨。

**結論: 加えられる。ただし「業界を1つの階層」として掛け算にしてはならない。**

#### 3つの入れ方と規模

| 入れ方 | 業界3種 | 業界6種 | 業界10種 |
|---|---|---|---|
| ① 業界ごとに丸ごと複製する | 4.1 GB/年 | **8.1 GB/年 ⚠️** | **13.6 GB/年 ⚠️** |
| ② 総量を固定して業界に配分する | 1.4 GB/年 | 1.4 GB/年 | 1.4 GB/年 |
| ③ 汎用は据え置き + 業界別を上乗せ | **2.0 GB/年** | 2.7 GB/年 | 3.4 GB/年 |

⚠️ は Azure TTS の無料枠(月50万文字)を超えるもの。

- **案①は選べない。** 業界6種で無料枠を超え、10種で 13.6GB/年 になる。
  業界を1つ足すたびに費用と容量が丸ごと増える構造は、破綻するのが目に見えている。
- **案②は容量が増えない代わりに中身が痩せる。** 業界6種に分けると
  1業界あたり週26件しか増えない。利用者から見ると
  「自分の業界の教材が全然増えない」となる。
- **案③を採用する。** 汎用(日常会話)は現行の週180件を維持し、
  業界別を週30件ずつ上乗せする。業界3種でも 2.0GB/年 に収まる。

#### 業界別の上乗せ量を抑えられる根拠

案③で「業界別は週30件」に抑えられるのは、次の2つの理由による。

**(1) 業界別が意味を持つのは中級以上**

基礎語彙が足りない段階で「医療英語」をやっても効果が薄い。
初級の利用者にはまず汎用の基礎を固めてもらうほうがよい。
したがって **業界別はレベル2・3のみに出す**。これで上乗せ量が 2/3 になる。

**(2) 学習方法そのものは業界に依存しない**

シャドーイングやオーバーラッピングのやり方は、素材が医療英語であろうと
日常会話であろうと変わらない。**業界を足しても学習方法は増えない。**
第 5.4.3 節で決めた「長文を4方法で共用する」構造がそのまま効く。

#### 業界は「階層」ではなく「素材の属性」として持つ

設計上の要点はここである。業界ごとにテーブルやフォルダを分けるのではなく、
**`materials` テーブルに列を1つ足すだけ**にする。

```
materials
  ...
  industry   text   NULL = 汎用(全員に出す)
                    'it' / 'medical' / 'hospitality' / 'manufacturing' ...
```

こうすると:

- 業界を1つ足す作業は「新しい値を使い始める」だけで、**スキーマ変更もアプリ改修も不要**
- 業界をやめる判断も、その値の素材を非公開にするだけで済む
- 利用者には **汎用 + 自分が選んだ業界** を出す。
  業界を選んでいない利用者には汎用だけが出るので、
  業界機能を後から足しても既存の利用者の体験は変わらない

`profiles` 側にも1列足す(`industry`、NULL = 未選択)。

#### 需要駆動で生成する(重要な運用ルール)

**利用者がいない業界の素材は作らない。**

案③の 2.0GB/年 は「業界3種を常時回した場合」の数字である。
実際には、公開直後は業界別の利用者がゼロなので、**汎用だけで始める**。
利用者が集まってきた業界から1つずつ有効にしていく。

こうすれば、誰も聞かない音声のために無料枠と容量を使うことがない。
生成の自動処理(第 5.4.5 節)には、
**「有効な業界」の一覧を見て回す**作りにしておく。

#### 業界の粒度は粗くから始める

細かく分けるほど1業界あたりの中身が痩せる(案②の問題が案③でも起きる)。
最初は3〜5程度の粗い区分から始め、利用者が偏ってきたら分割する。

`要確認`: 最初に用意する業界の区分。以下は案。

| 区分 | 想定 |
|---|---|
| (汎用) | 日常会話。全員に出す既定 |
| ビジネス全般 | 会議、メール、電話、出張 |
| IT・技術 | 開発、仕様説明、障害対応 |
| 医療・介護 | 患者対応、記録、多職種連携 |
| 接客・観光 | 案内、予約、トラブル対応 |

#### 管理画面への影響

利用者ごとに出る教材が変わるが、**発音スコアの比較には影響しない。**
管理画面が見ているのは「同じ学習者の推移」であり、
学習者どうしで同じ英文を読ませて比べる作りにはなっていない。

ただし「この英文を何人が練習したか」のような素材単位の集計を将来入れる場合、
業界で母数が分かれることに注意する。

## 5.5 スクール限定での規模(2026-08 確定: 生徒30人・トレーナー1人)

第 5.4 節の見積りは一般公開を前提としたもの。スクール限定なら前提が変わる。

### 確定した前提

| 項目 | 値 |
|---|---|
| 生徒数 | **最大 30 人** |
| トレーナー | **1 人**(開発者本人) |
| レッスン | 1人あたり週2回 → **週 60 レッスン** |
| 教材1件の英文 | 8 文(1文 約60文字・約5秒) |
| お手本の話者 | 2人(男女1人ずつ) |

### 結論: 制約は費用ではなく「トレーナーの作業時間」である

費用は最大でも月 $34 で、どの条件でも問題にならない。
**問題になるのは、トレーナー1人が週に何件の教材を作れるかである。**

1レッスンで 1.5 件出すとして、週 90 件を配信する場合:

| 再利用率 | 新規に作る | **トレーナーの作業/週** | 音声/年 | 生成費/月 |
|---|---|---|---|---|
| 0%(毎回新規) | 90 件 | **9.0 時間** ← 不可能 | 2.14 GB | $25.3 |
| 50% | 45 件 | 5.3 時間 | 1.07 GB | $12.7 |
| 70% | 27 件 | 3.8 時間 | 0.64 GB | $7.6 |
| **85%(目標)** | **14 件** | **2.6 時間** | **0.32 GB** | **$3.8** |
| 95% | 5 件 | 1.9 時間 | 0.11 GB | $1.3 |

> 作業時間は「AI の下書きを直して発行するのに1件6分、
> ライブラリから選んで配信するだけなら1件1分」として計算した仮定値。
> 実際に運用してから実測して置き換える。

**週60レッスンを担当したうえで、教材づくりに週9時間は割けない。**
つまり **教材ライブラリの再利用は、費用の節約策ではなく、
この仕組みが1人で回るかどうかを決める前提条件である。**

### この結論が設計に与える影響(重要)

教材作成画面は、**再利用を最短路にしなければならない。**

| 設計 | 理由 |
|---|---|
| 既定の動線は「**ライブラリから探す**」。AI 生成は2番目に置く | 逆にすると毎回作ってしまい、再利用率が上がらない |
| 発行時に**弱点タグを必須にする** | タグの付いていない教材は二度と見つからず、資産にならない |
| 「この弱点で過去に配信した教材」を**1クリックで出す** | ①→②(第 2.3 節)を数秒で終わらせる |
| **1つの教材を複数の生徒に同時配信できる** | 週60レッスンなら、同じ弱点の生徒は必ず複数いる |

### ライブラリが埋まるまでの見通し

弱点タグ37個 × レベル3 = **111 通り**。
1通りにつき3件そろえば、たいていの指摘に即応できる → **約 333 件**。

| 週に作る新規教材 | 333 件そろうまで |
|---|---|
| 18 件 | 約 18 週(4か月半) |
| 27 件 | 約 12 週(3か月) |

**最初の3〜4か月はライブラリを育てる期間**と考える。
この期間は再利用率が低く、作業時間が最も重い。

### したがって、30人全員で始めない

開始直後の再利用率は 0% であり、いきなり30人だと週9時間かかる。
**段階的に増やす。**

| 時期 | 生徒数 | 週の新規作成 | トレーナーの作業/週 |
|---|---|---|---|
| 導入期(1〜2か月) | 5 人 | 約 15 件 | 約 1.5 時間 |
| 拡大期(3〜4か月) | 15 人 | 約 25 件 | 約 2.8 時間 |
| 定常(5か月〜) | 30 人 | 約 14 件 | 約 2.6 時間 |

定常期に作業が減るのは、**ライブラリが育って再利用が効きはじめる**ため。
生徒が増えても作業が増えないのがこの仕組みの狙いである。

`要確認`: 1レッスンで出す教材の件数(上表は 1.5 件と仮定)。
`要確認`: 1件あたりの実作業時間(上表は6分と仮定)。導入期に実測する。

### 容量と費用のまとめ

再利用率85%なら音声は **年 0.32GB**。
**Supabase の無料枠(1GB)で3年もつ。**
Azure TTS は月56,160文字で無料枠(50万文字)の1割強。**音声は実質 $0。**
教材生成(Claude API `claude-opus-5`)が **月 $3.8**。

**月額の合計は $4 程度**で、生徒30人・トレーナー1人の規模なら十分に収まる。

## 5.6 組織の規模とアクセス範囲(2026-08 確定)

当初は「トレーナー1人・生徒30人」だったが、実際の構想は
**トレーナー約50人・1人あたり生徒30人 = 生徒 約1,500人**である。
あわせて「全体の集計だけを見る管理者」という3つ目の役割が必要になった。

### 5.6.1 規模

| 項目 | 年間 |
|---|---|
| 生徒 | 1,500 人 |
| 週のレッスン | 3,000 回 |
| 配信する宿題 | 234,000 行 |
| 発音練習の記録 | 1,170,000 行 |
| 学習記録 | 312,000 行 |
| チャット | 468,000 行 |
| **データベースの容量** | **約 0.63 GB / 年** |
| 音声の転送量 | 約 30 GB / 月 |

- Supabase の無料枠(DB 500MB)は**初年度で超える。Pro(月 $25 前後)が要る。**
  Pro は DB 8GB・転送 250GB を含むので、上の数字は収まる。
- **音声の容量は生徒数では増えない。** 教材ごとに1つ作るだけで、
  1,500人が同じ音声を聞く。3年ためても 0.5GB 程度。

### 5.6.2 教材ライブラリは50人で共有する ← 大きな変化

第 5.5 節では「トレーナー1人だと、ライブラリがそろうまで3〜4か月」だった。
**50人で共有すれば、1人が週1件作るだけで全体では週50件。7週でそろう。**

| 作り方 | 333件そろうまで |
|---|---|
| トレーナー1人(第 5.5 節) | 約 18 週 |
| **50人で共有** | **約 7 週**(1人が週1件) |
| 50人で共有・1人が週2件 | 約 4 週 |

したがって `materials.visibility` の既定は **`school`(全トレーナーで共有)** とする。
`private` を選べば自分だけの下書きにできる。

**共有が既定であることは品質管理の要件を強める。** 1つの悪い教材が
1,500人に届きうる。発行前の確認を省かないこと(第 2.3 節④)。

### 5.6.3 役割は3つ

| 画面に書く言葉 | `profiles.role` | できること |
|---|---|---|
| 生徒 | `learner` | 自分に配信された教材と自分の記録だけ |
| トレーナー | `trainer` | 担当生徒の記録、共有された教材、自分の教材 |
| 管理者 | `owner` | **全体の集計。** トレーナーの権限も兼ねる |

0001 では `admin` の2値だった。0002 で3値に変え、既存の `admin` は
`trainer` へ移した。**アカウントが増える前に変えた**(後からだと全員の
データを移す作業になり、間違えれば見えてはいけないものが見える)。

### 5.6.4 管理者には「生の記録」を渡さず、「集計」だけを返す ← 重要な設計

管理者が見たいのは平均や件数であって、個々の生徒の録音回数ではない。
そこで **行を読む権限を増やさず、集計を計算して返す関数だけを渡す。**

```
✕ owner に「全部の行が読める」権限を与える
    → その権限が漏れたら、全生徒のデータが出る

○ owner だけが呼べる「集計を返す関数」を用意する
    → 漏れても出るのは平均値だけ。生の行は誰も余分に読めない
```

実装は `security definer` 関数(`school_summary` / `trainer_summary`)。
RLS を迂回するのは関数の内側だけで、外に出るのは集計値のみ。
関数の中に `where public.is_owner()` を入れてあるので、
**管理者以外が呼んでも0行しか返らない**(テストで確認済み)。

`要確認`: 管理者が個々の生徒の詳細を見る必要が出た場合の扱い。
現時点では「見せない」で設計している。必要になったら、
**誰がいつ誰のデータを見たかを記録する**仕組みとあわせて検討する。

### 5.6.5 社内での共有は2種類ある

混同しやすいので分ける。

| 何を共有するか | 仕組み | 状態 |
|---|---|---|
| **教材** | `materials.visibility = 'school'` | ✅ 0002 で実装 |
| **生徒の情報** | `learner_admins` は多対多。副担当を足せる | 仕組みはあるが画面が未実装 |

`要確認`: 「指定した内容だけ社内に共有したい」の具体的な単位。
教材(実装済み)なのか、特定の生徒の特定の期間なのか、
レッスンの記録1件なのかで、必要なものが変わる。

### 5.6.6 個人情報についての注意(方針の転換にあたる)

トレーナー1人・生徒30人のときは「スクール内の閉じた運用」だった。
**50人・1,500人になると、社内であっても「誰がどこまで見られるか」を
決めて記録に残す必要がある。**

- 生徒に未成年が含まれるなら、保護者への説明と同意(第 1.2.1 節)
- 退職したトレーナーのアカウントを止める運用
- 担当が変わったときに前任者から見えなくする運用

第 5.6.4 節の「集計だけ返す」は、この要件を設計で満たすための措置でもある。

## 5.7 チャット機能(2026-08 検討)

生徒とトレーナーがアプリの中でやりとりできるようにしたい、という要望。

### 5.7.1 Slack は要らない

| | アプリ内チャット | Slack |
|---|---|---|
| 生徒側の準備 | **不要**(ログイン済み) | 1,500人分のアカウントが要る |
| 学習データとの結びつき | **宿題や教材に紐づけられる** | 失われる |
| データの置き場 | 自分たちのデータベース | 外部サービス |
| 絵文字 | **使える** | 使える |
| 即時に届くか | **届く**(Supabase Realtime) | 届く |
| **通知(アプリを閉じているとき)** | **弱い** ← 唯一の弱点 | 強い |
| 費用 | 実質 $0 | 人数分の課金 |

**Slack を使うと、生徒のやりとりが別のサービスに出る。**
「学習にまつわるデータは1か所にまとめる」という方針(第 3.2 節)に反する。
また「どの宿題についての話か」が失われ、弱点→教材の循環から切り離される。

**アプリ内で作る。**

### 5.7.2 唯一の弱点は通知

アプリを開いていないと気づかない。対策は3段階あり、後から足せる。

| 段階 | 方法 | 手間 |
|---|---|---|
| 1 | アプリを開いたときに未読の印を出す | 小 |
| 2 | メールで知らせる(Supabase の仕組みで送れる) | 中 |
| 3 | スマホの通知(PWA のプッシュ通知) | 大。iOS では制約が多い |

**まず1から始める。** レッスンが週2回ある関係なので、
即時性が要る場面は多くない。

### 5.7.3 絵文字は使える

データベースは文字をそのまま保存するので、**絵文字は何もしなくても使える。**
絵文字での反応(リアクション)を付けたい場合は、
「どのメッセージに・誰が・どの絵文字を」を記録する表を1つ足せばよい。

### 5.7.4 追加になるデータモデル(未実装)

```
message_threads              やりとりの単位
  id            uuid
  learner_id    uuid → profiles.id    その生徒についてのやりとり
  assignment_id uuid → assignments.id 宿題に紐づく場合。NULL なら雑談
  created_at    timestamptz

messages
  id            uuid
  thread_id     uuid → message_threads.id
  sender_id     uuid → profiles.id
  body          text                  絵文字はそのまま入る
  read_at       timestamptz           未読の印に使う
  created_at    timestamptz

message_reactions            絵文字での反応(必要になったら)
  message_id    uuid
  user_id       uuid
  emoji         text
```

アクセス制御の方針は他と同じ。
**生徒は自分のやりとりだけ。トレーナーは担当生徒のやりとりだけ。
管理者は中身を読めない**(集計のみ。第 5.6.4 節)。

`要確認`: トレーナー同士のやりとりを同じ仕組みで扱うか。
上の設計は「生徒との1対1」を前提にしている。

## 5.8 アカウントの発行(2026-08 確定)

**トレーナー約50人と生徒約1,500人は、Supabase も GitHub も一切触らない。**
アプリの画面だけでアカウントを作れる必要がある。

### 5.8.1 なぜ素直にできないか

アカウントを作る方法は2つしかなく、**どちらもそのままでは使えない。**

| 方法 | 問題 |
|---|---|
| 自由登録(`signUp`) | **生徒が勝手に登録できてしまう。** 第 1.2 節の方針に反する |
| 管理者として作る(`auth.admin.createUser`) | **`service_role` の鍵が要る。** ブラウザに置いた時点で全データが漏れる |

### 5.8.2 解決策: Supabase のサーバー上に受付窓口を置く

Edge Function(`supabase/functions/create-user`)を1つ置く。
**`service_role` の鍵はこの関数の中だけにあり、ブラウザにも
GitHub にも利用者の手元にも出ない。**

```
トレーナーのブラウザ
  「生徒を追加: 田中 / ID: tanaka01 / パスワード: ****」
        ↓ 自分のログイン情報を添えて送る(鍵は送らない)
Supabase のサーバー上の受付窓口   ← service_role はここだけにある
        ↓ ① 送ってきた人がログインしているか
        ↓ ② その人がトレーナーか管理者か(生徒は誰も作れない)
        ↓ ③ トレーナーは「生徒」しか作れない
        ↓ ④ 作った生徒を、そのトレーナーの担当に登録する
   完了
```

**③がこの設計の要である。** これが無いと、トレーナーが自分用の
管理者アカウントを作り、全生徒の集計を見られるようになる。
**役割の判定は必ずサーバー側で行い、ブラウザから送られた値は信用しない。**

### 5.8.3 誰が誰を作れるか

| 作る人 | 作れる役割 | 備考 |
|---|---|---|
| 生徒 | **なし** | 呼んでも 403 で断られる |
| トレーナー | 生徒のみ | 作った生徒は自動で自分の担当になる |
| 管理者 | 生徒・トレーナー・管理者 | |

### 5.8.4 ログインは「ID」で行う

要望は「IDとパスワードだけ」。Supabase のログインはメールアドレスの形を
要求するため、**ログインIDから実在しないメールアドレスを組み立てる。**

```
ログインID: tanaka01
  → 内部では tanaka01@users.english-ai-system.local として登録
```

作成時に確認済みにするので、**メールは1通も送らない。**
利用者はIDとパスワードだけを覚えればよい。

> **この方式の代償:** メールが実在しないため、
> **「パスワードを忘れた」を利用者自身で解決できない。**
> トレーナーが生徒の、管理者がトレーナーのパスワードを再設定する運用になる。
> 週2回顔を合わせる関係なので、この運用で回ると判断した。
>
> `要確認`: 生徒が実在のメールアドレスを持っている場合、
> そちらを使えば自分で再設定できる。どちらにするかは運用しながら決める。

### 5.8.5 必要になる画面(未実装)

- [ ] 管理者: トレーナーの追加・一覧・停止
- [ ] トレーナー: 生徒の追加・一覧・停止
- [ ] トレーナー: 自分の生徒のパスワード再設定
- [ ] 管理者: トレーナーのパスワード再設定
- [ ] 停止したアカウントはログインできない仕組み

`要確認`: 「停止」の実装方法。`profiles` に列を足して RLS で弾くか、
Supabase Auth 側で禁止するか。**退職したトレーナーが担当生徒の
データを見続けられないこと**が要件(第 5.6.6 節)。

### 5.8.6 この関数を Supabase に置く作業について

Edge Function は、書いただけでは動かない。Supabase に配置する必要がある。

- **この作業環境からは配置できない**(`supabase.co` への通信が遮断されている)
- 配置は Supabase の管理画面上の関数エディタ、または利用者の Mac から
  Supabase CLI で行う。**どちらが使えるかは実際の画面で確認する**
- **配置は最初の1回だけ。** 以後、トレーナー50人はこの作業に関わらない

## 5.9 担当の引き継ぎと退職(2026-08 確定)

トレーナーは退職する。生徒の希望で担当が変わることもある。
**トレーナー50人の規模では日常的に起きる**ので、仕組みで扱う。

### 5.9.1 同時に満たすべき3つのこと

| | 内容 |
|---|---|
| **1. 過去の記録を壊さない** | 「誰が配信したか」「誰がフィードバックしたか」はトレーナーに紐づく。**退職者を削除すると過去の記録ごと壊れる** |
| **2. 弱点の履歴を引き継ぐ** | 新しい担当は、その生徒の過去のレッスン記録と弱点を知らないと指導できない |
| **3. 前の担当を断つ** | 退職後も担当生徒のデータが見え続けてはいけない(第 5.6.6 節) |

### 5.9.2 「消さずに止める」

`profiles.status`(`active` / `inactive`)を足した。**行は消さない。**

- 停止された人は、ログインできてもデータが一切見えない
  (`is_trainer()` / `is_owner()` / `teaches()` が偽になる)
- その人が過去に残した配信やレッスン記録は、そのまま残る

### 5.9.3 担当には「期間」を持たせる

`learner_admins` に `started_on` / `ended_on` / `handover_note` を足した。

- `ended_on` が NULL なら現在の担当。日付が入っていれば過去の担当
- 担当を外すのは「終わりの日を入れる」だけ。**履歴が残る**
- 同じ人が再び担当になることもあるため、行ごとの `id` を主キーにした
  (元の複合キーだと2回目を登録できない)

`teaches()` に「終わっていないこと」を加えたので、
**引き継ぎと退職が、そのままアクセス制御に効く。**

### 5.9.4 引き継ぎは1回の操作で行う

`transfer_learner(生徒, 新しい担当, 申し送り)` — **管理者のみ。**

「前の担当を終わらせる」と「新しい担当を始める」を別々に行うと、
片方だけ実行された中途半端な状態が起こりうる。1つの関数にまとめてある。

`retire_trainer(トレーナー, 引き継ぎ先, 申し送り)` — **管理者のみ。**
担当生徒をまとめて引き継ぎ、本人を停止する。
**自分自身は停止できない**(管理者が誰もいなくなるのを防ぐ)。

`deactivate_learner(生徒)` — 管理者、または担当トレーナー。

### 5.9.5 引き継ぎで何が残り、何が断たれるか(テストで確認済み)

| | |
|---|---|
| **新しい担当に見えるもの** | その生徒の学習記録、**過去のレッスン記録、弱点の指摘内容**、宿題の履歴 |
| **前の担当に見えるもの** | **何も見えない**(その日のうちに) |
| **残るもの** | 担当の履歴(誰がいつ担当だったか)、退職者が残した記録 |

**紙の引き継ぎより確実である。** 前の担当が積み上げた弱点の履歴が
そのまま次の担当に渡るので、引き継ぎ直後から的確な教材を出せる。
これはこのアプリの利点のひとつとして数えてよい。

`要確認`: 引き継ぎの際、前の担当が指摘した弱点のうち
「まだ克服していないもの」を新しい担当に強調して見せる画面。
仕組みとしてはデータがそろっているので、画面を作れば実現できる。

## 5.10 生徒の在籍状態とトレーナーの休み(2026-08 確定)

### 5.10.1 在籍状態は3つ

| 画面に書く言葉 | `profiles.status` | 内容 |
|---|---|---|
| **受講中** | `active` | 通常 |
| **休会中** | `paused` | 月額コース休止中 / 回数コース修了後 |
| **退会済** | `inactive` | 全額返金で退会 など |

トレーナーは `active`(在籍中)/ `inactive`(退職)の2つを使う。
理由は `status_note` に残す(例:「回数コース修了後」「全額返金で退会」)。

### 5.10.2 休会中にできること・できないこと

| | 休会中 | 退会済 |
|---|---|---|
| 自分の過去の学習記録を見る | **○** | ✕ |
| 配信済みの教材を見る | **○** | ✕ |
| 新しい宿題が配信される | **✕** | ✕ |
| 担当トレーナー | **外れない**(戻ってきたら再開) | 外れる |
| 集計での扱い | 「休会中」として別に数える | 「退会済」として別に数える |

**休会中に担当を外さないのが要点。** 戻ってきたときに、
過去の弱点の履歴ごとそのまま再開できる。

**新しい宿題を配信できないことは、画面ではなくデータベース側で止めている。**
画面の作りに関係なく成立する。

> **退会したら、自分の記録も見えなくなる。**
> ただし自分のプロフィール(名前と状態)だけは読めるままにしてある。
> 読めないと、アプリが「退会済です」と表示することすらできなくなるため。

### 5.10.3 トレーナーの休みの予定

`trainer_absences`(期間 + 理由)。

| 誰が | できること |
|---|---|
| トレーナー本人 | 自分の休みを入れる・直す |
| 管理者 | 全員分を入れる・直す・見る |
| **担当している生徒** | **見るだけ** |
| 担当ではない生徒 | 見えない |

> `reason` は生徒にも見えるため、**私的な事情は書かない前提**で運用する。
> 「研修のため」「夏季休暇」程度にとどめる。この注意は列のコメントにも書いた。

## 5.11 【要判断】カレンダーとタスクの共有

「管理者とトレーナーの間でカレンダーやタスクを共有したい」という要望。
**技術的にはどちらも作れる。ただし作るべきかは分けて考える。**

### 5.11.1 カレンダーは作らないほうがよい

本格的なカレンダーに必要なものは、実際にはとても多い。

| 必要なもの | 自作すると |
|---|---|
| スマホのカレンダーとの同期 | 大きな手間 |
| 繰り返しの予定(毎週火曜など) | 意外に複雑 |
| 予定の招待と出欠 | 大きな手間 |
| 通知・リマインド | 第 5.7.2 節と同じ壁 |

**Google カレンダー等が無料で、はるかに良くできている。**
ここは既存のものを使うほうがよい。

**例外はすでに作った。** トレーナーの休み(第 5.10.3 節)は
**生徒に見せる必要がある**ため、アプリの中にある必要があった。
社内だけの予定は外のカレンダーでよい。

### 5.11.2 タスクはアプリの中に作る価値がある

一方タスクは違う。このアプリのタスクは、**生徒や教材に紐づく**ためである。

```
「田中さんの語尾の子音の教材を作る」  → 生徒と弱点タグに紐づく
「引き継いだ3人の弱点履歴を確認する」  → 引き継ぎに紐づく
「今週発行した教材を見直す」           → 教材に紐づく
```

外のタスク管理ツールに書くと、**その生徒の画面から1クリックで飛べない。**
アプリの中にあれば、タスクから生徒へ、生徒から教材へ、そのまま進める。

`要判断`: 作るかどうか、作るならいつか。
**第1段階(教材の作成と配信)より後**でよいと考えている。

想定するデータモデル(未実装):

```
tasks
  id           uuid
  title        text
  assignee_id  uuid → profiles.id   担当者。NULL なら誰でも
  created_by   uuid → profiles.id
  learner_id   uuid → profiles.id   関係する生徒。NULL 可
  material_id  uuid → materials.id  関係する教材。NULL 可
  due_on       date
  done_at      timestamptz
  created_at   timestamptz
```

アクセス制御の方針:トレーナーは自分に割り当てられたものと
自分が作ったもの。管理者は全部。**生徒には見えない。**

## 5.12 さらに規模が大きくなった場合(2026-08 試算)

「トレーナーが100人、150人と増えたら、Supabase の有料プランで対応できるか」

**できる。** 試算は以下のとおり(1人あたり生徒30人で計算)。

| トレーナー | 生徒 | データベース/年 | 5年後 | 転送/月 | プラン |
|---|---|---|---|---|---|
| 50 | 1,500 | 0.63 GB | 3.2 GB | 30 GB | **Pro $25** |
| 100 | 3,000 | 1.26 GB | 6.3 GB | 59 GB | **Pro $25** |
| 150 | 4,500 | 1.90 GB | 9.5 GB | 89 GB | Pro + 容量追加 |
| 300 | 9,000 | 3.79 GB | 19.0 GB | 177 GB | Pro + 容量追加 |

- Pro プランの含み(2026-08 の公開情報):DB 8GB / 転送 250GB / ストレージ 100GB
- **トレーナー100人までは Pro のまま**(月 $25)
- 150人・5年運用で DB が 1.5GB 超過 → **追加は月 $0.2 程度**

**費用は問題にならない。** 150人規模でも月 $25〜30 の見込み。
生徒4,500人で割ると 1人あたり月 1円未満。

`要確認`: 上記は 2026-08 時点の公開情報にもとづく概算。
契約前に最新の料金を確認する。

### 5.12.1 費用より先に問題になるもの

規模が大きくなったときに効いてくるのは、容量ではなく次の2つ。

| | 内容 |
|---|---|
| **アクセス制御の複雑さ** | トレーナーが増えるほど「誰が誰を見られるか」の組み合わせが増える。**`npm run test:db` の項目を増やし続けること**が唯一の防波堤 |
| **教材の品質管理** | 共有ライブラリなので、悪い教材1つが全生徒に届く。150人規模だと 4,500人。発行前の確認をどう担保するかが課題になる |

**Supabase の容量は、増やせばよいので心配しなくてよい。
心配すべきはこの2つである。**

## 5.13 教材の実際の形(2026-08 実物から確定)

利用者が**レッスン中に生徒の目の前で作っている本物のドリル**を共有してもらった。
それまでの設計は形が間違っていた。ここに実物から分かったことを残す。

### 5.13.1 設計が間違っていた点

| それまでの想定 | 実際 |
|---|---|
| 教材 = 英文の並び | 教材 = **1つの文法ポイントを軸にした演習のまとまり** |
| 項目は1種類 | **演習が複数種類**(和訳・穴埋め・英訳・リスニング) |
| 英文と訳だけ持てばよい | **解答・与える語・設問・読み上げ用の英文**が要る |
| 1教材 8〜30文 | **40問で「3日分のほんの一部」** |

実物(名詞 + to不定詞 =「〜すべき/〜する必要のある」)の構成:

```
教材:「名詞 + to不定詞」        指導ポイント: reply to の to を落とすな
  ├ ① 英文和訳    × 10   英文 → 和訳
  ├ ② 穴埋め      × 10   穴あき文 + 与える語(reply to)→ 解答(to reply to)
  ├ ③ 和文英訳    × 10   日本語 → 英語(解答例。別解あり)
  └ ④ リスニング  × 10   読み上げ文(見せない)+ 設問 + 解答
```

**②と④は、それまでの形では表現できなかった。**
②は「与える語」を、④は「設問」と「見せない英文」を持つ場所が無かった。

### 5.13.2 直した形

```
materials         教材 = 1つの文法ポイント
  teaching_point  教材全体にかかる指導ポイント
    ↓
material_sections 演習(①②③④)
  exercise_type   和訳 / 穴埋め / 英訳 / リスニング / 音読 / シャドーイング …
  instruction     その演習の指示文
    ↓
material_items    設問
  prompt_en   英語で提示するもの(和訳の出題文、穴あき文)
  prompt_ja   日本語で提示するもの(英訳の出題文)
  hint        与える語(穴埋め)
  question    設問(リスニング)
  answer      解答 / 解答例
  answer_alt  別解(和文英訳は複数ありうる)
  audio_text  読み上げる英文。**音声を作る対象はこの欄**
  note        1問ごとの補足
```

演習の種類ごとに使う欄が違う。使わない欄は空のままにする。

| 種類 | prompt_en | prompt_ja | hint | question | answer | audio_text |
|---|---|---|---|---|---|---|
| 英文和訳 | 出題文 | | | | 和訳 | 出題文 |
| 穴埋め | 穴あき文 | | 与える語 | | 入る語 | **作らない** |
| 和文英訳 | | 出題文 | | | 解答例 | 解答例 |
| リスニング | | | | 設問 | 解答 | 読み上げ文 |
| 音読ほか | 英文 | 訳 | | | | 英文 |

**この形が実物を収められることは、実際のドリルをそのまま入れて確認した**
(`supabase/test/material_shape_test.sql`、11項目)。
「reply to の to が解答に残る」ことまで検証している。

### 5.13.3 ボリュームの決め方

実物は **4演習 × 10問 = 40問で「3日分のほんの一部」**。
利用者の言葉:「同じ文法を使った違う文章を30個あって、やっと理屈ではなく
頭が語順に慣れる」。**量は定着の条件であって、削る対象ではない。**

決め方は次のとおり(2026-08)。

| 教材の種類 | 演習の既定 | 1演習あたり |
|---|---|---|
| **文型ドリル**(新設) | 和訳 / 穴埋め / 英訳 / リスニング | **各10問 = 40問** |
| 長文 | 音読 / オーバーラッピング / シャドーイング | 1本 150〜200語 |
| 単語 | 単語 | 20語 |
| フレーズ | フレーズ | 20 |

- トレーナーが増減できる
- **分割配信**(40問を10問ずつ4回に分けて出す)は、同じ教材を複数回
  配信するだけで実現できる。仕組みは既にある。
  **量と同じくらい「間隔」が定着に効く**ため、1回で出し切らない運用を勧める

### 5.13.4 費用への影響(1教材40問で計算し直した)

| 項目 | 値 |
|---|---|
| 音声を作る対象 | 40問中 **約20問**(穴埋めと一部の英訳は作らない) |
| ライブラリ全体(333教材)の音声 | 約 0.6 GB |
| 初回の TTS 文字数 | 約 110万文字 → **3か月に分ければ無料枠内** |
| 定常期の TTS | 月 約38万文字(無料枠 50万文字の内) |
| 定常期の生成費(Claude API) | **月 約 $9** |

**費用は問題にならない。** 文数を増やしても効いてくるのは
トレーナーの確認時間だけであり、**同じ文型が並ぶ教材は
1問目を直せば残りは流し読みで済む**ため、比例しては増えない。

### 5.13.5 自動生成の設計(未実装)

`要確認`: Claude API の鍵が必要。実装はアカウント発行と同じく
Supabase 上の受付窓口に置き、鍵をブラウザに出さない(第 5.8 節と同じ形)。

```
トレーナーの操作は2つだけ
  ① 生徒を選ぶ(複数可)
  ② 弱点タグを選ぶ ← レッスンで指摘したもの
        ↓
  AI が40問を生成(生徒のレベル14段階と業界を自動で反映)
        ↓
  ③ トレーナーが目を通して直す  ← ここは省けない
        ↓
  ④ 発行 → 配信(教材名は日付・弱点・生徒名から自動)
```

**③を省けない理由:** 共有ライブラリなので、悪い教材1つが
1,500人(将来4,500人)に届く。

`docs/MATERIAL_EXAMPLE.md` に実物のドリルを残してある。
**AI に生成させるときの手本はこれである。** 形だけでなく、
「reply to の to を落とすな」のような指導ポイントの粒度まで含めて写す。

## 5.14 会社名義への引っ越し(2026-08 方針)

いまは開発者個人の名義で、Supabase・GitHub・Claude API・Azure を使っている。
**会社として進める判断が出た段階で、会社名義へ移す。**

### 5.14.1 いつ移すか

| 時期 | 個人名義でよいか |
|---|---|
| 開発中(トレーナー1人・テスト生徒数名) | ✅ 問題ない |
| 試験運用(生徒 数名〜十数名) | ✅ まだよい |
| **本格運用(トレーナー50人・生徒1,500人)** | ❌ **会社名義にする** |

**技術の問題ではなく事業の問題である。**
退職・事故・相続などの際に、会社が自社の生徒データにアクセスできなくなる。
生徒の個人情報を預かる以上、名義は会社であるべき。

### 5.14.2 引っ越しの手間

| 何を | 手間 | やり方 |
|---|---|---|
| Claude API の鍵 | **1分** | 会社で鍵を作り、Supabase の Secrets を差し替える |
| Azure Speech の鍵 | **1分** | 同上 |
| GitHub | 数分 | リポジトリの Transfer で所有者を移す。履歴もそのまま |
| **Supabase の構造** | **10分** | 会社側に新プロジェクトを作り、`0001`〜`0007` を順に流す |
| Supabase のデータ | 半日 | バックアップからの復元、または移送作業 |
| Claude Code の契約 | 0分 | 誰の契約でも同じリポジトリで作業できる |

**いちばん大きい「データベースの構造」が10分で済むのは、
すべてが移行SQLとしてリポジトリにあるからである。**
`npm run test:db` で正しく作られたかも機械的に確認できる。

> **この節は、これまでの作法の効果が出る場所である。**
> 場当たりに Supabase の画面で直接テーブルを作っていたら、
> 引っ越しは「思い出しながら手で作り直す」になっていた。
> 構造はSQLに、判断は仕様書に、塞いだ穴はテストに——を続けること。

### 5.14.3 いま決めておくとよいこと

| 項目 | 内容 |
|---|---|
| **独自ドメイン** | GitHub Pages の URL は所有者名を含む。 独自ドメインにしておけば、引っ越してもURLが変わらない。 生徒に配ったURLが使えなくなる事態を避けられる |
| 個人名義のうちに溜めすぎない | 本格運用は会社名義になってから始める |

`要確認`: 独自ドメインを取るかどうか、取るならいつか。

### 5.14.4 Claude API のアカウント種別

Console の最初の選択は **「個人」** とした(2026-08)。

- 「組織」はチームメンバーを招待して請求を一元管理するためのもの。
  いま招待する相手がいない
- **鍵は Supabase の Secrets に1つ置いてあるだけ**なので、
  会社のアカウントに切り替えるのは文字列の差し替えで済む

`要確認`: Console の Limits で月の上限額を決めておく。
使いすぎを金額で止められる。

### RLS ポリシーの方針(教材まわり)

| テーブル | 生徒 | トレーナー |
|---|---|---|
| `materials` / `material_items` / `material_audio` | 自分に配信されたもののみ SELECT | 自分が作ったものを全操作 |
| `assignments` | 自分の行を SELECT、`learner_done_at` のみ UPDATE | 担当生徒の行を全操作 |
| `attempts` | 自分の行を全操作 | 担当生徒の行を SELECT のみ |
| `lesson_feedback` | 自分の行を SELECT のみ | 担当生徒の行を全操作 |
| `weakness_tags` | SELECT のみ | 全操作 |

**生徒が `materials` に INSERT できないことを DB 層で担保する。**
画面に作成ボタンを出さないだけでは不十分である。

### RLS ポリシーの方針(学習記録まわり)
- 生徒: 自分の `user_id` の行のみ SELECT / INSERT / UPDATE / DELETE 可能
- トレーナー: `learner_admins` で紐付いた生徒の行のみ SELECT 可能(書き込みは不可)
