## 1. プロジェクト概要

### 1.1 目的

英語学習者が日々の学習を記録し、AI による発音・表現のフィードバックを受けながら
継続的に学習できるシステム。あわせて、指導者(講師・保護者)が学習状況を
俯瞰できる管理画面を提供する。

### 1.2 想定ユーザー

| ロール | 想定する人物 | 主な利用シーン |
|---|---|---|
| 学習者 (learner) | 英語を学習する本人 | 日々の学習記録、音読・発音練習、復習 |
| 管理者 (admin) | 講師・保護者・スクール運営者 | 学習状況の確認、進捗の把握、フィードバック |

### 1.3 プロトタイプの構成

このリポジトリに、動作する試作版が入っています(React + Vite)。

- `src/components/EnglishStudyLog.jsx` — 学習者向け画面。学習記録の入力、発音練習、履歴、グラフ。
- `src/components/AdminDashboard.jsx` — 管理者向け画面。学習者一覧、集計・可視化、学習者別の内訳。

データはブラウザの localStorage に保存しており、サーバーは使っていません。
**認証・複数端末での共有・実際の発音評価は未実装です。**

動かし方は [`../README.md`](../README.md) を、
ファイルの役割は [`GETTING_STARTED.md`](GETTING_STARTED.md) を参照してください。

## 3. 技術構成(決定事項)

### 3.1 バックエンド: Supabase を採用

**採用理由**

- 認証・DB・ストレージ・ホスティングが 1 つのサービスで揃い、個人開発の運用負荷が小さい
- PostgreSQL なので、学習ログの集計・分析クエリを SQL でそのまま書ける
- Row Level Security (RLS) により「学習者は自分のデータのみ、管理者は担当学習者のデータのみ」
  というアクセス制御を DB 層で担保できる
- 無料枠が実用的で、プロトタイプから本番まで同じ構成で進められる

**利用するサービス**

| 機能 | Supabase の該当機能 |
|---|---|
| ユーザー認証 | Supabase Auth(メール + パスワード想定、`要確認`: マジックリンク/OAuth の要否) |
| 学習ログの保存 | Postgres Database |
| アクセス制御 | Row Level Security |
| 集計 | Postgres View / RPC (SQL 関数) |

### 3.2 音声データは端末内に保存する(サーバーに上げない)

**決定内容**: 録音した音声ファイルは Supabase Storage 等にアップロードせず、
利用者の端末内(ブラウザの IndexedDB / ネイティブアプリならローカルストレージ)に保存する。

**理由**

- 音声は生体情報に近い機微なデータであり、学習者に未成年が含まれる可能性を考えると
  サーバー保管はプライバシー上のリスクとコンプライアンス負担が大きい
- ストレージ課金と転送量課金を抑えられる
- 発音スコアの算出はクライアント側または API へのその場送信で完結し、
  音声そのものを保持し続ける必要がない

> **補足(第 5.1 節を参照):** 「サーバーに保存しない」ことと
> 「外部に送信しない」ことは別である。発音採点をブラウザの音声認識で行う場合も、
> 音声はブラウザメーカーのサーバーに送信される。この方針が担保するのは
> **保存しないこと**であり、送信しないことではない。

**サーバーに保存するのはスコアとメタデータのみ**

保存する: 発音スコア、練習した文章、練習日時、練習回数
保存しない: 音声ファイル本体、音声の波形データ

**この決定に伴う制約**

- 端末を変えると過去の録音は聞き返せない(スコアの履歴は残る)
- ブラウザのストレージ上限に達した場合は古い録音から削除する必要がある
  → `要確認`: 端末内に何日分保持するか(既定案: 直近 30 日 or 100 件)

### 3.3 フロントエンド

- React + Vite

**利用環境(確定)**

| 端末 | 用途 | 制約 |
|---|---|---|
| 会社PC | 閲覧・動作確認 | **アプリのインストール不可**。ブラウザで開くことしかできない |
| Mac(自宅) | 開発・閲覧 | 制約なし |
| iPhone(移動中) | 閲覧・発音練習 | 画面が狭い。Safari の挙動に合わせる必要あり |

この3環境を行き来するため、次の方針を採る。

- **ウェブアプリとして作り、URL を開くだけで使える形にする**
  会社PCにインストールできない以上、これ以外の選択肢がない
- **iPhone の「ホーム画面に追加」に対応させる**
  ネイティブアプリを作らずに、アプリに近い使い勝手を得る
- **画面は狭い幅を前提に設計する**(実装済み)
- ネイティブアプリ化(React Native)は当面見送る

## 4. 費用感

個人〜小規模スクール(学習者 数十名程度)を想定した試算。

| 項目 | 想定コスト | 備考 |
|---|---|---|
| Supabase Free プラン | $0 / 月 | DB 500MB、認証ユーザー数の無料枠あり。プロトタイプ〜小規模はこれで足りる想定 |
| Supabase Pro プラン | $25 / 月 | 無料枠を超えた場合。DB 8GB、日次バックアップ、無操作でも一時停止しない |
| ホスティング (Vercel 等) | $0 / 月 | 個人利用なら無料枠内 |
| TTS (Web Speech API) | $0 | ブラウザ内蔵のため課金なし |
| 発音評価 API | `要見積り` | 採用するサービス次第。第 5 章の判断待ち |

**音声データを端末内保存にしたことで、ストレージ課金と転送量課金がほぼゼロになる**のが
この構成の費用面での大きな利点。

`要確認`: 発音評価に外部 API を使う場合、1 回あたりの単価 × 想定練習回数 で
月額が変動する。学習者 1 人あたり 1 日 10 回練習 × 30 日 × 人数 で試算すること。

## 5. プロトタイプで実現できていない部分(重要)

Claude Code で実装を進める際、**ここが最も判断を要する箇所**です。
プロトタイプの見た目だけを見て「動いている」と誤解しないよう明記します。

### 5.1 発音スコアは現在シミュレーション

`EnglishStudyLog.jsx` に表示される発音スコアは、
**実際の音声を解析した結果ではなく、ランダム値または固定ロジックで生成した見せかけの数値**です。

- UI とデータフローを確認するためのダミー実装
- 「録音 → スコア表示」という体験の流れを検証する目的で入れたもの
- **本実装では、実際の音声認識・発音評価に置き換える必要がある**

**検討すべき選択肢**

3案の詳細な比較、費用の概算、推奨案は
[`PRONUNCIATION_OPTIONS.md`](PRONUNCIATION_OPTIONS.md) にまとめた。要約は以下。

| | 案1 ブラウザの音声認識 | 案2 発音評価サービス | 案3 端末内で解析 |
|---|---|---|---|
| 費用 | 無料 | 月3,000円程度(30人規模) | 無料 |
| 音素単位の評価 | ✕ | ◎ | △(精度不明) |
| 実装の手間 | 小(1〜2日) | 中(3〜5日) | 大(2週間〜) |
| iPhone での動作 | **不安定との報告あり。要実機確認** | 問題なし | 重い |

**推奨: 案1で始め、物足りなければ案2に移る。** 案3は現時点では選ばない。

`要確認`: **どの方針を採るかが未決定。** ここを決めないと発音機能の本実装に進めない。
案1を採る場合、その前に **iPhone の Safari で音声認識が動くかの実機確認**が必要。

> ### ⚠️ 3.2 の前提に対する訂正
>
> 当初「案1なら音声が端末外に出ない」と想定していたが、これは**誤り**である。
> ブラウザの音声認識は音声をブラウザメーカーのサーバー(Chrome なら Google、
> Safari なら Apple)に送信して処理する。
>
> したがって **「音声を外部に送信しない」が成立するのは案3のみ**。
> 一方 **「音声をサーバーに保存しない」という方針は3案とも維持できる**
> (採点結果とメタデータのみを保存すればよいため)。
>
> どの案を選んでも、利用規約・プライバシーポリシーに
> 「発音採点のために音声を外部サービスへ送信すること」の記載が必要。

### 5.2 TTS のアクセント・自然さの限界

お手本音声にブラウザ内蔵の Web Speech API を使っているため、以下の制約があります。

- **利用できる音声(声質・アクセント)が OS とブラウザに依存する**
  同じコードでも Windows / macOS / iOS / Android で読み上げの声が変わる
- **アメリカ英語・イギリス英語などのアクセントを確実に指定できない**
  端末にその音声がインストールされていなければフォールバックされる
- 抑揚・リズムが機械的で、シャドーイングのお手本としては物足りない場面がある
- 音声の読み込みタイミングにブラウザ差があり、
  `speechSynthesis.getVoices()` が初回は空配列を返す端末がある(実装時の既知の落とし穴)

**対応の選択肢**

1. Web Speech API のまま、利用可能な音声一覧から英語音声を選ばせる UI を用意する(無料)
2. 外部 TTS API で音声を生成し、生成済み音声をキャッシュして配信する(高品質・要課金)
3. 教材ごとにネイティブ音声を事前収録しておく(最高品質・制作コスト大)

`要確認`: お手本音声の品質をどこまで求めるか。
学習用途では「アクセントが端末ごとに変わる」ことが学習の妨げになり得るため、
本番では 2 か 3 への移行を想定しておくのが無難。

### 5.3 その他の未実装

- 認証がない(誰でも全データを見られる状態)
- 学習者と管理者のロール分離がない
- **端末をまたいだデータの共有ができない**(最も影響が大きい制約)
  データはブラウザごとに保存されるため、会社PC・Mac・iPhone がそれぞれ
  別の記録を持つ。3環境を行き来する使い方とは相容れないため、
  Supabase の接続が実質的な最優先課題となる
- エラーハンドリング・ローディング状態の表示がほぼない
- ~~レスポンシブ対応が不十分~~ → 対応済み(iPhone の画面幅で確認済み)

## 6. データモデル案

Supabase (PostgreSQL) 上のテーブル構成の初期案。実装時に見直す前提。

### `profiles`
| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK, auth.users 参照) | ユーザー ID |
| display_name | text | 表示名 |
| role | text | `learner` / `admin` |
| created_at | timestamptz | 作成日時 |

### `study_logs`
| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | ログ ID |
| user_id | uuid (FK → profiles.id) | 学習者 |
| studied_on | date | 学習日 |
| minutes | integer | 学習時間(分) |
| category | text | 音読 / 単語 / 文法 / リスニング / 会話 |
| material | text | 教材名 |
| note | text | メモ |
| created_at | timestamptz | 作成日時 |

### `pronunciation_attempts`
音声本体は保存しない。スコアとメタデータのみ。

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | 試行 ID |
| user_id | uuid (FK → profiles.id) | 学習者 |
| target_text | text | 練習した英文 |
| score | numeric | 発音スコア(0–100) |
| recognized_text | text | 音声認識結果(取得できた場合) |
| engine | text | 評価に使ったエンジン名。シミュレーション時は `mock` |
| attempted_at | timestamptz | 練習日時 |

> `engine` カラムを持たせることで、
> 「シミュレーションで記録されたスコア」と「実エンジンのスコア」を後から区別できる。
> これはシミュレーション期間のデータが本番の統計を汚さないための措置。

### `learner_admins`(管理者と学習者の紐付け)
| カラム | 型 | 説明 |
|---|---|---|
| admin_id | uuid (FK → profiles.id) | 管理者 |
| learner_id | uuid (FK → profiles.id) | 学習者 |

`要確認`: 1 人の学習者に複数の管理者が付く運用があるか(上記は多対多で設計)。

### RLS ポリシーの方針
- 学習者: 自分の `user_id` の行のみ SELECT / INSERT / UPDATE / DELETE 可能
- 管理者: `learner_admins` で紐付いた学習者の行のみ SELECT 可能(書き込みは不可)
