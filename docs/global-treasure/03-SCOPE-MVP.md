# 03. MVP スコープ — 入れるものと後回しにするもの

> **前提**: [機能台帳](00-VISION-AND-FEATURE-LEDGER.md) の行は消さない。
> ここで決めるのは「いつ作るか」だけであって、「作らない」ではない。

---

## 1. MVP の定義

MVP で証明したい仮説は 1 つだけである。

> **日本の中古店で商品を撮った日本人が、海外に売って、実際に利益を得られるか。**

この 1 本の線が通らない機能は、どれだけ魅力的でも MVP に入れない。
逆に、この線の途中で**ユーザーが詰まって止まる**ものは、地味でも必ず入れる
（型番の手入力、送料が取れなかったときの表示、EXPORT CHECK など）。

### MVP の範囲を 1 文で

**カメラ・レンズ 1 カテゴリ**について、**国内と eBay（米・英・独）**の相場を比較し、
3 価格戦略と実質利益を出し、**英語の SELL PACK** と**送料比較**と**梱包手順**まで導き、
**購入者との簡単なやり取り**を日本語で処理できる。

### なぜこれらが「削れない」か

| 一見削れそうな機能 | 削れない理由 |
|---|---|
| EXPORT CHECK (F40) | 電池入りカメラを送れないと知らずに出品させると、**ユーザーが規約違反者になる**。信用を最初に失う |
| FACT-LOCK (F27) | 1 件でも虚偽記載の出品が出たら、プロダクトの前提が崩れる |
| PROOF VAULT (F46) | 越境取引の紛争は必ず起きる。証拠がないと初期ユーザーが焼ける |
| Confidence (F53) | データが薄い初期こそ必要。**薄いデータで断定するのが最大のリスク** |
| 型番手入力 (S-04) | 画像認識は必ず外す。逃げ道がないとユーザーが止まる |

## 5. MVP に**入れない**と明示すること（誤解防止）

初期ユーザーに誤解させないため、アプリ内で明示する。

- 全 Marketplace への自動出品は**しない**（国内は SELL PACK のコピー方式）
- 集荷依頼はアプリから**できない**（公式手続きへ案内する）
- 価格は**予測であって保証ではない**
- 関税・輸入税の**最終的な負担額は保証しない**（Landed Cost は V1、それでも参考値）
- 法規制の最終判断は**ユーザーと公式情報**に委ねる（アプリは確認を支援する）

## 6. 段階リリース計画

| 段階 | 内容 | 完了の判断 |
|---|---|---|
| **α（内部）** | 開発者本人が**自分の持ち物**をカメラ 1 カテゴリで 20 件スキャン、3 件を実際に eBay で売り切る | 予測と実売の差が説明可能な範囲に収まる |
| **α2（HUNT 検証）** | **古物商許可の取得後**、店頭で仕入れて転売する | MAX BUY PRICE に従って仕入れ、実際に利益が出る |
| **β（クローズド 10〜30 名）** | 招待制。せどり経験者を含める | 1 人あたり月 1 件以上の海外売却が成立する |
| **一般公開** | 課金設計を入れて公開 | 継続率と原価が事業として成立する |

**α の前に一般公開しない。** 価格を扱うアプリで最初に外すと、信用は戻らない。

### なぜ α を「自分の持ち物」から始めるのか

開発者本人は個人事業主で、**古物商許可がまだない**（[11](11-SETUP-CHECKLIST.md)）。
仕入れを伴う検証は許可の取得を待つ必要があるが、
**自分の持ち物を売る検証は待たなくてよい**（`要確認`: 管轄警察署に確認すること）。

越境販売の一本道 —— 撮影 → 状態確認 → 価格戦略 → 英語出品 → 送料比較 → 梱包 → 発送 → 手取り確定
—— は、売る商品が自分の持ち物でも仕入れ品でもまったく同じである。
**したがって MVP の機能は 1 つも削らない。検証に使う商品を変えるだけでよい。**

HUNT モード（GT-F06）は MVP に含めて実装するが、
**初回起動時に古物商許可についての告知を必ず表示する**（[09](09-LEGAL-CHECKLIST.md) L-0）。
