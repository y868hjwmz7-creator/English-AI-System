## この設計の背骨（3つだけ覚えるなら）

### 1. VALUE ENGINE が中心。UI はその表示層にすぎない

NEW BUY / MY STUFF / HUNT は**別機能ではなく、同じ VALUE ENGINE の使い方違い**です。
エンジンはネットワークにも DB にも触らない純粋な計算モジュールとして独立させ、
入力（商品／状態／市場データ／手数料／送料／為替）を注入して結果を得ます。
→ 詳細は [07-VALUE-ENGINE.md](07-VALUE-ENGINE.md)

### 2. AI は「解釈と文章化」だけを担当する。数字と法律は担当しない

価格・送料・税・Marketplace ルールを LLM の記憶から生成することを、
アーキテクチャのレベルで**不可能にします**（AI に数値生成の出力経路を与えない）。
出品文は **FACT LEDGER（確認済み事実の台帳）に紐づく主張しか書けない**仕組みにし、
生成後に検証器が事実 ID の裏付けがない文を機械的に弾きます。
→ 詳細は [05-AI-PIPELINE.md](05-AI-PIPELINE.md)

### 3. データは「取ってよいものだけ」を積み上げる

無断スクレイピングを前提にしません。公式 API・許諾済みデータ・ユーザー自身の実績、
そして同意を得た匿名集計だけで市場データを育てます。
この制約は不便ですが、**長期的にはこれ自体が競争優位**になります。
→ 詳細は [06-INTEGRATIONS.md](06-INTEGRATIONS.md) と [09-LEGAL-CHECKLIST.md](09-LEGAL-CHECKLIST.md)

## いま判断が必要なこと（`要確認` の最重要 5 件）

| # | 論点 | 設計側の推奨 | なぜ判断が必要か |
|---|---|---|---|
| D-1 | リポジトリ | **新規リポジトリに分離**（本リポジトリは英語学習アプリ） | 別プロダクト。CI・依存・権限が混ざる |
| D-2 | クライアント形態 | **Expo (React Native) のモバイルアプリ** | 店頭でカメラを使う体験が中核。Web だけでは成立しない |
| D-3 | 最初の海外市場 | **eBay 1 本から**（米国・英国・独が同一 API 圏） | 複数同時は API 審査・出品ルール対応で確実に遅延する |
| D-4 | 国内出品の扱い | **SELL PACK（コピー用）まで**。自動出品はしない | 公式出品 API の利用可否が未確認（[09](09-LEGAL-CHECKLIST.md)） |
| D-5 | 事業主体 | 未定 | 古物商許可・特商法表記・API 審査すべてに事業者情報が必要 |

D-5 は**最優先**です。HUNT モード（せどり）は日本では古物営業法の対象になり得るため、
アプリの立ち上げ順序そのものに影響します。→ [09-LEGAL-CHECKLIST.md](09-LEGAL-CHECKLIST.md) 第 1 節

## 記法

- `要確認` … 一次情報の確認、または事業判断が必要な箇所。設計側で断定しない。
- 機能 ID `GT-Fxx` … [機能台帳](00-VISION-AND-FEATURE-LEDGER.md)の通し番号。全ドキュメントで共通。
- 見積の `pt` … 相対規模。1pt ≒ 慣れた開発者 1 人日の作業量を目安とする。
