# Supabase を始める手順

データを端末の中ではなくサーバーに置き、会社PC・Mac・iPhone のどこから開いても
同じ記録が見えるようにするための準備です。

**このページの作業は、あなたにしかできません。**
アカウントの作成とパスワードの管理が必要なためです。
作業自体はブラウザだけで完結し、パソコンに何かをインストールする必要はありません。
所要時間は10〜15分ほどです。

---

## Supabase とは何か

かんたんに言うと、**「データの保管庫」と「ログイン機能」をまとめて借りられるサービス**です。

自分でサーバーを用意して、データベースを設定して、ログインの仕組みを作って……
という作業を全部肩代わりしてくれます。ブラウザの管理画面から操作できます。

---

## 手順

### 1. アカウントを作る

1. ブラウザで `https://supabase.com` を開く
2. 右上の **Start your project**(または **Sign in**)を押す
3. サインイン方法を選ぶ
   - **GitHub でサインイン** — おすすめ。すでにお持ちのGitHubアカウントが使えます
   - メールアドレスでの登録も可能です

> クレジットカードの登録は、無料プランで使う限り不要です。

### 2. 組織(Organization)を作る

初回は組織名を聞かれます。個人利用なら自分の名前やプロジェクト名で構いません。

- **Name**: 任意(例: `english-ai`)
- **Type**: Personal
- **Plan**: **Free** を選ぶ

### 3. プロジェクトを作る

**New project** を押して、次を入力します。

| 項目 | 入れる値 | 補足 |
|---|---|---|
| **Name** | `english-ai-system` | 何でも構いません |
| **Database Password** | 強いパスワードを自動生成させる | ⚠️ 下記の注意を必ず読んでください |
| **Region** | **Northeast Asia (Tokyo)** | 日本から使うので東京を選ぶと速くなります |
| **Plan** | Free | |

> ### ⚠️ Database Password について
>
> この画面で表示されるパスワードは、**この時だけしか表示されません。**
> 必ずパスワード管理アプリ(Mac / iPhone の「パスワード」アプリなど)に保存してください。
>
> なくしても再発行はできますが、面倒な手順が必要になります。
> なお、このパスワードはアプリの動作には使いません。データベースに直接つなぐときだけ使うものです。

プロジェクトの準備には1〜2分かかります。

### 4. 接続情報を確認する

プロジェクトができたら、次の2つの値を確認します。
**この2つは別々の画面にあります。**

#### ① Project URL

左メニューの **⚙️ Settings** → **General** を開くと
**Project ID** が書いてあります。URL はそこから決まります。

```
Project ID が  tsfoecjabgcdmvxdcpgy  なら
Project URL は https://tsfoecjabgcdmvxdcpgy.supabase.co
```

つまり **`https://` + Project ID + `.supabase.co`** です。
`Project URL` という名前の欄が見当たらなくても、これで分かります。

#### ② 公開用の鍵

左メニューの **⚙️ Settings** → **API Keys** を開きます。
(General のすぐ下にあります。**JWT Keys とは別**です)

Supabase は鍵の呼び方を新しくしたため、
**プロジェクトを作った時期によって見た目が違います。** どちらでも構いません。

| 世代 | 名前 | 見た目 |
|---|---|---|
| 新しい | **Publishable key** | `sb_publishable_...` |
| 従来 | **anon public** | `eyJ...` で始まる長い文字列 |

どちらも「アプリに埋め込んでよい、公開前提の鍵」です。
**画面に出ているほうを控えてください。**

> `anon public` が見つからない場合は、API Keys の画面に
> **Legacy API keys** のような切り替えがないか探してください。
> なければ新方式なので、`sb_publishable_...` のほうを使います。

#### 控える2つ

| 項目 | 見た目 | 用途 |
|---|---|---|
| **Project URL** | `https://xxxxxxxx.supabase.co` | どのプロジェクトにつなぐか |
| **公開用の鍵** | `sb_publishable_...` または `eyJ...` | アプリからつなぐための鍵 |

この2つを、次のように Claude Code に渡してください(このチャットに貼っていただいて構いません)。

```
VITE_SUPABASE_URL=https://xxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
```

---

## 🔑 鍵の扱いについて — ここだけは間違えないでください

Supabase の管理画面には、似た名前の鍵が複数あります。**扱いが全く違います。**

| 鍵の名前 | 性質 | 扱い |
|---|---|---|
| **anon public** / **Publishable key**(`sb_publishable_...`) | 公開されることを前提に作られた鍵 | ✅ アプリに埋め込んでよい。人に見えても問題なし |
| **service_role** / **Secret key**(`sb_secret_...`) | **すべての制限を無視できる管理者の鍵** | ❌ **アプリに絶対に埋め込まない。人に見せない** |
| **JWT Keys** の画面にあるもの | 鍵に署名するための土台 | ❌ 触らない。今回の作業では使わない |

**見分け方はこれだけ覚えてください。**
名前に **`publishable`** か **`anon`** が入っていれば貼ってよい鍵。
**`secret`** か **`service_role`** が入っていれば絶対に貼ってはいけない鍵。

`anon` キーがアプリに埋め込まれていても安全なのは、
**RLS(Row Level Security)という仕組みで「誰がどのデータを読めるか」を
データベース側で制限している**からです。この設定は実装時に必ず行います。

一方 `service_role` キーはその制限をすべて飛び越えられるため、
これが外に出ると**全ユーザーのデータを誰でも読み書きできる状態**になります。

> **もし誤って `service_role` キーを人に見せてしまったら**
> Project Settings → API から鍵を作り直せます(Reset)。すぐに再発行してください。

念のため、このチャットに貼っていただくのは
**`anon public`(または `Publishable key`)だけ**にしてください。
`service_role` / `Secret key` は、こちらから求めることはありません。

## 費用について

2026年8月時点の内容です。最新は Supabase の Pricing ページでご確認ください。

| | Free | Pro |
|---|---|---|
| 月額 | **$0** | **$25**(約3,700円) |
| データベース容量 | 500 MB | 8 GB |
| 月間アクティブユーザー | 50,000人 | 100,000人 |
| ファイル保存 | 1 GB | 100 GB |
| 同時に持てるプロジェクト | 2つまで | 制限なし |

**このアプリの規模なら、当面 Free で足ります。**
学習記録は1件あたり数百バイト程度なので、
学習者30人が毎日記録しても500MBに達するのは相当先です。

### Free プランで1つだけ注意すること

**1週間まったくアクセスがないと、プロジェクトが自動的に一時停止します。**

止まっても管理画面から復帰できますし、データが消えるわけではありませんが、
「久しぶりに開いたら動かない」ということが起こり得ます。
実際に使い始めれば毎日アクセスがあるので、問題になるのは開発が止まった期間だけです。

これが煩わしくなったら Pro($25/月)に上げると、一時停止しなくなります。

## この作業が終わったら

Claude Code に「Supabaseのアカウントを作りました」と伝えて、
上の2つの値(URL と anon キー)を渡してください。そのあとの作業は次のとおりです。

1. データを入れる表(テーブル)を作る
2. 「誰がどのデータを読めるか」の制限(RLS)を設定する
3. `src/lib/store.js` を、保存先が Supabase になるよう書き換える
4. ログイン画面を追加する

1〜4はこちらで進められます。あなたの作業は、このページの手順だけです。

## 5. データベースを作る(SQL を1回実行する)

接続情報がそろったら、テーブルとアクセス制御を作ります。

1. Supabase の管理画面 → 左メニュー **SQL Editor** → **New query**
2. リポジトリの [`../supabase/migrations/0001_init.sql`](../supabase/migrations/0001_init.sql)
   の中身を**すべて**コピーして貼り付ける
3. **Run** を押す
4. **「Potential issue detected」という警告が出ます。`Run query` を押して進めてください**(下記参照)
5. **Success. No rows returned** と出れば成功

### 「Potential issue detected」の警告について

Supabase は、SQL に「作る」以外の操作が1つでも含まれていると
**内容にかかわらず一律にこの警告を出します。** 出るのが正常です。

このファイルに含まれる「作る」以外の操作は、次の3つだけです。

| 文 | 何をするか |
|---|---|
| `drop policy` | **このファイルが作る12テーブルのポリシーだけ**を消す。前回の設定を上書きするため |
| `drop trigger` | **このファイルが作るトリガー1つだけ**を消す。同上 |
| `revoke` | `assignments` の更新権限を絞る。生徒が「やった」以外の欄を書き換えられないようにする |

**利用者のデータを消す文(`delete` / `drop table` / `truncate`)は1つも含まれていません。**
不安であれば、貼り付けたあとに `Ctrl + F`(Mac は `⌘ + F`)で
`delete` や `drop table` を検索して、0件であることを確かめてください。

> `drop policy` は**このファイルが管理する12テーブルに限って**います。
> 同じデータベースに別の用途のテーブルがあっても、そちらには触れません。

失敗しても何度でも貼り直して実行できます
(すべて「無ければ作る」書き方にしてあります)。

### この SQL が作るもの

| 種類 | テーブル |
|---|---|
| 人 | `profiles` / `learner_admins` |
| 弱点タグ | `weakness_tags`(38件を自動で投入) |
| 教材 | `materials` / `material_items` / `material_tags` / `material_audio` |
| 宿題 | `assignments` |
| 記録 | `study_logs` / `attempts` |
| フィードバック | `lesson_feedback` / `lesson_feedback_tags` |
| 音声の置き場 | Storage バケット `material-audio` |

あわせて、**すべてのテーブルに RLS(誰がどの行を読めるか)を設定します。**
ここが安全性の本体です。**RLS を無効にしないでください。**
無効にすると、アプリの鍵を持つ誰もが全データを読めるようになります。

### 6. 自分を「トレーナー」にする(必須)

SQL を実行しただけでは、まだ誰も教材を作れません。

1. アプリを開いてサインアップし、自分のアカウントを作る
2. SQL Editor で次を実行する(メールアドレスは自分のものに置き換える)

```sql
update public.profiles set role = 'admin'
where id = (select id from auth.users where email = 'あなたのメールアドレス');
```

> **役割(role)の変更は、アプリからは一切できません。** SQL Editor だけです。
> これは意図的な制限です。アプリから変更できると、
> **生徒が自分をトレーナーに書き換えて、全生徒のデータを見られるようになります。**
> 実際、最初に書いた SQL にはこの穴があり、検証で見つかったため塞ぎました。

生徒のアカウントを作ったら、担当関係も登録します。

```sql
insert into public.learner_admins (admin_id, learner_id)
values ('トレーナーのUUID', '生徒のUUID');
```

UUID は SQL Editor で `select id, email from auth.users;` を実行すると分かります。

## 7. 公開版(GitHub Pages)にも接続情報を渡す

`.env` は Git に入らないので、公開版のビルドには別に渡す必要があります。

1. GitHub のリポジトリ → **Settings** → 左メニュー **Secrets and variables** → **Actions**
2. **New repository secret** を2回押して、次の2つを登録する

| Name | Secret |
|---|---|
| `VITE_SUPABASE_URL` | `https://<Project ID>.supabase.co` |
| `VITE_SUPABASE_ANON_KEY` | `sb_publishable_...`(または `eyJ...`) |

登録すると、次回の公開から自動で使われます。
**登録しなくてもビルドは失敗しません**(その場合はこれまでどおり端末内のデータで動きます)。

> `anon` / `publishable` キーはブラウザに配られる以上そもそも隠せませんが、
> 鍵の置き場所を1か所にそろえておくと、あとで Azure の鍵など
> **本当に秘密の鍵**を扱うときに間違えません。

## 8. つながったか確かめる

アプリを開くと、画面の上に接続状態が出ます。

| 表示 | 意味 | 次にすること |
|---|---|---|
| **Supabase に接続できています** | 完了 | — |
| **Supabase はまだ設定されていません** | URL か鍵が無い | 第4節・第7節 |
| **あと一歩 — テーブルがまだありません** | 接続はできている | 第5節の SQL を実行する |
| **Supabase に届きませんでした** | 通信できていない | URL の綴りを確認する |
| **Supabase がエラーを返しました** | 鍵が違う可能性 | 鍵を貼り直す |

この帯は、つなぎ込みが終わったら外します。

## 9. SQL を書き換えたときは、貼る前に手元で試す

`supabase/migrations/` の SQL を直したら、Supabase に貼る前に確かめられます。

```
npm run test:db
```

手元の PostgreSQL にまっさらなデータベースを作り、Supabase 環境の最小の再現を入れ、
移行 SQL を **2回** 実行します(何度実行してもよいことの確認)。
そのうえで、アクセス制御が意図どおりかを25項目で検証します。

| 確かめていること | 例 |
|---|---|
| 生徒に見えるもの | 配信された教材だけ。他人の教材・記録は見えない |
| 生徒にできないこと | 教材を作る、宿題を配信する、**自分をトレーナーに昇格する** |
| 生徒にできること | 「やった」の記録だけ(提出期限やトレーナーの確認印は書き換えられない) |
| トレーナーに見えるもの | 担当している生徒の分だけ。担当外の生徒の記録は見えない |
| 未ログイン | 何も見えない |

**Supabase に貼る前に必ずこれを通してください。**
本番のデータベースで試すより、はるかに安全で速いです。
