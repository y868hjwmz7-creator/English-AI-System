### 集中モード — 1段落ずつ調べるときは、「送る必要」をなくす

`FocusReader.jsx`(2026-09 利用者の指定)。
**画面に出す名前は「集中モード」**(利用者が選んだ)。
コードの中の名前(`FocusReader` / `.focus-*`)は変えていない。
**単位(段落 / 発言)は名前に入れない。** 名前は1つにしておき、
いま何番目かは中の「3 / 6 段落」が言う。

> 段落ごとに画面を固定し、ブラウザの機能をシャットアウトできるように
> したいです。そのモードの時は段落を進める、戻るのボタンを配置して、
> ドラッグなどをしてもブラウザの影響を受けないように。

**「送らせない」のではなく「送る必要をなくす」。**
語のタップと画面送りが喧嘩していたのは、**画面が送れる状態だったから**である。
iOS はいったん送り始めると `touchmove` を取り消せない。
**時間や判定で戦うかぎり、この穴は塞げない**(3度踏んでいる)。
**1段落だけを画面ぴったりに出せば、送るものが無くなる。**

| 邪魔なもの | 止まるか | どうやって |
|---|---|---|
| ページ全体が動く | **止まる** | `100dvh` で画面ぴったり。送るものを無くす |
| 引っぱって更新 | **止まる** | `overscroll-behavior: contain` |
| アドレスバーの出入り | **止まる** | 送らなければ動かない |
| 二度叩いての拡大 | **止まる** | `touch-action: manipulation` |
| **指2本での拡大** | **止まらない** | iOS は `user-scalable=no` を**無視する** |
| **端からの戻るスワイプ** | **止まらない** | Safari の仕様。JS から触れない |

止まらない2つは**避ける**。押すものを端から離し、
**ホーム画面に追加**してもらえばアドレスバーごと消える(`manifest.json` +
`apple-mobile-web-app-capable`。**両方要る。片方では片方の端末で効かない**)。

#### 長い段落は、**入るまで割る**(`focusChunks.js`・2026-09 利用者の指定)

> 段落が長い場合、せっかく集中モードに入ってもそこでスクロールが
> 発生してしまっています。ちょうど良い単語数、内容で区切る仕様にしないと
> 通常モードと同じ操作感の悪さを引き継いでしまい、
> 集中モードの存在意義が問われてしまいます。

**この画面は「送るものを無くす」ことで成り立っている。**
ところが**貼った原稿は1段落が桁違いに長い**ので、その1段落だけで
画面に入らず、**中で送ることになっていた。** 送るものが在るなら、
この画面である意味がない。

##### **語数を決め打ちにしない。測って、入るまで増やす**

実測(Chromium)。**同じ 146 語の段落でも、入るかどうかは端末で違う。**

| 端末 | 本文の箱 | 1語あたり | 146 語は |
|---|---|---|---|
| iPhone 390×844 | 734px | 5.0px | **入らない**(825px 要る) |
| 320×568 | 458px | 6.4px | **入らない**(1,025px 要る) |
| パッド 820×1180 | 1,070px | 2.9px | 入る |

しかも紙の文字は3段(16 / 19 / 23px)、幅は7段ある。
**「◯語で切る」と決めた瞬間に、どこかで外れる。**
320px に合わせて 30 語で切れば、ふつうの記事(1段落 55 語ほど)まで
真っ二つになる —— **切らなくてよいものまで切る。**

だから**幅で決めない。入るまで割る**(`useFitRow` と同じ考え方)。
描き終えたあと、目に映る前(`useLayoutEffect`)に
`scrollHeight > clientHeight` を見て、**1枚ずつ増やす。**

- **算段は `src/lib/focusChunks.js` 1か所。** 画面の中に書くと
  **素の node で一度も走らせられない**(`playMark.js` と同じ考え方)
- **切れ目は必ず文の切れ目**(`pastedParagraphs` / `speakChunks` と同じ)
- **1語も落とさない。** つなぐと元の英文に1文字も違わず戻る
- **`at`(元の英文の何文字目か)を必ず返し、色を付けるときに引く。**
  引かないと**段落の先頭に戻って光る**(`speakChunks` で踏んだ穴)
- **文の数より多くは割れない。** 割れないならそのまま出す
  (**行き止まりを作らない** —— 送ることにはなるが、消えはしない)
- **訳は、数が合ったときだけ割る。** 合わなければ段落の訳をそのまま
  添えて「段落の訳」の札を出す(`sentencePair.js` と同じ決まり)

##### **段落の番号は動かさない**

紙の丸番号と一致していることは、レッスンで「2番のところ」と言えるための
決まりである(このファイルの上の節)。だから

| 何 | 何を指すか |
|---|---|
| 本文の丸番号 | **段落の番号のまま**(紙と一致) |
| そのとなりの `2 / 3` | その段落の何枚目か。**割った段落にだけ出す** |
| 下の帯の「9 / 17 段落」 | **段落のまま。** どこまで来たかの目安 |

**◀ ▶ は1枚ずつ動く。** 割れている段落では、まず段落の中を進む
(そのあいだ下の帯の数字は動かないので、**となりの `2 / 3` が無いと
何も起きていないように見える**)。

- **◀ で戻ったら、その段落の最後の1枚に着く**(`cuts` に控えておく)。
  頭に着けると、割れている段落を戻り切れない
- **鳴っているかけらも、そのまま開く**(段落を追うのと同じ考え方)。
  追わないと、割った段落では**残りの2枚のあいだ何も光らない**
- **窓が変わったら 1 枚に戻して測り直す。** 広くなったのに割れたままでは
  割りすぎになる

##### 実測(割ったあと)

| 端末 | 1段落目(146語) | 送るか |
|---|---|---|
| iPhone 390×844 | **2枚**(78 + 68 語) | 送らない |
| 320×568 | **3枚**(56 + 44 + 46 語) | 送らない |
| パッド 820×1180 | 割らない(146 語) | 送らない |
| PC 1440×900 | 割らない | 送らない |
| ふつうの会話(10 語) | **割らない** | 送らない |

`npm run test:play` が算段を、**`npm run test:bar` が実際に描いて**
「どの枚も送らないか」「1語も落ちていないか」
「**ふつうの段落まで割っていないか**」を見張る
(実際に割るのをやめて、赤くなることを確かめてある)。

#### **ブラウザの帯は、ページの側からは消せない**(2026-09 実機・利用者の指定)

> 集中モードに入ったらデフォルトが下のブラウザのUIが無しの状態になるように
> 調整してください。今は逆です

**できない。** iOS Safari の上下の帯が細くなるのは、
**利用者自身が「ページそのもの」を送ったとき**だけである。

- **JavaScript からは消せない。** `window.scrollTo(0, 1)` は
  iOS 7 までの手で、いまは効かない
- **全画面(Fullscreen API)は iPhone の Safari に無い**(iPad にはある)
- **`user-scalable=no` と同じで、`minimal-ui` も無くなっている**

しかも**集中モードは「送るものを無くす」ことで成り立っている**
(語のタップと画面送りの喧嘩を、3度踏んで消した設計)。
ページが送れないのだから、**帯は細くなりようがない。**
帯を消すためにページを送れるようにするのは、**この画面を壊すこと**である。

**確実に消す道は1つだけ ——「ホーム画面に追加」**(`display: standalone`)。
そうすればアドレスバーも下の帯も**アプリ全体で**消える。
`manifest.json` と `apple-mobile-web-app-capable` は**両方とも入っている**ので、
こちら側の作業は無い。

- **`100vh` に戻して「はみ出させる」手を使わない。** 帯が細くなるまで
  下の帯が画面の外に出るが、`position: fixed` なので**送っても出てこない**
  (押せないボタンになる)。CLAUDE.md の「`100vh` を使わない」はこの話でもある
- **この環境から iPhone の Safari は確かめられない。**
  帯の出入りは Chromium には無い挙動なので、**実機でしか分からない**

- **`100vh` を使わない。** アドレスバーが隠れている前提の値なので、下が切れる
- **入り口は、レッスン表示の「練習の行」に置く**(`.practice-row`。
  6Steps・Quick Response と横に並べる)。

  はじめは `PassagePractice` の中にだけ置いていた。ところが
  **レッスン表示では `PassagePractice` は「6Steps」を押したときにしか
  描かれない**ので、集中モードは 6Steps の**中に埋もれていた。**
  ゲストの「今週の宿題」に至っては、`PassagePractice` は
  **印刷する一瞬しか描かれない。** だから利用者からは
  **「どこにも集中モードがありません」**に見えた(2026-09 実機)。

  語を調べるのは 6Steps に入る**前**の段階である。
  **入り口を、その中に置かない。**
  `PassagePractice` の側は `showFocus={false}` で出さない
  (**同じことをするボタンを、1つの画面に2つ見せない**)。
- **入口が3つになったら、狭い画面で1行に入るか実測する。**
  紙の上の `.practice-row` は `flex-wrap: nowrap` なので、
  **入らないぶんは横にはみ出し、紙が横に送れる状態になる**
  (下の「横方向のゆらゆら」)。
  600px 以下では**絵を落として**言葉だけにしてある
  (この3つは名前でしか見分けられないので、削るのは絵のほう)。
  実測 320px → 272px / 390px → 342px。どちらも1行 44px
- **鳴っている音は、入っても止めない**(2026-09 利用者の指定
  「再生中に集中モードに入ったとしても、再生中の音はそのまま続くように
  して下さい」)。以前は `openFocus()` で `stopAll()` を呼んでいたので、
  **入った瞬間に黙って**いた。聴きながら語を調べたいのだから、切る理由がない。
  止めたいときは、集中モードの Listen を押せば入れ替わる
- **入り口は、右下にも貼り付ける**(`.focus-float`・2026-09 利用者の指定)。

  > このボタンは「教材を作る」のように常に右下にも固定してください。

  ボタンの行は**紙と一緒に送られて消える。** 記事は6段落あるので、
  読んでいる途中で「この語を調べたい」と思ったときにはもう画面の外にいる。
  置き方は**さがす画面の `.finder-float` にそろえる。**
  ただし**通しの練習(6Steps / Quick Response)のあいだは出さない**
  (あちらも下にボタンがあり、重なる)。
- **狭い画面では、絵だけにして操作盤の左へ寄せる**(2026-09 実機・利用者の指摘
  「スマホではプレーヤーの下に『集中モード』のボタンがきてしまいますが、
  もう少し気の利いた場所にどけることはできませんか?」)。
  折り返させていたので、**操作盤(2段)の下にもう1段**積まれて3段になって
  いた。言葉を落として絵だけにし、`order: -1` で左へ寄せる。
  操作盤は残りの幅で自分の中を折り返すので、**全体は2段に収まる**
  (実測 390 / 320px とも 136 → 90px)。
  **同じ囲みの中にいるまま**なので、「別々に `fixed` で置かない」は保たれる。
  **読み上げのための名前(`aria-label`)を必ず添える**
- **出る場所も、同じ右下にそろえる**(`.focus-exit`・利用者の指定
  「すぐに元に戻れるボタンも作ってください」)。
  左上の「✕ 閉じる」は残してあるが、**スマホで親指がいちばん届かないのは左上**
  である。入った場所を押せば戻れる。
  **帯の上に浮かせる**(`bottom: 100%`)。帯そのものに置くと「次 ▶」と
  重なるか、320px で1行に収まらない(実測)
- **広い画面では、本文を横のまん中に寄せる**(利用者の指定
  「パソコンではもう少し文章を真ん中に寄せてください」)。
  上限が無かったので、1440px では 19px の行が画面いっぱいに伸び、
  **左に貼り付いて見えていた**(実測 左 16px / 右 778px)。
  `.focus-body > *` に `max-width: 34em` と左右 `auto` の余白
  (Quick Response の日本語と同じ読み幅)。
  **`max-width` なので狭い画面は何も変わらない**(実測 390px は前と同じ)。
  **文字そのものは左そろえのまま。** 寄せるのは「かたまり」である。
  なお `.focus-en, .focus-ja` に `margin: 0` と書くと**あとに来るこちらが勝って
  寄せが効かない。** 上下だけ 0 にする
- **いま紙のまん中に出ている発言から始める**(2026-09 利用者の指定)。

  > KENJI が大体画面の中心に来ている時は集中モードを押したら
  > ②KENJI の集中モードに入り、解除したら同じ場所に戻るようにしてください。
  > 集中モードに入る前のピッタリの場所です

  集中モードは「どこまで見たか」を覚えているが、**紙を読んでいる途中で
  押したときは、そちらのほうが強い。** 目はいまその発言の上にあるので、
  別のところから始まると探し直すことになる。

  - 選び方は**画面のまん中からの近さ**(`centeredFocusIndex`)。
    **まん中にかかっていれば距離 0** なので、画面をまたぐ長い発言でも当たる
  - 目印は **`data-focus`**(`<li>`)。**`data-key` では足りない。**
    あれは演習をまたいで一意なだけで、集中モードは
    **本文が空の項目を外した番号**で数えている
  - **控え(どこまで見たか)は書き換えない。** 覗いただけで動くと、
    次に開いたときに話が飛ぶ。◀ ▶ を1度でも押したら控えの側に戻す
  - **見えていないときは、これまでどおり覚えている場所から。**
    ほかのページを開いていると本文の `<li>` は高さ 0 なので、
    そのときは `null` を返す
- **終えたら、入る前とぴったり同じ場所へ戻す**(利用者の指定)。
  紙は `overflow-y: auto` の箱なので `scrollTop` を控えておくだけだが、
  練習中は `.lesson-sheet.is-running` で**並べ方が変わる**ため、
  そのままでは送りの量が落ちる。
  - 戻すのは **`useLayoutEffect`**(描き直しのあと・目に映る前)。
    `useEffect` だと、いったん頭に戻ったのが見えてしまう
  - 並べ方が落ち着くのが次の1コマ先のことがあるので、**そこでも念のため戻す**
  - **中で ◀ ▶ を押していても、戻るのは入る前の場所。**
    「入る前のピッタリの場所」という指定である
  - 実測(390px / 1440px): 送り 277 → 277・1071 → 1071・1812 → 1812。
    **6Steps と Quick Response には効かせていない**(言われた場所だけを直す)
- **くり返し(オートリピート)を Listen の横に置く**(2026-09 利用者の指定
  「これは集中モードで、全てのデバイスで同じにしてください」)。
  まねて言うには、同じ発言を何度も聴く。押し直していては口が追いつかない
- **「この段落で ◯語 入れました」は出さない**(2026-09 利用者の指定
  「やはりいらないです」)。数えるだけの行で、読むものが1行増える害のほうが
  大きかった。**まとめの1枚は残してある** — あちらは教材ぜんぶの控えである
- **本文の隣に、紙と同じ丸の番号を出す**(2026-09 利用者の指定
  「集中モード内も①や②のような番号を入れてください」)。
  レッスンは紙を見ながら話すので、「2番のところ」と言えば
  **どちらを見ていても同じ場所を指せる。**
  上の帯の「3 / 14 発言」は**どこまで来たか**の目安であって、役目が違う。
  - 見た目は `.lesson-items > li::before` にそろえる(うすい面の丸)
  - **数字は自分で丸に入れる。** ①②③ の文字は端末ごとに形も大きさも違い、
    50 を超えると尽きる(絵文字を使わないのと同じ理由)
  - **話す人がいなくても出す**(記事の段落にも紙は番号を振っている)
  - 英語と訳のどちらでも出す。**箱も帯も 1px も動かない**
    (実測 `.focus-body` 57→777 / `.focus-bar` 777→844 が両方で同じ)。
    本文そのものは上下のまん中に置いてあるので、
    行数が変われば上下する。**これは前からの決まりで、変えていない**
- **紙の幅をそのまま引き継ぐ**(2026-09 利用者の指定
  「PCで集中モードに入った時は、それまでの画面幅を引き継いでください」)。
  紙で 130% にして読んでいた人が、入った瞬間に別の幅に変わっては落ち着かない。
  数字は `.lesson-sheet--w*` と**同じもの**を使う(`.focus--w*`)。
  **狭い画面では効かない**(`max-width` なので、画面のほうが狭ければそのまま)。
  実測: 紙 860 / 946 / 1032 / 1118 / 1204 / 1290 / 1416px に対し、
  集中モードの本文も同じ幅になる
- **横スワイプで送らない。** 2語以上をなぞって調べる操作とぶつかり、
  端では「戻る」とも誤爆する。**ボタンだけにする**
- 吹き出し(`.etext-pop` は z-index 200)**より下**に置く(120)。
  語の意味がこの画面の裏に隠れては意味がない

#### 語を調べられるのは、広い画面と集中モードだけ

2026-09 利用者の指定。**方針の変更である。**

> スマホ、パッドのみ集中モード以外の時は単語を調べる機能を除外してください。
> これでスクロールが快適になるはずです

**語のタップと画面送りは、同じ指の動きから始まる。** 長押しをやめ、
「動かずに離れたらタップ」まで詰めてもなお喧嘩は残った(3度踏んでいる)。
**1段落だけを画面に固定する集中モードでは、送るものが無い**ので、
この喧嘩そのものが起きない。だから**調べるのは集中モードで**、
ふだんの読みは送りに徹する。

- 判断は `EnglishText` の **`tappable`** 1か所。既定は `'auto'`(広い画面だけ)、
  集中モードだけが `'always'` を渡す。**画面ごとに書き分けない**
- **判断は幅だけ**(`useWide()` = 1024px)。UA も `pointer` も見ない。
  **パッドを横向きにすれば押せるようになる**のも素直である
- **押せないときは `<button>` を残さない。** `.etext-word` は
  `user-select: none` を持っているので、押せないのに残すと
  **選んでコピーすることまでできない**、いちばん困る形になる。ただの文字に戻す
- **色(知っていた / 知らなかった)は消えない。** 印は `.etext-run` が
  持っているので、中を `<span>` にしても残る
- 要点フレーズの札(`PhraseChips`)は**そのまま。** あれは独立したボタンで、
  本文の上に重なっていないので送りの邪魔をしない(言われた場所だけを直す)
- **効く範囲は英文が出る画面すべて**(`EnglishText` を使う10か所)。
  狭い画面では、**紙・宿題・単語帳の例文でも語を押せなくなる。**
  記事・会話は集中モードで調べられるが、**ドリル・単語の問題文には
  集中モードが無い**(本文が無いので作れない)。狭い画面でそれらの語を
  調べる道は、いまは無い

##### 押せないなら、**押せない理由と行き先を、その場で言う**

2026-09 利用者の指定。

> 単語に長押しした時に表示が出るようにしましょう。

**狭い画面では、語を押しても何も起きない。** それが正しい振る舞いなの
だが、**画面の側は何も言っていなかった。** 調べられないのか、壊れている
のか、押し方が違うのかが、利用者には区別できない。
**黙って消さない**(ゲストの「書いたものはトレーナーに届きます」と同じ
考え方)を、ここでも当てる。

- **長押しで、1行の案内と「集中モードで開く」を出す**(`.etext-hint`)。
  概念の説明はしない —— **一度入れば、体で分かる**
- **長押しで「意味」を出す道は、二度と作らない。** あれは 2026-08 に
  3度踏んで消した(長押しは**押しているあいだに開く**ので、送ろうとして
  指を置いただけで開く)。ここで出すのは**消せる案内1つ**なので、
  間違って出ても害が無い —— しかも `watchHold` を使い回しており、
  **動いた・画面が送られた時点で取り消す**
- **出す場所は、指を置いた文**(`.etext-sent`)。段落まるごとを基準に
  すると、長い段落では案内が画面の外まで押し出される
- **行き先が無いのに誘わない。** `onNeedFocus` を渡した所だけに出す。
  いま渡しているのは **`LessonView` の本文1か所だけ**で、
  ドリル・単語には集中モードが無いので何も出ない
  (右下の「集中モード」を出す条件と同じ)
- **広い画面では出さない。** 語をそのまま押せば意味が出る
  (**同じことをするものを2つ見せない**)
- **色は決め打ちしない。** `createPortal` で body の直下に出るので、
  何も足さなければアプリの配色に従う(`.focus-paper` と同じ考え方)
- **`npm run test:bar` が3つとも見張る** —— ①390px で出て集中モードへ
  入るか ②送っているあいだは出ないか ③**1440px では出ないか。**
  「出る」だけを見ると、**全部の幅で出すようにしても緑のまま**になる。
  実際に窓口(`onNeedFocus`)を外して、赤くなることを確かめてある

#### 訳は「並べる」のではなく「入れ替える」

2026-09 利用者の判断「画面を切り替えれるようにするのが良い」。

**①並べるとこのモードが壊れる**(箱が2倍になり、送らないと読めない)。
**②訳が隣にあると、英語を読まずに済んでしまう**(記事の紙で同じ判断をしている)。

- **箱の高さは中身で変わらない**(残りいっぱいを取る)。
  実測で、切り替えても**帯も本文も 1px も動かない**
- **段落を送ったら、必ず英語に戻す。** 訳のまま送ると次も日本語で始まり、
  **英語を一度も読まないまま最後まで行けてしまう**
- **戻る道は同じボタン**(「訳を見る」⇄「英語に戻す」)
- **訳が無い段落では出さない**(効かない操作を見せない)
- **音も訳も両方出す**(2026-09 利用者の指定)

`useWordStatuses` が返すのは **Map**。オブジェクトのつもりで `statuses[w]` と
書くと**常に `undefined` になり、黙って 0 が並ぶ。**

##### **二度踏んだ。だから「気をつける」をやめた**(2026-09 実機)

> なぜ０語になっているのですか？

単語帳 → 業種べつ で、**同じ画面の中で数が食い違っていた。**

    学ぶ分野  [ ビジネス全般(0 語) ]     ← ここだけ 0
    まだ 190 / 覚えかけ 10 / 覚えた 0     ← 合わせて 200 語
    200 語から 5 語を出す / 聞き流す(200 語) / 印刷(200 語)

出どころは1行。`loadShelfCounts()` が返すのは **`Map`** なのに、
`ShelfBooks` が **`counts[s.id]`** と読んでいた。**35 冊ぜんぶが 0 語**である。

- **読む側が形を知らなくてよい形にする。**
  判断は **`shelfCountOf(counts, id)`(`src/data/shelves.js`)1か所**で、
  `Map` でも素のオブジェクトでも数えられる。
  **`ShelfBuilder` も同じものを通す**(数え方を2通り持たない ——
  2か所に持っていたから、片方だけがこの穴に落ちた)
- **数えられなかったら `null`。** `loadShelfCounts()` は数えられないと
  `null` を返すので、そのまま通して**呼ぶ側が「語数そのものを出さない」を
  選べる**ようにする。0 と書くと「まだ1語もありません」という嘘になる。
  同じ理由で、控えの初めの値も **`{}` ではなく `null`**
- **骨組みが本物と食い違うと、検証は何も守らない**(この節の下にある決まり)。
  `__screens.jsx` が `Object.fromEntries(...)` を渡していたので、
  **骨組みでは正しく数が出て、ずっと緑だった**
- `npm run test:play` が、`Map` / オブジェクト / `null` の3とおりと、
  **`counts[` が戻っていないか**・**骨組みが `Map` を渡しているか**を見張る

##### **同じ関数に、もう1つ「0 語」の芽があった**(`.range()`)

`loadShelfCounts()` は**棚ぜんぶの行**を数える。35 冊 × 200 語 = **7,000 行**で、
PostgREST(Supabase)は**1回に返す行数に上限を持つ**(既定 1,000)。
`.range()` を付けずに読むとそこで切られ、**後ろの棚がまるごと「0 語」**になる
—— 利用者が見たのと**同じ見え方をする、別の原因**である。

- **上限がいくつでも正しい形にする。**「返ってきた行が1ページぶんに
  満たなくなるまで読む」なら、上限を知らなくてよい。
  **上限が 7,000 なら1回で終わり、増える問い合わせは0回**である
- **並び順を必ず決める**(鍵は 分野 × そろえた語)。決めないと、
  ページのあいだで同じ行が二度来たり、抜けたりする
- **1ページでも読めていれば、そこまでを返す。** 1行も読めていなければ `null`
- **こちらでは実測していない**(この環境から Supabase へ届かない)。
  上限の値そのものは推測だが、**この形は上限がいくつでも正しい**

### ③⑤ は「同じ本文を、どう見ながら読むか」を選べる

`PASSAGE_VIEWS`(素の文章 / 区切りを出す / **区切り + 訳**)と「段落で区切らない」。
区切りは②と同じ決まりで出す(`SlashedText`)。**2か所に持たない。**

- **通し表示では、行ごとの操作も語の意味も出さない。** 押したところから
  読み上げが始まるので、語の吹き出しとぶつかる。読むことに集中させる
- **通し表示では、話す人の名前も出さない**(2026-09 利用者の指定)。

  > 本文全文表示させた時に話しての名前が文章の間に入ってしまっています。
  > これは排除してください。段落ごと、発現ごとの場合は今まで通りでOKです

  通しは**1本の文章として続けて読む**ための見せ方なので、発言を横につなぐ。
  すると名前が**文の途中**に紛れ込み、英文の一部のように見えていた。
  誰の発言かは**声が分けている。** 段落ごと・発言ごとでは、これまでどおり出す
- **要点の札(`PhraseChips`)は ③⑤ に出さない。** 声に出す練習なので、
  読むものが増えると気が散る(2026-08 の指摘)
- **通しの読み上げは、押した段落から始められる**(`playAll(id)`)

### 練習の囲みは、どのトレーニングでも同じ形にする

**1問 = 1枚のカード**(`.qa-row`)、**答えは灰色の囲み**(`.answer-box`)。
細い線1本で区切っていたので、どこからどこまでが1問か分からなかった
(2026-08 の指摘)。**部品ごとに書くと、必ずどこかだけ違う見た目になる。**
紙の上の色は `--qa-bg` / `--qa-line` / `--qa-answer` で差し替える。

### 英文と訳は「1文ずつ」対にする

教材の1項目は、記事なら**段落**、会話なら**発言**である。そのままでは
Quick Response の1問が5行になり、6Steps でも1文に段落まるごとの訳が付く。
`alignedSentences()`(`src/lib/sentencePair.js`)が英語と日本語を
それぞれ文で切って対にする。**数が合わないときは切らない。**
長い対より、**まちがった対のほうが害が大きい**(違う英語が答えとして出る)。
合わなかったときだけ `jaIsWhole` を立て、画面が「段落の訳」の札を出す。

**日本語のほうが文が多いときは、長さの比でまとめて数をそろえる**
(2026-09 実機「ディクテーション内での訳が、1文ずつになっていません」)。
英語1文がコロンのところで2文に訳されることがあり、実測した段落は
**英語4文・日本語5文**で、段落の訳が4回並んでいた。
日本語と英語の長さの比は同じ段落の中ではほぼ一定なので、
「英語の何%まで来たか」で当てられる。
**外れそうなときはやらない**(`TOLERANCE` を超えたら「段落の訳」に落ちる)。
あわせて窓口にも「**prompt_ja の文の数は prompt_en と同じにする**」を足した。

### 練習の画面は、文の長さが変わってもボタンが動かないようにする

「文章の長さにかかわらず、上下にスクロールして微調整せずに、
常に安定して全体像がまん中あたりに収まるように」(2026-08 利用者の指定)。

- **Quick Response は、答えを同じ場所で入れ替える**(2026-09 利用者の指定・
  **方針の変更**)。

  > quick reponse内の表示だが、単語帳と同じにしてくれ

  2026-08 は「**入るなら並べる。入らないときだけ入れ替える**」で、
  入るかどうかを実測(`scrollHeight > clientHeight`)して出し分けていた。
  ところが**単語帳はいつでも入れ替えである**(「英語を見るにすると
  日本語と入れ替えで同じ場所に表示してください」)。
  **同じことをする2つの画面で、開いたときの動きが違っていた。**

  - **いつでも入れ替えなら、必ず収まる。** 測って出し分ける道具
    (`is-tight`)は**ごと消した**。値を偽にするだけだと、
    次に見た人が「まだ使うのかもしれない」と読む
  - **答えはうすい色の囲み**(`.answer-box`)に入れる。
    ほかのトレーニングの解答と同じ形にそろえる。
    **これは 2026-08 の別の指定**(「クイックレスポンスの正解は、
    以前のように、淡い色の囲みで表示される方がよかったです」)なので、
    入れ替えにしても**囲みは残す**
  - **上下のまん中に置く。文字が増えたら下へ伸ばし、それでもまん中を保つ**
    (2026-08 の指定で改めた)。枠は `min-height`(下限 6rem)。
  - **ただし、伸ばしていいのは「残りの高さ」までである**(2026-09 実機
    「quick response で英語を見ると、その後閉じられません」)。

    上限がまったく無かったので、長い英文を開くと枠がそのぶん下へ伸び、
    **「英語を隠す」「まだ」「言えた」の行を画面の外へ押し出していた。**
    押した本人からは「開いたら閉じられない」に見える。
    しかも枠は伸びる一方なので `scrollHeight > clientHeight` が
    **一度も成り立たず**、入れ替えの判断(`is-tight`)も死んでいた。

    紙の上では**残りの高さを計算しない。**
    枠を `flex: 1 1 auto`、ボタンの行を `flex: 0 0 auto` にすれば、
    残りにひとりでに収まる。**ただし途中の箱(`.qr` / `.qr-card`)に
    `min-height: 0` を置く。** flex の箱は既定では中身より小さくならないので、
    置かないと長い英文で紙より背が高くなる(実測 320×568 で 404 → 659px)。
    **`min-height: 0` を置くのは途中の箱だけ。** いちばん中の出題の枠には
    下限(5rem)を残す(0 まで縮むと問題が真っ白になる)。
    紙の外で使うときのために `max-height: calc(100dvh - 15rem)` も置いてある
  - **同じことを、集中モード(`.qrfocus`)にもする**(2026-09)。

    **紙の上にしか無かった。** `.focus-body` は送る箱なので、中身は
    そのぶんの高さしか取らない。だから出題の枠は base の `min-height`
    に落ち、**中身なりに伸びていた。** 実測(390×844・本物の部品):

        枠 219px → 238px。**ボタンの行が 19px 下がる**

    **Quick Response の復習は、いつも集中モードである**(`QrReview`)。
    つまり利用者が毎日見るほうが、ずっとこうなっていた。
    直し方は紙とまったく同じ(`.focus-paper` → `.qr` → `.qr-card` に
    「残りいっぱい」と `min-height: 0`、枠に `flex: 1 1 auto` と
    `max-height: none`)。**新しい決まりを作らない**
  - **測るときは、本物の置かれ方で測る。** はじめ検証が裸の `<div>` に
    `QrCard` を置いていたので、19px 動いても「入れ物が本物と違うせいか、
    本当に壊れているのか」が切り分けられなかった(答えは**本当に
    壊れていた**)。**高さの決まりは置かれ方で変わる** ——
    `?screen=qr` は `FocusFrame` + `<section className="qr">` の
    本物の形にしてある
- 出題の枠の下限は **`clamp(6rem, 26vh, 15rem)`**。
  **下限を必ず置く。** `min-height: 0` にすると窓が低いときに
  **高さ 0 になって問題が真っ白になる**(2026-08 実機)。
  この値が効くのは**紙にも集中モードにも入っていないとき**だけで、
  実際の2か所では上の「残りの高さ」が勝つ
- **広い画面では、1行ぶん上に置く**(2026-08 利用者の指定)。
  まん中に置く決まりはそのままで、**下に余白を足してまん中を持ち上げる**
  (足す量は上げたい量の2倍。まん中なので半分ずつ効く)。
  **スマホには足さない**(「良好な表示位置なので変えないでください」)
- **Quick Response は、いつでも上下のまん中**(2026-08 の指定で改めた)。
  紙の残りいっぱいを取り、その中でまん中に置く。
  以前は「上から積む」だったが、パソコンの大きな画面で
  **上半分に寄って、下が大きく空いていた**
- **`min-height: 0` にしない。** 窓が低いと高さ 0 まで縮み、
  **問題が真っ白になった**(2026-08 実機)。下限(`7rem`)を必ず置く
- `justify-content` は **`safe center`**。`center` だけだと、はみ出したときに
  中身が**上へ逃げて届かなくなる**
- それでも入りきらないときは、**こちらで送る。** ただし
  `scrollIntoView` は**紙まで一緒に送ってしまう**ので、`scrollTop` で
  **その枠だけ**を動かす。**送りの面倒は1つの effect にまとめる**
  (「開いたら送る」と「問が変わったら戻す」を別々に書いたら、
  次の問の日本語が枠の外から始まった)
- **6Steps の切り替えは、プルダウン**(2026-09 利用者の指定「6Steps は
  プルダウンにしてください」)。以前は札を6つ横に並べ、どの幅でも6つとも
  見えるように折り返させていたが、狭い画面では2段になり、
  紙で文字を大きくすると帯だけで場所を食っていた。
  **番号(①〜⑥)は選択肢に出す**(何番目かが道しるべになる)
- **行の操作は右上へ。** 話す人の名前と反対側に置くと、本文と解答を
  そのぶん上に寄せられる(`.row-head` / `.row-tools`)
- **音声認識の断り書きは、話すボタンがあるステップにだけ出す。**
  ② スラッシュリーディングには関係がない
- **答えはボタンの上に出す。** 下に出していたので画面の下端へ押し出された
- 紙(レッスン表示)では `.lesson-sheet.is-running` で**縦いっぱいの1枚**にする
- 練習中は**効かないボタンを出さない**(ページ送り・解答)。迷わせるだけ
- **紙の上の札は小さくする**(`0.8em`)。始めたあと出しっぱなしになるため。
  ただし**狭い画面(600px 以下)では px で固定し、折り返させない。**
  紙の文字を「特大」にすると 0.8em でも 18px になり、
  「6Steps」「Quick Response」が縦に積まれて 105px を食っていた
  (2026-08 実機)。**操作は、読むものの大きさに合わせなくてよい**
