### 欄が「無い」と言われたら、**本当に無いのかを先に確かめる**(第5.213節)

2026-09 利用者の指定。

> 記事や会話、会議も含めた全ての教材を作成する際に、細かい指定を
> 書き込める欄を作ってください。現状は文型トレーニングや
> スピーチ練習にはすでにあります。

**欄は第5.190節で全種類に出ていた。** 無かったのではない。

| 何が悪かったか | 直し方 |
|---|---|
| 呼び名が種類ごとに違う(話題 / 話す中身 / 文の中身 / 出す語の中身) | **どの種類でも同じ1つ**にそろえた(`SUBJECT_LABEL`) |
| **1行の入力**だった。注文を2つ3つ書くと左へ流れて消える | **複数行の箱**にした |

- **呼び分けると、同じ物が別物に見える。** 「呼び名を2か所に書かない」の
  **もう一つの面**である —— 1か所から引いていても、
  **引いた先が種類ごとに違えば同じこと**になる
- **例(`example`)までは1つにしない。** 何を書けばよいかは種類で本当に
  変わる。そこまでそろえると、どの種類でも同じ例になる
- **見張りは、向きごと書き換える。** 第5.190節では
  「呼び名が種類ごとに変わること」を赤チェックしていた。
  決まりが変わったので、**そのまま逆向きに**書き換えた

### 画面の言葉と、データベースの値を混同しない(第5.213節)

「スピーチ練習」→「モノローグ」。**`id` は `speech` のまま変えない** ——
あれは `materials.kind` に入っている値で、変えると
`material_kind_check` に引っかかり、すでに作った教材が開けなくなる。

**同じ名前のものが2か所にあった。** どちらを変えるかを先に確かめた。

| | 何 | 変えたか |
|---|---|---|
| 教材の種類(`materials.kind = 'speech'`) | 作るときに選ぶ | **変えた** |
| ゲストのメニュー(`pages.id = 'pronunciation'`) | 自分の声を録って練習する画面 | 変えていない |

### タブは `Tabs.jsx` を使う。折り返させない

スマホの幅でタブが2行に折り返し、「教」「材」のように縦に割れて
読めなくなった(2026-08)。**折り返さず横に流し、選んでいるタブを
見える位置へ寄せる。** 画面の切り替えは下線、教材の中の切り替えは丸い札で、
階層を見分けられるようにしてある。

### 同じ分野の中の「種類」は、2段の欄で選ぶ

`parent` / `short` / `kindsOf()`(`src/data/industries.js`・2026-09 利用者の指定)。

> 各趣味、業種は、同じ業種内に種類がある場合はさらにメニューが展開して
> 選べるようにしてください。

**入れ物は1つのまま**(`materials.industry`)。保存されるのは
**選んだ種類の id**(`consult_con` など)で、**階層は保存しない。**
だから SQL も要らないし、種類をあとから組み替えても既存の教材は壊れない。

- 1つめの欄には**親だけ**を出す(`industriesIn`)。
  種類があるときだけ2つめの欄が出る(**効かない操作を見せない**)
- 種類の先頭は**「全般」(親そのもの)。** 決めきれない人が行き止まりに
  ならないようにする。**全般では、種類ぜんぶの場面・話題を集めて出す**
  (`ownOf`)。親に場面を持たせていないので、そうしないと共通しか出ない
- さがす画面で「全般」を選んだら、**その中の種類の教材もまとめて出す**
  (`searchMaterials`)。コンサルを選んで建設・車が出ないのでは意味がない
- **`label` は、それだけで通じる名前にする**(「コンサル(建設)」)。
  教材の名前や絞り込みに出るため。2つめの欄に出す短い名前が `short`
- **さがす画面と作る画面で、同じ形にする**(片方だけ2段にしない)

### 一度入れた業種・趣味を、勝手に減らさない

2026-09 利用者の指定。**プロジェクトを超えた決まり**である。

> 一度入れた業種や趣味は勝手に減らさないでください。
> 一度追加した要素は指示がない限りは勝手に変更を加えないでください。
> これはプロジェクトを超えたルールです。業種や趣味については追加を
> お願いしたことはありますが、減らしてくださいとは一度も頼んでいません。

**「並べ替え」も「減らす」に当たる。** 2026-09 に「種類があるときは2段に」
という指定を受けて、**趣味にも当ててしまった。** ところが「スポーツ」
「食べること」「音楽」という親は**こちらが勝手に作ったもの**で、
その下にゴルフ・料理・食べ歩き・ワイン・DJ を押し込んだ結果、
1つめの欄に出る趣味が **15 → 6 に減って見えた。**

- **2段にしてよいのは「同じ分野の中の種類」だけ**
  (コンサル(建設 / 車)のように、もともと1つの分野が分かれる場合)
- **無い親を作って、既にあるものをその下に入れない**
- 消さざるをえないときも、**`id` は残す。**
  その id で作った教材の名前が出なくなる

### 種類を持てるのは2段まで

`parent` は1つしか持てない。3段にしたくなったら、
**中の1つを1つめの欄へ上げる**(2026-09、格闘技を MMA / ボクシングの
親にするために、スポーツの種類から分野へ上げた)。
上げても**見えなくなるわけではない。** むしろ上に出る。

### 格闘技は、それだけで1つの分野。**種類はその中に並べる**

2026-09 利用者の指定。**3手かかっている。経緯ごと残す。**

| | 言われたこと | どうしたか |
|---|---|---|
| ① | — | 格闘技はスポーツの種類だった(MMA もボクシングも無い) |
| ② | 「格闘技には、MMAとボクシングを」 | **種類は2段まで**なので、格闘技を1つめの欄へ上げ、下に2つを並べた |
| ③ | 「スポーツの中に MMA・ボクシング・柔術を追加してください」 | 3つをスポーツへ移した |
| ④ | **「スポーツの中に MMA とボクシングは必要ない。格闘技の中に、さまざまな格闘技を入れ…ムエタイもほしい」** | 格闘技の下に戻し、種類を9つに増やした |

**③はこちらの読み違いだった。** 利用者が言っていたのは
「**格闘技の一覧を充実させたい**」であって、
「スポーツの中に混ぜたい」ではなかった。
**言われた言葉のとおりに置く前に、その人が何をしたいのかを考える。**

いまの格闘技の種類(9つ + 全般)。

    全般 / MMA / ボクシング / キックボクシング / ムエタイ /
    柔術 / 柔道 / レスリング / 空手 / テコンドー

- **1つずつ並べる。まとめない。** 同じ「格闘技」でも、ジムで交わす言葉は
  別物である。ボクシング(手だけ)/ ムエタイ(肘膝と首相撲)/
  柔術(寝技と帯)/ レスリング(タックル)/ 柔道(投げと一本)。
  場面・話題もそれぞれに用意してある
- **`id` は一度も変えていない。** 変えると、その id で作った教材の
  名前が出なくなる。②③④で動かしたのは `parent` だけである
- **「全般」を選べば、種類ぜんぶの場面・話題が並ぶ**(`ownOf`)

### 業界は `src/data/industries.js` 1か所。**趣味・娯楽も同じ列に入れる**

**表も列も増やさない。** `materials.industry` の1列のまま、`group` で
「お仕事」と「趣味・娯楽」に分けて見せるだけ(`<optgroup>`)。
`group` が無いものは、これまでどおり「お仕事」。

> 業界を選ばない場合に選べるようにしたいのが、「趣味・娯楽」です。
> (2026-08 利用者の指定)

**生成の窓口には、id ではなく日本語の名前を渡す**(`industryText`)。
以前は `it の場面に寄せること` と入っており、**AI には何のことか伝わらない。**
趣味を足したことで `listening` `watching` のような語が増え、
「聞き取りの場面」と読まれる危険が出た。
**データベースに入れるのは、これまでどおり id。**

### 場面・話題は「分野ごとの特化 + 共通」で出す

`src/data/genres.js` 1か所(2026-08 利用者の指定)。

> どの業種でもあるような共通のシチュエーションはそれぞれに入れておいて
> ください。なぜなら例えば朝のミーティングでも業界によって使われる単語や
> フレーズが異なるからです。

`scenesFor(industry)` / `genresFor(industry)` が
**その分野に特化したもの + どこにでもあるもの**を並べて返す。

- **共通の側は、仕事と趣味で別に持つ。** 仕事の「真面目な会議」を
  ゴルフに出しても、その人が英語を使う場面にはならない
- **登録の無い分野は、共通だけになる。** 分野を足して場面・話題を
  足し忘れても壊れない
- **id は分野の名前で始める**(`sur_preop` / `wing_grape`)。
  `materials.scene` / `materials.genre` に保存されるので**変えない**
- **分野を変えたら、場面・話題もその分野のものに入れ替える。**
  入れ替えないと、外科医の教材に「打ち合わせ前の雑談」が残る。
  いまの選択がその分野にもあれば、そのままにする
- 名前引き(`sceneLabel` / `genreLabel`)は全部から探す。
  **これまでに作った教材の名前が出なくならないように**

#### どの業種にもある場面は、**業種ごとに書かず共通に置く**

2026-09 利用者の指定「『面接の練習』を全ての業種に入れて下さい」。

`jobinterview`(`DIALOGUE_SCENES`)。**業種ごとに書き写さない** ——
写すと、業種を足すたびに書き足すことになり、必ずどこかが抜ける。
共通に置いても**出てくる語は業種で変わる**(IT なら設計や障害対応、
製造なら現場や歩留まり)。`DIALOGUE_SCENES` を持っている理由そのものである。

- **`review`(面談・振り返り)とは別物。** あちらは上司と部下の評価の話で、
  相手はもう自分を知っている。こちらは**初対面**で、経歴を自分から説明する
- **`sp_interview`(面接での自己 PR)とも別物。** あちらは1人が話しきる
  スピーチで、こちらは**やりとり**である
- **いちばん下に足す。** 上の13件は1つも消していないし、並びも動かしていない
- `npm run test:play` が、**4つの業種で本当に出るか**を確かめている

#### 趣味に「ファッション」を足した(2026-09 利用者の指定)

`fashion`(`industries.js`)+ 場面6件(`fas_*`)+ 話題4件(`fasg_*`)。
**いちばん下に足してあり、既存の分野は1つも動かしていない。**
種類(`kinds`)は作らない —— 言われたのは1つだけである。
`npm run test:play` が「趣味の数が減っていないか」も一緒に数える。

### 教材を作る欄の並びは、利用者が決めている

**レベル → 業界・趣味 → トレーニングの種類 → 話題 / シチュエーション → ゲスト**
(2026-08 利用者の指定)。`MaterialForm.jsx` 1か所なので、
トレーナーの「教材」からでも、ゲストのカードの「この人に教材を作る」からでも
同じ並びになる。**並びを変えるときは、この指定を確かめること。**

**「読み上げの声」は、種類・場面のすぐ下に置く**(2026-09 利用者の指定)。

> 話者(国・訛り)の指定が、記事・ダイアローグ、会議を選んだ時点で
> 表示されるよう改良してください

以前は「ゲスト」より**下**にあったので、記事や会話を選んでもそこから
見えず、**送らないと気づけなかった。** 種類を選んだ流れのまま、
誰が読むかまで決められるようにする。
**上の5つの並びは崩していない** — 声をゲストの前に入れただけである。

**訛りの欄と「話す人」の欄は、下端でそろえる**(`.voice-row` の
`align-items: flex-end`・2026-09 実機「話者を指定するタブが縦にずれて
表示されます」)。訛りには**見出しを出していない**(2026-08 利用者の指定)
ので、見出しの1行(16px + 隙間 4px)だけ背が低い。
既定の `stretch` では入力欄がそれぞれの箱の**上**に置かれ、
**訛りだけが 20px 高い位置**に出ていた。
下でそろえれば、見出しの有る無しにかかわらず1直線に並ぶ。
**見出しを足して直さない** — 出さないと決めた見出しである。

**業界と趣味は、プルダウンを2つに分けて同じ行に左右**に並べる。
入れ物は `materials.industry` の1列のままで、**表も列も増やさない。**
教材が持つ場面は1つなので、片方を選ぶともう片方は空に戻る。

### ゲストのカードから作るときも、まったく同じ画面にする

**片方にだけ注意書きを足さない**(2026-08 利用者の指定)。

> 教材作成のデザインはゲストモード内でも教材モードと全く同じにしてください。
> ゲストモード内は余計な文言が多すぎて無駄が多いので注意書きも
> 教材モードと同じくほとんどない状態にしてください。

外したのは2つ。どちらもゲストのカードからのときだけ出ていた。

- 「◯◯さんだけに共有されます」— **選べるゲストがその人1人しか出ていない。**
  画面を見れば分かることを、文で言わない
- 「1人に絞ったので…教材名にもお名前が入ります」— **もう本当ではない**
  (教材名にゲスト名を入れない)。同じ英文を二度出さない仕組みは、
  選んだ人数によらず働く

**古い注意書きは、消し忘れると嘘になる。** 仕様を変えたら、
それを説明していた文も一緒に探すこと。

### 画面に出す長い日本語は `TeachingNote.jsx` を通す

指導ポイントを1つの `<p>` に流したところ、改行も区切りも無い棒になり
読めなかった(2026-08 の指摘)。行で区切り、【弱点名】を見出しにし、
**日本語の中の英語を太字にする。** 古い教材(改行の無い長文)は
句点で切って並べるので、作り直さなくてよい。

**`\n` という「文字」が混じることがある**(2026-08 実機)。
画面に `\na few/a little は…` と出ていた。これは本物の改行ではなく、
**バックスラッシュと n の2文字**である(AI が JSON の中で改行を書こうとして、
そのまま文字になったもの)。**すでに作った教材にも入っている**ので、
作り直させずに、`toLines()` が出すときに本物の改行として扱う。


### スピーチの場面に「あいさつ」を9つ足した(第5.182節)

2026-09 利用者の指定「挨拶、クライアントとのプロジェクトの初めての挨拶、など
考えられる場面を作り出してください」。

もとからあったのは「自己紹介(初対面の場)」「着任のあいさつ」の2つで、
**どちらも自分の話**である。足りなかったのは**相手先へ出向くとき・
場を開くとき・締めるとき**で、話す長さも丁寧さも入り方も違う。

23 → 32 件。**後ろへ足す。並べ替えない。**
`SCENE_STYLES`(場面 × 話し方の型)にも9つとも足した ——
書き足さないと**全部の型が出る**(あいさつに「創業者のように」が出る)。

#### 「選べなくなっている」は再現しなかった

同じ道(教材 → Speech練習 → 業界エネルギー → 種類 風力発電)を
**実際に描いて数えた**ところ、シチュエーションは 23 個あり選べた。
`MaterialForm.jsx` はその作業のあいだ1文字も触っていない。

**再現しなかったことは、再現しなかったと言う**(`.claude/rules/common.md`)。
そのうえで「どの欄のことか」を利用者に確かめる ——
候補は ①シチュエーション ②話題(いまは記事のときだけ出る)③話し方の型。

### エネルギー関連ぜんぶに、土木の要素を足した(第5.188節)

2026-09 実機・利用者の指定。

> 「業界」内のエネルギー関連すべてに「土木」の要素をうまく追加してください。
> スピーチに対しても同様です。

**発電所は、電気の話の前に土木の話がある。** 用地・造成・基礎・進入路・
排水がまとまらなければ、1枚のパネルも1本の鉄塔も立たない。

#### 足す場所は4つ。**1か所だけでは、教材の中身は変わらない**

| どこ | 何 |
|---|---|
| `industries.js` の `hint` | 12 種ぜんぶ。**画面にも出るし、そのまま AI にも渡る** |
| `SCENES_BY_INDUSTRY`(会話) | 11 種 × 2 |
| `GENRES_BY_INDUSTRY`(話題) | 11 種 × 1 |
| `SPEECH_BY_INDUSTRY`(スピーチ・**新しい表**) | 6 件を 11 種で分け合う |

**もとの語は1つも消していない。後ろへ足しただけ**である。

#### 会話は種類ごと、スピーチは分け合う

風力の「基礎とアンカー」と水力の「導水トンネル」は別のものなので、
**会話の場面は1種類ずつ書く。**

けれども「住民へ工事の説明をする」「安全大会であいさつする」は、
**太陽光でも送電でも同じ場面**である。だから `ENERGY_CIVIL_SPEECH` を
1つ書いて、11 種で分け合う ——
**同じものを11か所に書き写さない**(CLAUDE.md)。

#### スピーチの場面にも、業界ごとの表を持てるようにした

これまでスピーチは**共通の一覧だけ**だった。
会話(`scenesFor`)とまったく同じ形(**特化 + 共通**)にしてある。

- **登録が無い業界は1つも増えない。** これまでどおり共通だけ
- **`ALL_SCENES` にも足す。** 忘れると、教材の名前に
  `spc_safety` という id がそのまま出る

#### **「1つでもあれば緑」にしない**

はじめ「土木の語を含む場面が1つでもあれば緑」という見張りを書いたが、
**風力の「洋上の工事」のように、もとから土木の語を含む場面があった。**
そのため**足したものを丸ごと消しても緑のまま**になった(赤チェックで発覚)。

- **2つ以上**にする
- **説明ではなく名前で数える**(説明に紛れ込んだ1語で数を増やさない)
- **「よその業界には足していない」も一緒に見張る** ——
  **言われた場所だけを直す**が守れているかは、測らないと分からない

### モノローグの場面は、細かい指定を書けば選ばなくてよい(第5.228節)

2026-09 利用者の指定。

> モノローグの教材の場面設定は、「細かい指定」に記入した場合には、
> 選択はオプションに出来ないでしょうか?

**場面と細かい指定は、どちらも「どんな話にするか」を決めるもの**である。
細かい指定に書いてあるのに場面まで選ばされると、
**書いた中身と食い違う場面が、勝手に混ざる。**

- **判断は `sceneFree` 1か所。** 画面の中で `kind === 'speech' && …` と書かない
- **既定は「選ぶ」側。** 細かい指定が空なら、これまでどおり必ず1つ選ぶ ——
  書いていないのに「選ばない」を出すと、**場面も中身も無いまま**作れてしまう
- **細かい指定を消したら、場面を先頭へ戻す**(黙って無指定にしない)
- 分野を変える道と、話し方の型を選ぶ道の**2つが場面を書き戻していた。**
  どちらも塞がないと、「選ばない」がすぐ壊れる
- `speechBrief()` はもともと空の場面を落とす作りだった(素の node で確認)

### 「細かい指定」に書いたら、それが主になる(第5.232節・2026-09 実機)

> 唐揚げの加工工場の話だと指定したら、「悪い知らせをする」という
> 切り口が強制的に選ばれ、そのような話になってしまいました

- **「おまかせ」は「そのときどきで決める」**という意味であって、
  「必ず1つ付ける」ではない。**中身が書いてあるなら、それが答え**
- **切り口は、細かい指定があれば引かない。** 値(`''`)は変えず、
  **欄の言葉だけ**を、いまの意味に変える(値を変えると控えと食い違う)
- **場面と話題は、自動で外さない。** あちらは先頭が選ばれている状態が
  既定なので、**自分で選んだのかどうかを見分けられない。**
  勝手に外すと**黙って消す**ことになる。道だけ用意する
- **欄そのものは消さない。** 選びたければ選べる(行き止まりを作らない)
- **両方えらんだときは、切り口の文に「話題が優先」と足す。**
  窓口は置き直さない —— 切り口は**画面が作る文字列**である
- 判断は `materialKinds.js` の `freeFromSubject()` 1か所。
  第5.228節は speech だけだったが、**同じ困り方が会話・会議・記事でも
  起きていた**ので、本文を持つ4種類すべてに広げた

### 用件 × 感情 × 相手への態度 × 会話上の反応(第5.361節)

2026-10-03 利用者の指定。**90 個の値と、4つの軸をそのままいただいた。**

> ただし、これらは全部を「話す目的」という一つの欄に詰め込むより、
> 次のように分けると教材の組み合わせを作りやすい。
>   ・発話の目的：頼む、断る、謝る、知らせる、説得する
>   ・感情・状態：怒っている、弱っている、喜んでいる、不安がある
>   ・相手への態度：叱る、励ます、嫌味を言う、気遣う
>   ・会話上の反応：反論する、受け流す、言い訳する、共感する

> たとえば「仕事のミスを報告する」場面でも、「焦って言い訳する」
> 「落ち込んで謝る」「怒って責任を追及する」「冷静に再発防止策を
> 提案する」と、感情や態度を変えるだけで会話の内容が大きく変わる。

#### 軸を分ける意味は、ここにしかない

| | 個数 |
|---|---|
| 発話の目的 | 5 |
| 感情・状態 | 36 |
| 相手への態度 | 28 |
| 会話上の反応 | 21 |
| **掛け合わせ** | **105,840 通り**(足し算なら 90) |

**1つの欄に並べると、1本の教材で1つしか選べない。**
場面(83分野 × 平均21場面 = 1,700通り)と掛ければ、
**事実上、同じ組み合わせは二度と出ない。**

#### どこに置いたか —— **1つも捨てていない**

いただいた4つのまとまりは、ほぼそのまま軸に対応した。

| いただいた分類 | 軸 |
|---|---|
| 感情を表す(27) | 感情・状態 |
| 相手への働きかけ(26) | 相手への態度 |
| 会話で反応する(14) | 会話上の反応 |
| 意見や態度を示す(20) | **3つに分かれた**(下記) |

**「意見や態度を示す」の分け方**(こちらの判断。直すのは `speechAxes.js` 1か所)

- → 会話上の反応 … 賛成する / 反対する / 同意する / 異議を唱える /
  疑問を呈する / 納得する / 納得できないと伝える(7)
- → 感情・状態 … 迷う / ためらう / 決意する / 覚悟を示す / 勇み立つ /
  意欲を見せる / 諦める / 開き直る / 強がる(9)
- → 相手への態度 … 遠慮する / 気遣う / 本音を打ち明ける / 秘密を明かす(4)

**`謝る` と `説得する` は「発話の目的」に置いた。**
いただいた一覧では「相手への働きかけ」にも入っていたが、
**同じ言葉を2つの軸に出すと、どちらを選べばよいか分からなくなる。**

**「発話の目的」は、挙げていただいた5つだけ**にしてある ——
ほかの3軸のような長い一覧をもらっていないので、**勝手に足していない。**

#### 置き方は `materialAngles.js`(切り口)とまったく同じ

- **閉じた一覧で持つ。** AI に「毎回ちがう気持ちで」と頼まない ——
  頼んでも寄るものは寄るし、**Sonnet 5 は `temperature` を指定できない**
- **`materials.stance` に保存する**(0074)。保存しないと
  「まだ使っていないものから引く」ができない
- **窓口は置き直さない。** 画面が作る文字列として、切り口と同じ欄に足して送る
- **話し手がいる教材だけに出す**(`stanceWorks()` 1か所)——
  読み物には話し手がいないので「怒っている」も「受け流す」も成り立たない

#### 「気持ちを、言葉で説明させない」が肝心なところ

書かないと AI は `I'm really anxious about this.` と**気持ちそのものを
口に出す。** それでは練習にならない。

    **語の選び方・文の長さ・言いよどみ・くり返し・間の取り方**に出す
    （焦っているなら文が短く切れ、落ち込んでいるなら語数が減り、
    苛立っているなら相手の言葉を遮る、というように）

#### 日本語だけ渡すと、AI の中で混ざる

「苛立つ(irritated)」と「うんざりする(fed up)」は、日本語だけでは
取り違えられる。**短い英語を1つずつ添えてある** —— 訳させるためではなく、
**どの気持ちかを決めるため**である。

#### 列は1つだけにした

4つの軸を `pu_apologize|em_down|at_openup|re_excuse` の形で
**`materials.stance` 1列**に入れる。4列に分けるより、
**利用者が貼る SQL が1つで済む。**
つなぎ方・ほどき方は `stanceText()` / `parseStance()` の2つだけが知っている。

#### 実際に描いて確かめた

Chromium で作る画面を開き、会話・会議・応答問題では4つの欄が出て
感情は 37 択(おまかせ + 36)、読み物・スピーチ・単語では1つも出ないことを
測ってある。

#### 既存の見張りが1本、**仕組みは無傷なのに赤くなった**

`angle: angleWithSubject(angleBrief(angleId), subject` と**式をそのまま
書き写して**あったので、人物設定を同じ欄に足した瞬間に外れた。
呼んでいるかどうかだけを見る形に直した ——
CLAUDE.md の「**式も、関数の名前も書き写さない**」を**5度め**に踏んだ。
