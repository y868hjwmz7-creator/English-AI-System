### 読み上げは `readAloud.js` を呼ぶ。端末の声を直接使わない

**iPhone では、どのブラウザを使っても良い声を出せない。**
iOS はすべてのブラウザの中身が Safari(WebKit)であり、
高品質音声を Web Speech API に**一切公開しない**(実機で生47件・premium 0件)。
2026-08、知り合いの iPhone + Chrome で「最低な声」が出た、という報告で確定した。

そこで教材の英文は **こちらで作った MP3 を配る。**

```
tts/<話者>/<英文の SHA-256>.mp3   ← 場所は計算で決まる。目録の表は持たない
```

- 画面はまずこの場所を `<audio>` に渡す。**あればそれで終わり**(CDN と端末の控え)
- 無ければ窓口 `speak` が Azure に作らせて置き、場所を返す
- それも駄目なら**端末の声に落ちる。画面には何も出さない**

**画面はどちらを鳴らすか決めない。** 英文が出る場所は4つある。
4か所に分岐を書けば必ず食い違う。`src/lib/readAloud.js` の
`readAloud()` / `readAloudSequence()` / `stopReading()` だけを呼ぶこと。
`speech.js` の `speak()` は受け皿であって、画面から直接呼ぶものではない。

**速さでファイルを増やさない。** MP3 は自然な速さで1本だけ作り、
5段階の速さは `playbackRate` で変える。作り分けると費用も容量も5倍になる。

**語の重みの配り方は `wordTiming.js` 1つに置く。** 端末の声と MP3 で
別々に書くと、同じ本文なのに色の進み方が変わる。

**`<audio>` は1つだけ作り、作り直さない。** 最初に画面へ触れた瞬間に
無音を鳴らして解錠する。iOS は「押した流れの中で始まった再生」しか許さず、
MP3 を取りに行く待ちで流れが切れるためである
(`AudioContext` を1つだけ作るのと同じ理由)。

**会話の話者は `castClipSpeakers()` で決める。端末の声から換算しない。**
英語の声が1つも無い端末では、換算すると2人とも同じ話者になる。

`tts` バケツに**録音は入らない。** 入るのは教材の英文の読み上げだけ。
だから public にしてある。**書き込めるのは窓口だけ**(0016 はそれ以外の
書き込みポリシーを1つも作らない)。ここを緩めない。

**音声を作れなかったら、係の人に知らせる**(2026-09 実機)。
`speak` を配置していなかったあいだ、画面は**黙って端末の声に落ちて**いた。
理由(`lastClipDetail`)は集めていたのに、**どこからも読んでいなかった**ので、
「良い声にならない」ことに何日も気づけなかった。
`onClipTrouble()` で `App.jsx` に伝え、**トレーナーと管理者にだけ**静かに出す。
**ゲストには出さない**(仕組みの内側の話で、できることが何も無い)。
役割が分からないうちも出さない(既定は「見せない」)。

**知らせは、直ったら引っ込める**(2026-09 実機・利用者の指摘)。

> そして、音声がちゃんと作られているのにいまだにこの表示が消えないです。

**出しっぱなしだった。** 一度でも失敗すると、そのあと音声がちゃんと
作られるようになっても、**✕ を押すまで居座る。**
利用者から見れば「直したのに直っていない」にしか見えない。
**成功と失敗を同じ見た目で終わらせない**の裏返しで、
**直ったことも同じだけはっきり見せる。**

- 窓口が音声を返せた時点で `clearDetail()`。`askForClip` と `wholeClip` の
  **成功したところ**に置く(失敗と対になる場所)
- **画面は `null` を「直った」と読む。** 以前は `if (!detail) return` で
  捨てていたので、引っ込めようがなかった(`App.jsx`)
- **「窓口が古い」だけは残す**(`staleNote()` 1か所)。あちらは
  **音が鳴っても本当のまま**で、引っ込めると永久に気づけない ——
  そのために版を返させるようにしたのだから、ここで消しては元も子もない
- `stopped` が立っているとき(窓口に届かない)は、そもそも次を試さないので
  知らせは残る。**それが正しい**

**1本にまとめられなかっただけで、「端末の声」と言わない**(同じ回)。

`wholeClip` が失敗すると
**「読み上げ音声を作れませんでした。端末の声で鳴らしています。」**と出ていた。
**どちらも本当ではない** —— 段落ごとの音声はちゃんと作られるし、
端末の声にも落ちていない。しかも
**教材の画面は開いただけで全教材を裏で支度する**(`startPrepareAll`)ので、
**1本でも長すぎる教材があれば、開くたびにこの嘘が出る。**

- 1本にできないときは **黙って今までの形に落ちる**(もともとの決まり)。
  `wholeClip` からは `setDetail()` を1つも呼ばない
- **理由は、出す場所がすでにある** —— `lastWholeDetail()` →
  `prepareJob` → **支度の帯**。あちらは走っているあいだだけ出て、
  勝手に消える。**知らせを2か所から出さない**
- `npm run test:mp3` が、`wholeClip` の中に `FAILED` も `setDetail` も
  無いことを見張る(実際に戻して、赤くなることを確かめてある)

### **良い声に断られたら、標準の声に落とす。端末の声まで落とさない**

2026-09 実機・利用者の指摘。

> イギリスの男性、Jofra でスピーチを作成しようとしたら、
> google の女性の音声で生成されました。音声の入れ替えをしようとすると
> 添付の写真のようになります。すぐに改善してください

#### まず、その「Google の女性」は**こちらが作った音ではない**

声の当て方は正しかった。実際、作り直しの欄にも
**「イギリス … Jofra」**と出ている。出どころは別のところにある。

**`ELEVENLABS_API_KEY` が 401 で断られていた。** そのとき窓口は
**そのまま 502 を返して終わり**にしていたので、画面は**端末の声**に落ちる。
そして利用者の会社PC(Windows / Chrome)に入っている英語の声は
**Google の「通信を使う声」3つだけ**で、その既定が女性である
(このファイルの「端末に何が入っているかを、当て推量で決めない」)。
つまり**「Google の女性」は端末の声**であって、Google TTS ですらない。

**「選んだ声で鳴らない」を、声の当て方の問題だと決めつけない**
(2026-09 に一度書いた戒めが、そのまま当てはまった)。

#### ① 落ちる先を作る。**訛りも性別も、選んだとおりにする**

| | 何が鳴るか |
|---|---|
| 直す前 | **端末の声**(会社PC では Google の女性。日本語の声のことすらある) |
| いま | **標準の声**(Azure の `uk-male`)。**イギリスの男性のまま** |

- **鳴らないより、標準の声で鳴るほうがよい。** Voice ID を入れていない声で、
  もともとそうしている。**落ちる先が無かったのは、ここだけだった**
- **置き場所は「標準の段 × 代役の声」**(`<版>/standard/<代役>/<指紋>.mp3`)。
  **画面が標準の声を見に来る場所とまったく同じ**にする
  (`src/lib/audioClips.js` の `pathVoice`)。良い段の場所は**空のまま**なので、
  **鍵を直した日に、そこで初めて良い声が作られる**(`madeTier` の考え方)
- **もうあるなら作らない。** 落ちた先の場所も先に見に行く ——
  標準の声にも無料枠と待ち時間がある
- **作り直し(`force`)のときは落とさない。** あれは**良い声にするために
  課金して押すボタン**である。標準の声で作って「できました」と返すと、
  **成功と失敗が同じ見た目で終わる**
- **画面は、落ちたことを知らせる。** `askForClip` は `url` が返ると
  知らせを消していたので、そのままでは**音は鳴るのに、なぜ声が違うのかを
  知る道がどこにも無くなる**(`fellBack` のときは残す)

#### ② 断り方が、**直す場所を指していなかった**

画面に出ていたのはこれである。

    ElevenLabs の鍵が正しくありません。Supabase の Edge Functions →
    Secrets を確認してください(Azure は AZURE_SPEECH_KEY と
    AZURE_SPEECH_REGION、 Google は GOOGLE_TTS_API_KEY)。

**断ったのは ElevenLabs なのに、関係のない鍵を2つ挙げていた。**
しかも `ELEVENLABS_API_KEY` はどこにも出てこない。
正しい鍵を何度貼り直しても直らない。

**しかも、いちばん多い断られ方が全部この1文に化けていた。**
すぐ下に「**ElevenLabs はクレジットを使い切ると 401 / 402 で断る**」と
自分で書いてあるのに、**401 の枝のほうが先にあった。**
だから 402 の枝には**一度も来ていなかった。順が逆だった。**

##### **この回の本当の原因も、それだった**(2026-09 利用者の確認)

> ただ単に Elevenlabs の月額の上限に達してしまっただけのようです。

**クレジット切れである。** つまり画面に出ていた
「鍵が正しくありません」は**こちらの誤診**で、
利用者は**正しい鍵を疑わされていた。**

- **枝の順を間違えただけで、原因の切り分けをまるごと狂わせる。**
  この節は、そのための記録である
- **断り方を直すことは、機能を足すことと同じだけ重い。**
  こちらには ElevenLabs へ問い合わせる手段が無いので、
  **画面に出る1文が、そのまま調査の全部**になる

- **枝の順は「狭いものから」。** クレジット切れ・無料プランの停止・
  権限不足を**先に**見て、どれでもないときだけ「鍵が正しくありません」
- **その会社の鍵の名前だけを言う**(`SECRET_OF` 1か所)
- **向こうの言い分を、必ずそのまま添える**(`theirWords`)。
  ElevenLabs は 401 の中身に `detail.status` を入れてくる
  (`invalid_api_key` / `quota_exceeded` / `missing_permissions` /
  `detected_unusual_activity`)。**そこを捨てていた。**
  **こちらから ElevenLabs へ問い合わせる手段は無い**ので、
  **利用者の画面に出る1文だけが、唯一の手がかり**である

##### **鍵は、前後の空白を落としてから使う**

Secrets に貼るときに**改行や空白が1つ混じるだけ**で、
**正しい鍵でも 401 になる。** しかも画面には「鍵が正しくありません」と出るので、
**何度貼り直しても直らない**(貼るたびに同じ空白が付く)。
`envKey()` 1か所で落とす。**こちらで落とせるものは、こちらで落とす。**

##### **無料プランは、クラウドから呼ぶと止められることがある**

`detected_unusual_activity` / `Free Tier usage disabled`。
**鍵は正しいのに 401 で返る。** この窓口は Supabase のクラウドで動くので、
ここに当たりうる。ElevenLabs の画面では鳴るのに、アプリからは鳴らない。

**「鍵が正しくありません」と言ってはいけない。** 正しい鍵を何度も
貼り直させることになり、**永久に直らない**(有料プランに上げると通る)。

#### 検証は `npm run test:voice`。**中身を取り出して、素の node で走らせる**

断り方は**文字を探すだけでは足りない** —— 枝の順を入れ替えても
緑のままになる。窓口のソースの `ここから tts-error` … `ここまで tts-error` を
取り出して**実際に呼ぶ**(`mp3-fade` と同じ考え方)。

型注釈は**検証が知っている4つだけ**にする。足すと `new Function` が
落ちるので、**黙って素通りすることはない。**

実際に ①401 の枝を先に戻す ②鍵の名前を元に戻す ③言い分を1つの枝から落とす
④落ちる先をなくす ⑤`!force` を外す ⑥落ちた先の置き場所を良い段のフォルダにする
⑦画面が落ちたときも知らせを消す、の7つで赤くなることを確かめてある。

**版を書き写した見張りが、別の回で赤くなった。** `test:play` が
`FN_REV = '2026-09-07'` と**等号で**書いていたので、
版を進めるたびに関係のない検証が落ちる。
あそこが見たいのは「**時刻の控えが入った版より新しいか**」なので、
**以上で見る。** 版がそろっているかは `test:voice` が受け持つ。

#### **窓口の置き直しが要る**(`FN_REV` = `2026-09-11`)

置き直すまでは、**断り方も落ち方も1つも変わらない。**
画面が `NEED_FN_REV` と見比べて赤く知らせる。
**すでにある MP3 は作り直らない**(`CLIP_REV` は進めない)。

**良い声を用意できなかったときは、良い段の場所に置かない**(2026-09 実機)。
以前は頼まれた段のまま置いていたので、`ELEVENLABS_API_KEY` を入れる前に
一度でも鳴らした英文は、**標準の声の MP3 が良い段の場所に居座り、
あとから鍵を入れてもその英文だけ永久に標準の声のまま**だった。
`speak` は**実際に作った段**(`madeTier`)で置く。落ちているあいだは
画面が毎回窓口を呼ぶが、**作り直しはしない**ので課金は増えない。

**すでに置かれてしまった MP3 は、放っておいても直らない**(2026-09 実機)。

> Mika のひとつ目の発言だけ、明らかに ElevenLabs ではない酷い音声に
> なってしまいます。他でも起こりそうなので原因究明して改善してください。

**1つの発言だけがおかしい、という形で出る。** 直す前の窓口は、良い声で
作れなかったときも**良い段の場所に標準の声で置いていた。** 画面はその場所を
見に行き、**あればそれで終わり**にする(速いから)。だから窓口を直しても、
**一度でも鳴らした英文だけは永久に標準の声のまま**になる。
鍵を入れる前に Listen を1回押した発言 —— たいてい**1つめ** —— がこれになる。

- **これから作るものは、`madeTier` で直っている。**
  ただし**利用者が `speak` を配置し直すまでは増え続ける**
- **すでに置かれたものは、こちらから作り直させる。**
  `speak` に `force`(あっても上書き)、画面に
  **「読み上げ音声を作り直す」**(`remakeClips.js` + さがす画面のカード)
- **自動では作り直さない。** 作り直しはそのまま ElevenLabs への課金になる。
  押す前に**本数と、課金になること**を書く(**見えない費用は管理できない**)
- **2段で押させる**(1回目は「本当に作り直す」に変わる)。
  押し間違いがそのまま課金になる
- **同じ URL のまま中身だけが変わる。** 置くときに1年もつ指定を付けてあるので、
  そのままでは古い音が鳴る。**うしろに印(`?v=`)を足して別の URL にする**

  **その印は、端末に残さないと意味がない**(2026-09 実機)。
  はじめは `urlCache`(モジュールの中)にだけ置いていたので、
  **画面を読み込み直すと消えた。** 置き場所は元と同じままなので、
  次に開いたときは素の URL に戻り、

      Cache-Control: public, max-age=31536000, immutable

  で端末に残った**1年もちの古い MP3 がそのまま鳴る。**
  `immutable` は「1年のあいだ問い合わせすらするな」という意味なので、
  読み込み直しても取りに行かない。
  つまり**課金して作り直したものが、誰にも届いていなかった。**
  しかも**音は鳴る**ので、「作り直したのに直っていない」としか見えない。

  いまは `noteRemade()` が印を **localStorage(`eas.clipRemade`)** に残し、
  `clipUrl()` が**作り直した英文にだけ** `?v=` を付ける。
  - **付くのは作り直したものだけ。** ほかは素の URL のままなので、
    控えはこれまでどおり効く(通信も費用も増えない)
  - **新しいものから 4000 件**だけ残す(入れ物が膨らまないように)
  - `npm run test:voice` が、**印を残しているか・`clipUrl()` が
    それを見ているか**の両方を見張る。**残すだけで見なければ同じである**
    (`noteFnRev` を定義だけして誰も呼んでいなかったのと同じ落とし穴)
- **「もうあるので作りませんでした」で返ってきたら、失敗として扱う。**
  それは**窓口がまだ古い**(`force` を知らない)という意味である。
  成功と失敗を同じ見た目で終わらせない
- 作り直すのは**良い段の英文だけ。** 標準の段(ドリル・単語)は
  Google / Azure の無料枠で作られていて、**段を取り違えようがない**

#### **時刻表(`.json`)だけは、端末の控えを素通りする**(2026-09 実機)

2026-09 実機・利用者の指摘。**39回ぶんの直しが、ここで堰き止められていた。**

> 版も同じ数字が表示されるのに挙動だけが改善していない状態が維持されます。
> ここから直接 URL を踏むと改善されています。。。不思議です

##### まず測った。**同じ教材を、2つの入れ物で鳴らして数字を並べた**

| | Chrome | 控えの空な入れ物 |
|---|---|---|
| 音声 | 45.87 秒 | 45.87 秒(**同じ**) |
| **控え** | **44.32 秒** | **45.84 秒** |
| 合わせ方 | 音を測って合わせる(**覚えていた**継ぎ目 24 文) | 継ぎ目に配る **0.00 秒ずつ** |
| 3つめの文の頭 | **3.48** | **4.03** |

`控え` は `.json` の中身そのものから出している。**同じファイルなら同じ数字になる。**
44.32 と 45.84 は**別のファイル**である。3つめの文の頭が **0.55 秒**ずれており、
「文の終わりが早く切れる」「◀▶ が語の途中に落ちる」は、そのままこの数字だった。

##### なぜ古いものが残るのか。**そして、なぜ MP3 ではなく `.json` なのか**

窓口は `.mp3` にも `.json` にも
`Cache-Control: public, max-age=31536000, immutable` を付けている。
**1年のあいだ問い合わせすらするな**なので、あとから同じ場所へ上書きしても、
**すでに控えを持っている端末は取りに行かない。**
`remadeMark()` の `?v=` は**「作り直す」を押したブラウザにしかない。**

**そして、大きいものから捨てられる。** 数 MB の MP3 は端末に追い出されて
取り直されるのに、**数 KB の `.json` は居座る。** だから
**「新しい音 + 古い時刻表」**という、いちばん分かりにくい形になる。

##### 直し方 —— 時刻表だけ、必ず問い合わせる(`FRESH_JSON`)

`cache: 'no-cache'` は「控えがあっても、必ず向こうへ確かめる」。
変わっていなければ **304 が返るだけで、中身は流れない。**

- **MP3 は1年もちのまま。** 費用も通信も増えない
- **窓口の置き直しも SQL も、音声の作り直しも要らない**(画面だけ・0円)
- 取りに行くのは**1つの教材につき、その画面で1回だけ**
  (`timesCache` / `wholeCache` が控える)
- **`.json` を取りに行くのは2か所**(段落ごと `clipAlignment` /
  1本 `readWholeJson`)。**片方だけでは、片方の道が古いまま残る**

##### 覚えている継ぎ目には、**測り方の版**を持たせる(`SEAM_REV`)

19手めで「中身の**形**が変わったから鍵を分ける」(`eas.seams` → `eas.seams2`)と
決めたのに、**計算のしかたが変わったとき**には何もしていなかった。だから

    37・38・39手めが書き込んだ数字が、**コードを取り下げても端末に残り続ける。**

実際、利用者の Chrome には `覚えていた継ぎ目(24 文)` が残っていた。
