### 声ごとの音量は「全部の声の平均」にそろえる。**下げるだけ**

`src/lib/loudness.js`。**2026-09 に4度やり直している。経緯ごと残す。**

| | やり方 | 何が起きたか |
|---|---|---|
| ① | 決めた大きさ(0.15)に**全員を寄せる** | 小さい声が 2〜3 倍に持ち上がり、**息の音も破裂音も一緒に大きくなった** |
| ② | いちばん小さい声に合わせて下げ、**全体を 1.25 倍** | 上げるための面倒(頭打ち・割れの計算)が残った |
| ③ | 下げるだけ。**ただし Web Audio 経由** | **全部の声でバリバリ雑音**(下記。いちばん高くついた失敗) |
| ④ | **平均にそろえる。`<audio>` の `volume` だけ**(いま) | — |

#### **「平均に合わせる」と「最小に合わせる」は、同じ結果になる**

> コンプレッションやリミッターをかけるのではなく、ボリューム調整だけで、
> 全ての声の音量の平均値をとり、そこに全てを合わせてみてください(④の指定)

**先に算数の事実を押さえる。** 平均に合わせるには、平均より小さい声を
**上げる**必要がある。ところが `volume` は下げることしかできない。
そこで全体を「いちばん大きい倍率」で割って 1 以下に収めると、

    最終的な倍率 = いちばん小さい声 ÷ その声

**声どうしの比はまったく変わらない。** 変わるのは全体の音量だけである。
つまり②③④は**比としては同じもの**で、
**それでも差が残るなら、原因は「そろえ先」ではない。**

`gainFor()` は**指定どおり平均から出して、そのあと割っている。**
上げられるようになった日には、割るのをやめれば平均そのものに合う。

#### **RMS は「耳の感じる大きさ」ではない**

**④で実際に効いたのはこれである。**
波形をそのまま二乗した平均(素の RMS)は、**耳の感度を写していない。**
耳は低い音に鈍く、中〜高音に敏感なので、
**低音の多い声(男性に多い)は、数字上は大きいのにそう聞こえない。**
その声を下げすぎていた。

だから**測るときだけ**、放送の決まり(ITU-R BS.1770 の K特性)と同じ形に整える。

- 高い側を **+4dB**(1.5kHz からの棚)
- とても低いところを落とす(38Hz からの高域通過)

**Chromium で実測した効き**(同じ大きさの正弦波を通したときの変化)。

| 120Hz | 300Hz | 1000Hz | 1500Hz | 3000Hz |
|---|---|---|---|---|
| 105% | 101% | 108% | 126% | 154% |

**これは測るためだけの処理である。鳴らす音には一切かからない**(下記)。
**測り方を変えたら `MEASURE_REV` を必ず1つ進める。**
進めないと古い値と新しい値が混ざり、そろえ先がずれる。

#### **押し上げて帳尻を合わせない。そろえるのを壊す**

②③には「そろえ先の下限 0.05」があった。**これがそろえるのを壊していた。**
本当にいちばん小さい声が 0.04 だと、

    いちばん小さい声 … 0.05/0.04 は 1 を超えるので 1 倍のまま → 0.04
    ほかの声         … 0.05 まで下がる                       → 0.05

**いちばん小さい声だけが、いちばん小さいまま残る。**
人の声の平均は 0.03〜0.08 あたりなので、これは日常的に起きていた。
いまは**押し上げず、明らかに測り損ねたもの(0.01 未満)を外す。**
下げすぎの歯止めも 0.30 → **0.20**(3.3 倍ひらいた声が止まっていた)。

#### **音量を変えるために、音の通り道を変えない**

**③でいちばん高くついた失敗**(2026-09 実機)。

iPhone は `<audio>` の `volume` を無視する。そこでもそろえたくて、
`<audio>` を Web Audio(`MediaElementAudioSourceNode` → `GainNode`)に
つなぎ替えていた。すると、

> 小さな音量に合わせたはずなのに1回目の再生からバリバリ雑音だらけです。
> 1.25持ち上げると言う処理をやめたのに不思議です。
> ホワイトノイズが入るのであれば理解できるのですが。

**利用者の疑問が、そのまま答えだった。**
音を小さくする掛け算(0.4倍など)は**雑音を作れない。**
**原因は音量の値ではなく、通り道のほうにあった。**
Web Audio を通すと、`ctx.destination` の ±1.0 での切り落とし・
再生速度の処理・周波数の変換が**新しく**加わる。

**引き換えに iPhone ではそろわない。それでよい**
(そろわないことより、雑音が入ることのほうが悪い)。

**`npm run test:audio` が、`createMediaElementSource` /
`createGain` / `crossOrigin` を使っていないことを見張っている。**
**測る側で Web Audio を使うのは構わない**(`weighted()`)。
あれは鳴らす音に一切かからない。

#### **「プチッ」は、なだらかに上げ下げして消す**

2026-09 利用者の指摘。**2手かかっている。経緯ごと残す。**

> まだ会話の発言と発言の間にプチっと入りますね。入る時と入らない時が
> あります。…音の終わりをなだらかなフェードアウトにするとか、
> 何かできるはずです。ここは音に関することで、このアプリのキモです

**①の直し(差し替える前に `volume = 0`)では足りなかった。**
**0 に「跳ぶ」こと自体が段差**なので、鳴る場所を移しただけだった。
波形が途中の値のまま急に途切れれば、そこで「プチッ」と鳴る。

**②いまは、音量を時間をかけて上げ下げする**(`loudness.js` の `fadeGain`)。
動かすのは**もともと使っている `<audio>` の `volume` だけ**である
(**音の通り道は変えない** — ③でいちばん高くついた失敗)。

| | 値 | なぜ |
|---|---|---|
| 刻み | **10ms** | 画面の描き替え(約 16ms)では**粗すぎた**(下記) |
| 入り | **70ms** | 短すぎると1刻みめが持ち上がりすぎる(実測 50ms で 34%) |
| 終わり | **120ms** | ここが出どころ。長めに取る |
| 終わりの手前 | **25ms** | **ここで 0 に届かせる**(下記) |

**本物の `<audio>` で実測して、2つ直した。**

- **`requestAnimationFrame` では粗すぎた。** 1.5 秒の音を鳴らして測ると、
  鳴り終わりの最後のコマが「残り 41ms」で、**音量 0.205 のまま音が
  終わっていた**(半分の高さから急に切れていた)。`setInterval` で
  10ms ごとに動かすように変えた
- **10ms にしてもなお 0 に届かなかった**(最後の一刻みが「残り 33ms」で
  音量 0.11)。時計の揺らぎと、`ended` が長さぴったりでは来ないため。
  だから**終わりを 25ms 手前に見立てて**、そこで 0 に届かせる。
  **切っているのではない** — 最後まで鳴らしたうえで、そこだけ聞こえなくする

実測(音量 0.4・速さ 1.2 倍): 鳴り終わりは **10 段**で下がり、
1回の変わり幅は最大 **0.034**、音が終わった時点の音量は **0.024**
(直す前は **0.205**)。

**測るのは、鳴り終わってから**(2026-09)。測る側は Web Audio で MP3 を
ほどくので、**鳴っている最中に始めると音が一瞬途切れることがある。**
「入る時と入らない時がある」に合う — 測るのは**声ごとに1回だけ**なので、
その1本のときだけ起きる。**先に測らない**という決まりはそのままで、
変えたのは**いつ**だけである。

**`npm run test:audio` が曲線そのものを見張っている。**
こちらには音が聞こえないので、**耳の代わりに数字で見る。**
刻みの大きさ・終わりで 0 に届くか・入りの持ち上がり・`rAF` に頼って
いないか。実際に刻みを 8ms にして、赤くなることを確かめてある。

#### **差し替えの前に、止めて黙らせる**(①の直し。いまも残してある)

2026-09 利用者の指摘。

> 発言と発言の間、特に、ひとつの発言の終わりに小さく
> 「プチっ」というノイズが入ってます。

**`<audio>` は1つだけを使い回している**(iPhone の解錠をやり直さない
ため・CLAUDE.md)。次の発言に移るとき、**鳴り終わったままの `<audio>` に
新しい `src` を入れて `load()`** していた。これは
**再生の仕組みをいったん壊して作り直す操作**で、そのとき音の出口に
段差ができる。これが発言の切れ目で「プチッ」と鳴っていた。

**鳴らす音そのものは変えない。** することは2つだけ。

1. 先に **`pause()`**。鳴っている最中に作り直させない
2. **`volume` を 0 にしてから差し替える。** 段差ができても、
   音量が 0 なら**聞こえない。** 本当の音量は、読み込みが終わったあと
   `applyGain()` が入れ直す(**この順は変えない**)

**止めるとき(`stopClip`)も同じ。** 鳴っている途中で止めると、
そこに段差ができる。黙らせてから止める。

これは**すでに使っている `<audio>` の `volume`** であって `GainNode` では
ない。**通り道は1ミリも増えていない**(③の失敗をくり返さない)。

**`npm run test:audio` が順番を見張っている。** 入れ替わっても
`npm run lint` にも `npm run build` にも引っかからないためである
(実際に順を入れ替えて、赤くなることを確かめてある)。

#### 決まりごと

- **窓口では測れない。** Supabase の関数は CPU 2秒しか使えない。
  窓口側の音量指定も **ElevenLabs には無い**
- **1つの声につき1回だけ測る。** 端末に覚えるので、
  **その声の1本目だけはそろわない**
- **そろえ先は測るたびに動く。** より小さい声を測ると、ほかの声は次から下がる

**聞こえない。** ①の副作用も③の雑音も、見つけたのは利用者である。

### 会話の「間」は、内容から決める。話す人が替わるときだけ入れる

`src/lib/turnGap.js`(2026-09 利用者の指摘)。

> 女性の発話が不自然なくらい早いタイミングで食い気味に入ってきます。
> 本当の会話っぽい間をいれれないものでしょうか?特に内容によって。。。
> 間がある時と食い気味な時を内容によって自動でコントロールできませんか?

**原因は ElevenLabs ではなく、こちらのコードだった。**
`readAloudSequence()` は鳴り終わった**その瞬間**に次を始めていた(間 0 ミリ秒)。
コメントにも「間をあけない」と書いてあり、読み込みで黙るのを嫌ったためだが、
**v3 の音声は前後の無音がほとんど無い**ので、息継ぎも無しに次の人が話し出す。

- **決まりで書く。AI に頼まない**(`chunker.js` と同じ考え方)。
  要るのは記号と閉じた語のリストだけで、1発言ごとに課金する理由がない
- **上から順に見て、当てはまった時点で決める。足し合わせない。**
  足すと「相づちなのに疑問文だから長い」という説明できない値になる

  **2026-09、利用者の指定で全部を半分にした。**

  > 会話の発言と発言の間、記事の段落と段落の間の間が少し長いです。
  > 意味や感情の流れにより間を調整するにしても、
  > 今の半分近くにして良いと思います

  **比はそのままで、値だけを半分にする。** 相づちは短く、問われたら長く、
  という関係は残したいので、5つの値と「長さに応じて足す分」を
  **そろって半分**にした。**片方だけ縮めると、そこだけ不自然に詰まる。**

  | 何 | 間 |
  |---|---|
  | 前が `—` `...` で終わる(言い終わっていない) | **60ms** 相手が引き取る |
  | 次が相づち・即答で始まる(`Right` `Exactly` `Of course`) | **60ms** |
  | 前が付加疑問(`…, right?`)で終わる | **60ms** 同意を求めているだけ |
  | 次が言いよどみで始まる(`Well` `Let me` `Actually`) | **450ms** |
  | 前がふつうの疑問文 | **450ms +** 長さに応じて足す |
  | それ以外 | **190ms**(前が長ければ少し足す) |
  | 同じ人が続けて話す(記事の段落の切れ目) | **300ms**(息継ぎ) |

- **どの継ぎ目にも入れる**(2026-09 利用者の指定「記事でも同じ仕様にしてください」)。
  はじめは話す人が替わるときだけにしていたが、記事も段落と段落が詰まって聞こえる
- **同じ人が続けて話すときは、受け答えの規則を当てない**(`sameVoice`)。
  相づちも付加疑問も**相手がいる話**であって、一人で読んでいるところには無い。
  当てると「段落が `Right of way…` で始まったので食い気味」という、
  意味のない間になる。要るのは**息継ぎ**(600ms)で、
  問いかけで終わっていれば一拍足す
- **速さで割る。** 120% で聞いている人には、間も 120% で来る
- **速くした声には、そのぶんの余白を必ず足す**(`speedPadMs`・2026-09 利用者の指定)。

  > スピードを速くしたスピーカーはそのぶん前後の間が短くなります。
  > 速くした分と同じだけ前後に余白を入れてください。
  > そしてその余白は内容とは別に必ず入れるようにしてください。

  **再生速度は、音声の中の無音まで一緒に縮める。** 1.2 倍にすると、
  その1本の前後にもともと入っていた息継ぎも 1/1.2 になるので、
  **その声のまわりだけ詰まって聞こえる。**

  縮んだ割合 `(1 - 1/R)` を、基準(`PAD_BASE` = 1000ms)に対して足し戻す。
  1.2 倍なら**片側 167ms**、あいだは前後で **334ms** 増える。

  - **内容から決める間とは足し算にする。** 詰まっているのは**音声そのもの**で、
    話の中身とは関係がない。「相づちだから短く」と打ち消し合わせない
  - **前と後ろの両方に足す。** 発言のあいだの無音は1つなので、
    実際には「前の声のうしろ」と「次の声の前」が合わさって1つの間になる
  - **速くしていない声は 0。** ほかの声のリズムは1ミリも変えない
  - **利用者が選んだ速さでは割らない。** 縮めているのは声ごとの補正
    (`voiceRateOf`)だけで、全体の速さはどの声にも同じにかかる
  - 遅くした声(1 未満)も 0。**伸ばした声は、もともと間も伸びている**
- **間は止められるようにする。** まとめて待つと Stop を押しても
  最大 1.4 秒動かない。50ms ずつ刻んで、そのつど生きているかを見る
- **上限は 0.7 秒**(2026-09 に 1.4 秒から半分)。
  それ以上は「待たされている」に変わる
- **`so` を言いよどみに入れない。** ただのつなぎ言葉として文頭に立つことが多く、
  間があるとは限らない(`HEAD_WORDS` に副詞を入れないのと同じ理由)
- **付加疑問は、閉じたリストで見分ける。**「? で終わって、最後のコンマから先が
  短い」だけで判定すると、`Would you take the escrow, the holdback, or juice?` を
  付加疑問と取り違えて食い気味になる。`npm run test:gap` が見張っている

**この検証は、書いたときの思い込みを2つ捕まえている。**
`Understood` が即答の語だと気づかずに「前が長い」の枝を試そうとしたこと、
`It depends.` が言いよどみなので上限の枝を通っていなかったこと。
**間を触ったら、必ず通すこと。**

### 声が遅いときは、名簿の `rate` で直す。窓口では直せない

`voiceRateOf()`(`src/data/clipVoices.js`・2026-09 利用者の指定)。

> Jofra と Henry のスピードのデフォルトを 120% にしてください。

**ElevenLabs の v3 は `speed` の指定に対応していない。** だから窓口では直せない。
鳴らすときの **`playbackRate`** で補正する(`audioClips.js`)。

- **MP3 を作り直さない。** 費用は1円もかからず、**`CLIP_REV` も進めない**
- **利用者が選んだ速さに掛ける。** 120% で聞いている人には、
  その声だけがさらに 1.2 倍になる(ほかの声はそのまま)
- **上限を置く**(`MAX_RATE` = 2.5)。掛け算が重なると聞き取れなくなる
- **語の色は狂わない。** 印は `el.duration`(素の長さ)から作り、
  位置は `el.currentTime` で見ている。どちらも再生速度の影響を受けない
- 指定の無い声は 1 倍のまま。**全員を速くしない**(`npm run test:gap` が見張っている)

### Speech練習は種類の1つ。**自分の原稿を貼るのが基本**(0043)

2026-09 利用者の指定。

> 自分でスピーチなどを考えてもらったものをそのままコピペして指定する音声で
> text to speech をして、オーバーラッピングやシャドーイングのように
> 練習できるモードが欲しいです。基本的に「記事」と同じで大丈夫なのですが、
> タイトルを「Speech練習」などにしてほしいです。
> 内容は、自分で手入力が基本、業界とシチュエーションなどを選べば
> それに合わせた Speech を作ってくれるのも最高です。
> その際に「会社名」「自分の名前」「役職」「部署名」なども任意で指定すれば
> それに沿って Speech(モノローグ)を作成してくれる機能です

- **足したのは `materials.kind` の値1つだけ**(0043)。
  スピーチの本文は記事とまったく同じ形(段落が並び、話す人は1人)なので、
  **演習の種類は増やしていない。** `material_sections_type_check` も
  窓口も触っていない。**会議(0037)とまったく同じ考え方**である
- **中身は記事と同じ4つ**(本文6 + 内容の理解5 + ディスカッション5 + 語句8)。
  言われたとおりにしてある。要らない演習はチェックで外せるので、
  **こちらで勝手に減らさない**
- **`kind === 'reading'` と書かない。** 場面を出すかどうかは
  **`usesScene()`**(会話・会議・スピーチ)、貼れるかどうかは
  **`canPasteBody()`**、呼び名は **`bodyWord()`** 1か所

#### **窓口(`generate-material`)の置き直しは要らない**

記事とスピーチで変わるのは**書き方**だけで、出来上がりの形
(段落ごとに `prompt_en` / `prompt_ja`)は**まったく同じ**である。
形は `SECTION_FIELDS` が `strict: true` で保証しているので、
足すのは「どう書くか」の指示だけになる。

その指示は**すでにある「話題の指定」(`subject`)に画面が組み立てて渡す**
(`speechBrief()`・`src/lib/speechDraft.js`)。
**窓口の中に書いても画面から渡しても、AI に届く文字列は同じ**である。
だから `FN_REV` も進めていない。

- **必ず「記事ではない」と書く。** 窓口の指示は `article` のままなので、
  何も言わないと**記事の文体**で書かれる
- **1人が最後まで話しきる**とも書く(会話にさせない)
- **話し手の肩書きは「名乗らせる」のではなく、立場に効かせる。**
  毎段落で会社名を繰り返されると、練習にならない

#### 貼った原稿は、**AI に書き直させない**

`pastedParagraphs()`(`src/lib/speechDraft.js`)。

- **切り方は上から順に見て、当てはまった時点で決める**(`turnGap.js` と同じ)。
  ①空行 ②改行 ③どちらも無ければ文で切って ~45語ずつまとめる
- **③を「切らない」にしない。** 1本の長い塊のままだと
  「全部を一度に」しか練習できず、**段落ごとの Listen も、
  止めた場所からの再開も効かなくなる**
- **1語も落とさない。** 余りは直前の段落にくっつける
- 段落は **30 まで**(際限なく作らせない)
- 貼ったときは**本文だけを飛ばす。** 内容の理解・語句は、
  **貼った本文をそのまま渡して**作る —— AI が書いた本文のときと同じ道である。
  演習をぜんぶ外していれば、**AI は本文にも設問にも1回も呼ばれない**
- **訳(`prompt_ja`)は付かない。** 貼ったのは英文だけなので、
  **無いものをあるように見せない。** スラッシュリーディングの
  カタマリごとの訳は、これまでどおり作る

#### **窓口へ渡す直前で切る。貼るときの上限では足りなかった**(2026-09 実機・2手め)

> このspeech練習の教材、9段落目だけ最低な質の日本語英語の女性の音声に
> なっているので直してください。アメリカの指定した女性の声にしてください。

**下の直し(貼るときに 900 文字で切る)では足りなかった。** あれには
穴が3つある。

| 穴 | なぜ通り抜けるか |
|---|---|
| **AI が書いた本文** | `pastedParagraphs()` を通らない。長さを誰も見ていない |
| **すでに作った教材** | 段落は教材に保存されている。あとから直らない |
| 直す前に作った教材 | 同上 |

だから**窓口へ渡す直前**で切る(`speakChunks.js`)。
**ここが最後の関所**なので、どこから来た本文でも、作った日がいつでも、
**必ず収まる。**

- **収まっていれば1文字も動かさない**(ふつうの段落は今までどおり)
- 切れ目は**文の切れ目**。1文で超えるときだけ語の切れ目で分ける
- **画面に出す段落は1つも変えない。** 分けるのは「窓口へ何を渡すか」だけ。
  **番号(`index`)は元の段落のまま**なので、色も送りも今までどおり当たる
- **語の色は、かけらの頭(`at`)を足して送る。**
  足さないと**段落の先頭に戻って光る**
- **段落でくり返すときは、段落の頭へ戻す**(`pieceOf[part.index]`)。
  かけらだけを回すと、**段落の後ろ半分だけが延々と鳴る**
- **分けた段落では、止めた場所から再開しない。** 控えの秒は
  「その段落の音声の何秒め」で、分けたあとはどのかけらの秒か決められない。
  **当てずっぽうで飛ばすより、頭から鳴らすほうが説明できる**
- **かけらのあいだには段落の間を置かない**(90ms だけ)。
  分けたのはこちらの都合で、話のうえでは文と文の切れ目である
- **`speakChunks.js` に切り出してある。** `readAloud.js` は Supabase を
  引き連れていて**素の node で一度も走らせられない**
  (`playMark.js` / `mp3Join.js` と同じ考え方)

#### **窓口が断った理由を、一度も読んでいなかった**(2026-09 実機)

画面に出ていたのはこれだけだった。

    読み上げ音声を作れませんでした。端末の声で鳴らしています。
    Edge Function returned a non-2xx status code

**「non-2xx」は supabase-js の決まり文句であって、理由ではない。**
窓口はちゃんと `detail`(「英文が長すぎます(2,340 文字)」など)を
返している。ところが **2xx でないときは `data` が `null` になり、
中身は `error.context` の側に入る。** こちらは `data ?? {}` としか
書いていなかったので、**理由を一度も読めていなかった。**

- `errBody(error)` が `error.context.json()` を読む。
  **`ping` では同じことをしていたのに、本筋のほうでしていなかった**
- **副作用も1つ直した。** `body.fnRev` がいつも `undefined` になるので、
  **英文が1つ長すぎただけで「窓口が古い」と言い出していた。**
  版が付いてこないことを「古い」と読んでよいのは **`ping` だけ**である
  (`noteFnRev(rev, absentIsOld)`)

#### **端末の声に落ちたら、何段落目かを必ず言う**

**黙って落ちるのが、いちばん悪い。** iPhone の端末の声は
**日本語の声が英語を読む**ので、17 段落を聴き通すまで気づけない。
気づいたときには「最低な質の音声」として耳に入っている。

`noteFellBack('9 段落目の')` —— **場所を知っているのは呼ぶ側**
(`readAloud.js`)なので、そちらから言う。窓口が言った理由も添える。

#### **1段落が長すぎると、選んだ声で鳴らない**(2026-09 実機)

鳴らしています」と出ていた)。**端末の声は、選んだ声とは何の関係もない。**

- 切れ目は**必ず文の切れ目。** 文の途中では切らない

#### **頼んだだけで、確かめていなかった**(`voiceOrder.js`・2026-09 実機)

上に「**逆はしない。**名前から性別を読んで声を当て直すのは…**指名した声が
無視される**」と書いてある。**その決まりは破らない。**

### 話し方の特徴を最大限に活かす指定は、**全員に効く**

2026-09 利用者の指定。**2手かかっている。経緯ごと残す。**

| | 言われたこと | どうしたか |
|---|---|---|
| ① | 「この人(スコットランドの Ally)を音声として使用する際は、必ず元のアクセントを最大限生かしすようなコードを必ず使用してください」 | その行に `keep: true` を付け、**その声にだけ**添えた(いまの音を1つも変えないため) |
| ② | **「今回作った訛り、つまり話者の話し方の特徴を最大限反映させる指定は、全てのスピーカーに適用してくれますか?アメリカのスピーカーでもです」** | 印を外し、**名簿の全員**に添えた |

**訛りは、どの声にもある。** アメリカの声にも、その人の話し方の癖がある。
①で一部にだけ効かせたのは「いまの音を変えない」ためだったが、
利用者は**変わってよい**と判断した。**一部にだけ効かせる理由がない。**

**ElevenLabs は、もとの録音にどれだけ寄せるかを数字で指定できる。**
何も渡さないと ElevenLabs 側の既定で作られ、**その人らしさが薄まることがある。**

| 欄 | 何をするか | 値 | **v3 で効くか** |
|---|---|---|---|
| `similarity_boost` | もとの録音にどれだけ寄せるか | **1(最大)** | **効かない** |
| `stability` | 読み方をどれだけ揃えるか | **0.35**(低いほど感情が出る・2026-09 利用者の指定) | **効く** |
| `style` | 誇張の強さ | **0**(誇張は元の話し方から離れる) | 効く |
| `use_speaker_boost` | その話者らしさを強める | **true** | **効かない** |

#### **v3 が読むのは `stability` と `style` だけ。値をいじるならそこ**

2026-09 に ElevenLabs の説明で確かめた。

    Similarity is not available for the Eleven v3 model.
    Speaker Boost is not available for the Eleven v3 model.

**利用者が使う声はすべて v3** なので、`similarity_boost` と
`use_speaker_boost` は**渡っても捨てられる。**(`speed` も同じで、
だから声の速さは `playbackRate` で直している。)

**それでも4つとも渡している。** 渡す道が切れていないことを
`npm run test:voice` が見張っており、欄を減らすと見るものを失う。
v2 に落ちたときには効くし、捨てられるだけで害は無い。

**害があるのは「効くと思って値をいじること」のほうである。**
Ally で2度それをやり、**2度とも課金だけがかかった**(下記)。
`npm run test:voice` が、**名簿の `settings` に
`similarity_boost` / `use_speaker_boost` / `speed` を書いたら赤くする。**

- 値は **`ACCENT_KEEP`(`clipVoices.js`)1か所。** 判断は `voiceSettingsOf()`
- **`stability` は 0.4 → 0.35**(2026-09 利用者の指定「元の 0.45 もしくは
  0.35 くらいに戻してほしい。感情が豊かな方が良いです」)。
  **このリポジトリで 0.75 にしたことは一度も無い**(ずっと 0.4 だった。
  0.8 は Ally だけの実験値で、すでに消してある)。
  言われた 0.35〜0.45 の帯の**いちばん感情が出る側**に置いた。
  これ以上下げると、同じ英文でも鳴らすたびに読み方が変わりすぎる
- **名簿に無い id(代役)でも同じものを返す。** `undefined` を返すと
  そこだけ既定で作られ、**その1本だけ音が違う**ことになる
- **1人だけ違う値にしたくなったら**、その行に `settings` を足す
  (**書いた欄だけ**が差し替わる)。ふだんは要らない
- 窓口は名簿を持たないので、**中身だけ**を確かめる
  (知らない欄は捨て、0〜1 に丸める。範囲の外は 422 で断られる)
- **聞いて確かめていない。** こちらには音が聞こえないので、
  数字の意味から選んだ値である。物足りなければ書き換えて作り直す
- **値を変えても、自動では作り直らない**(置き場所は英文と声で決まる)。
  **すでにある MP3 は前の音のまま。** さがす画面の
  「読み上げ音声を作り直す」を押した教材だけが変わる。
  **`CLIP_REV` は進めない**(進めると全部が作り直し = 再課金)
- 効くのは **ElevenLabs の段だけ。** 標準の段(ドリル・単語)は
  Google / Azure なので、この指定は届かない
- `npm run test:voice` が、**渡す道(画面 → 窓口 → ElevenLabs)が
  1本も切れていないこと**を確かめる。
  **切れても音は鳴る**(既定で作られる)ので、**気づけない**

- 画面は `NEED_FN_REV`(`audioClips.js`)と見比べ、古ければ
  **すでにある知らせの道**(`onClipTrouble`)でトレーナーに伝える。
  **ゲストには出さない**(仕組みの内側の話)
- **版を返さない = 版を付ける前のもの**なので「古い」と読む
- **窓口に手を入れたら、`FN_REV` を必ず1つ進める**
- 「検証を頼む前に、版が分かるようにする」(共通ルール)と同じ考え方である。
  **これが無いあいだ、こちらは何日でも見当違いの値をいじり続けられる**

###### 知らせを「ついでに」出す形にしない。**訊きに行く**

2026-09 実機・利用者の指摘。

> トレーナーの画面に赤い知らせが出なくなってます

**版の見比べは `askForClip()` の中にしか無かった。** ところがあれが
呼ばれるのは、**その英文の MP3 がまだ無いとき**だけである
(`clipUrl()` は置き場所を計算して返すだけで、窓口を呼ばない)。

つまり**すでに音声のある教材を開いて聴くかぎり、窓口は一度も呼ばれず、
古いままでも何も出ない。** 新しい英文を作った日にだけ出る、
当てにならない知らせだった。**「『無ければ素通り』する形の検証を
書かない」を、検証ではなく知らせの側で破っていた。**

- **`checkClipGateway()` が、開いたときに1度だけ訊きに行く**
  (`audioClips.js`)。窓口は **`ping`** に版だけを返す。
  **音声は作らないので1円もかからない**
- **古い窓口は `ping` を知らない**ので 400 を返す。版も付いてこないので
  「古い」と読まれる。**それが正しい答えである**
- **失敗しても何もしない。** `stopped` を立てず、`detail` も窓口の言葉で
  書き換えない。ここは版を訊くだけの道で、読み上げを止めてよい場所ではない
- **トレーナー・管理者のときだけ呼ぶ**(知らせを出す相手が他にいない)
- `npm run test:voice` が、**呼んでいる形まで**見張る
  (定義だけあって誰も呼ばなければ、いまと同じことになる)

**知らせの文言を、画面に決め打ちしない**(2026-09 実機・同じ回)。
`App.jsx` に「**読み上げ音声を作れませんでした。端末の声で鳴らしています。**」
と固定していたので、**版が古いことを伝えるだけの知らせにもその文が付いた。**
音声を作りに行ってすらいないのに「作れませんでした」と出る。
**起きたことは、呼んだ側がいちばんよく知っている。**
文は `audioClips.js` の `setDetail()` を呼ぶところで書き、
画面は受け取った1文をそのまま出す。

##### 「発言の終わりのプチっ」は、**切り落としでは直せなかった**(2026-09・取り下げ)

2026-09 実機・利用者の指摘から始まり、**利用者の判断で取り下げた。経緯ごと残す。**

> さーっという音はずっと入っています。
> そして発言の終わりでほぼ必ずプチっという音が入ります。

鳴り終わりは `fadeGain` でなだらかに下げてある。**それでも残った。**
理由は単純で、**あれは `<audio>` の `volume` を動かすもの**であり、
**iPhone は `volume` を無視する**(この同じ CLAUDE.md に書いてある)。
つまり**利用者の iPhone では、なだらかにする直しが1ミリも効いていない。**

そこで**音量ではなく、鳴らす場所そのものを短くする**道を試した
(名簿の行に `trimMs`、鳴らす側は `pause()`、落とす MP3 は `trimTail`)。

| 切った長さ | 利用者の耳で何が起きたか |
|---|---|
| 150ms | 「プチっの発生は大幅に減りましたが、まだ散見されます」 |
| **200ms** | **「発言の最後が消えました。ダメです」** |

**消えるところまで切ると、語尾の子音が先に無くなる。**
MP3 のフレーム1枚は 44.1kHz で **26.12ms** で、150 → 200ms は
たった2枚ぶんである。**その2枚のあいだに、実用の境目があった。**
**v3 の音声は前後の無音がほとんど無い**(会話の「間」を自前で入れているのは
そのためである)ので、100ms を超えたあたりからすでに実音声を削っている。

> 200では発言の最後が消えました。ダメです。150でさえやめて
> フェードアウトなどの仕様はやめて、元々音の悪い音声は選ばない
> ことにしました。(2026-09 利用者の判断)

**だから仕組みごと取り下げた**(`voiceTrimMs` / `trimTail` / 鳴らす側の早止め)。
**方針は「元々音の悪い音声は選ばない」である。**

- **切り落としを、もう一度持ち込まない。** 1枚ずつ動かして拾える範囲に
  答えは無く、**消える手前では残り、消える長さでは語尾が欠ける**
- **音が悪い声は、名簿で外す**(`retired: true`)か、そもそも選ばない。
  こちらには**音が聞こえない**ので、判断できるのは利用者だけである
- `fadeGain`(`loudness.js`)は**そのまま残す**(2026-09 利用者の確認)。
  あれは iPhone 以外では効いており、しかも**音を1ミリも切らない。**
  「フェードアウトなどの仕様はやめて」は**切り落としのこと**であって、
  なだらかに下げるほうではない。**取り違えて消さない**

###### **iPhone では、音量を使う直しが2つとも効いていない**

取り下げても、この事実は変わらない。**iPhone は `<audio>` の `volume` を
無視する**ので、「プチっ」対策として入れたものは**どちらも死んでいる。**

| 直し | 何をしていたか | iPhone では |
|---|---|---|
| `fadeGain`(なだらかに下げる) | `volume` を 10ms ごとに動かす | **効かない** |
| 差し替えの前に黙らせる | `volume = 0` にしてから `src` を入れ替える | **効かない** |

**残っていた手は「鳴らす場所そのものを短くする」だけ**で、それが上のとおり
使えないと分かった。**つまり iPhone で「プチっ」を消す手は、いま無い。**
だから**入り口(どの声を採るか)で決める。**

**Web Audio に通して音量を効かせようとしない**(いちばん高くついた失敗・上記)。
そろわないことより、雑音が入ることのほうが悪い。

**→ ここは 2026-09 に解決した(次の節)。** 直したのは**鳴らすとき**ではなく、
**置くとき**である。だから iPhone でも効く。

#### 「プチっ」の正体は、**ElevenLabs の MP3 が音の途中で終わっていること**

2026-09 利用者の指定。**やっと実測できた。経緯ごと残す。**

> またアツゲン(発言)の後ろにプチッと入ります。
> まるでトランシーバーで通信しているようです。本気で解決策を考えてください

##### まず測った。**推測でいじらない**

利用者に**落とした MP3 をそのまま送ってもらい**、Chromium の
`decodeAudioData` で波形にほどいて、**発言の終わりが「いくつ」で
終わっているか**を1つずつ数えた(14発言・50秒)。

- **14発言のうち6発言が、音のある途中でぶつりと 0 に落ちていた。**
  1点(1/44100 秒)で落ちる。いちばん大きいもので **0.11(−19dBFS)**
- **落ちたところから、その音声が終わるまでは 11〜25ms しかない。**
  MP3 のフレーム1枚(26ms)より短い。つまり
  **音が鳴っている最中に、その音声ファイルそのものが終わっている**
- 話す人を**声の高さで見分けた**(男 98〜120Hz / 女 184〜215Hz)。
  **利用者は「Adam だけ」と見ていたが、数字の上では両方で起きていた**
  (いちばん大きい段差は、むしろ女性の発言だった)。
  **聞こえたとおりに書かず、測ったとおりに書く**

##### だから「切り落とし」では直らなかった

プチッの手前まで削るには**実音声を削るしかない。** 実際 150ms では残り、
200ms では「発言の最後が消えました。ダメです」だった。
**削る場所に答えは無い**(上の節)。
`fadeGain` も、iPhone が `volume` を無視するので届いていない。

##### 直したのは「鳴らすとき」ではなく「**置くとき**」

`speak`(窓口)が、Storage に置く**前に1回だけ**、
**終わりの約 65ms を段々小さくする**(`fadeMp3Tail`)。

MP3 は「グラニュール」(約13ms)ごとに、
**その塊全体の大きさを表す `global_gain` という 8 ビットの数**を持つ。
1 減らすと 1.5dB 小さくなる(mp3gain と同じ考え方)。
**ここだけを書き換える。**

- **音のデータには一切触れていない。**「作り直さない」という指定と矛盾しない
- **1バイトも増えない。** 長さも並びもそのまま
- **1ミリ秒も削っていない。** 小さくするだけなので語尾は消えない
- **グラニュールどうしは重ねて復号される**ので、下げ方そのものが段差にならない
- **音の通り道を1ミリも変えていない**(Web Audio の失敗をくり返さない)
- **iPhone でも効く**(`volume` を使っていない)
- **1本にまとめて落とす音声も同じように直る**(直した MP3 をつなぐため)

**実測(利用者が落とした、その音声で)。** いちばん大きな段差
**0.1117(−19.0dBFS)→ 0.0127(−37.9dBFS)。** 大きかった3つは
−47.8 / −49.6 / −43.9dBFS まで下がり、終わりの音量はほとんど変わっていない。

- 下げ方は **`FADE_RAMP`(`speak/index.ts`)1か所。**
  終わりから遡って 66 → 42 → 24 → 12 → 5 dB
- **効くのは ElevenLabs のときだけ**(利用者が言ったのは発言の話である)。
  Azure / Google は 24kHz(MPEG2)なので `fadeMp3Tail` は何もしない。
  CRC 付き・ステレオも触らない(**直せないなら、何もしない**)
- **`npm run test:mp3` が見張っている。** 窓口のソースから
  **印(`ここから mp3-fade`)のあいだを取り出して**素の node で走らせ、
  長さ・フレームの並び・下げたグラニュールの数と値・
  side info の外を書き換えていないこと・窓口が**実際に呼んでいる**ことを見る。
  実際に `body: audio` に戻して、赤くなることを確かめてある
- **窓口の置き直しが要る**(`FN_REV` = `2026-09-05b`)。
  置き直すまでは何も変わらない
- **すでにある MP3 は直らない。** 置き場所に「下げたかどうか」は入っていない
  (`<版>/<段>/<声の id>/<指紋>.mp3`)。さがす画面の
  **「読み上げ音声を作り直す」**を押した教材だけが直る。
  **`CLIP_REV` は進めない**(進めると全部が作り直し = 再課金)

#### そもそも、**つながない**(本文は1本で作る・2026-09 利用者の指定)

> 会話は、話者ごとに個別MP3を生成してアプリ側で連結せず、ElevenLabs の
> Text to Dialogue API を使い、複数の voice_id を指定して会話全体を
> 1本の音声として生成する。可能なら with-timestamps を使用し、
> 各発話の開始・終了時刻を保存する。

**ほかの作り手も同じところで詰まっていた。** 出ている答えは3つで、
①継ぎ目にフェード ②つないで丸ごと再エンコード ③**そもそもつながない。**
①は上の `fadeMp3Tail`、②は「作り直さない」という指定に反する。
**③がいちばん強い —— 継ぎ目を上手に隠すのではなく、継ぎ目を無くす。**

| どこ | 何をするか |
|---|---|
| 会話・会議 | `/v1/text-to-dialogue/with-timestamps`(声を並べて渡す) |
| 記事 | `/v1/text-to-speech/{id}/with-timestamps`(段落を空行でつないで1回) |

**確かめた決まりごと**(2026-09 に ElevenLabs の説明で確認)。

- Text to Dialogue は **v3 専用**。声は **10人まで**
- `settings` は **`stability` だけ**を受け取る(声ごとの指定は渡せない)
- **全ターン合わせて 2,000 文字**が目安。記事(1人)は 2,800 文字まで
- 時刻は `alignment` に**文字ごと**で返る

##### 区切りの計算は `wholeAudio.js` 1か所。**窓口でやらない**

窓口は `alignment` を**そのまま** `.json` に控えるだけにする。
「何番目が何秒から何秒か」は画面側(`src/lib/wholeAudio.js`)が出す。

- 窓口に置くと、**直したくなったときに置き直しが要る**
- しかも**素の node で一度も確かめられない**
  (`playMark.js` / `mp3Join.js` と同じ考え方)
- 置き場所は `<版>/premium/whole/<声と英文の指紋>.mp3`(と `.json`)。
  **SQL は要らない**(表を持たない)

**区切りは「空白でない文字の数」で当てる。** 向こうが改行や空白を
足しても揺るがない。**数が合わなければ、何も返さない** ——
当てずっぽうで区切ると**別の発言の場所を指す**(`sentencePair.js` と同じ)。

##### 発行したら、**裏で支度しておく**(`prepareJob.js`・2026-09 利用者の指定)

> 初めて再生するときの待ち時間が３０秒近くあり、これは、教材が完成した際に
> バックグランドで準備する仕様にできないでしょうか？
> 単語の意味についても同様の仕様にできないでしょうか？

**1本にまとめたぶん、初回は 50 秒ぶんをその場で作ることになった。**
押した人がそのあいだ待つ。語の意味も、開いてから 10 語ずつ引いていた。

**だから、発行した瞬間に用意する。** トレーナーは発行のあと次の教材へ
移ることが多いので、**その時間を支度に使う。**

| いつ | 何を |
|---|---|
| **発行したとき**(`MaterialForm`) | 本文の音声(1本)+ 語の意味 |
| **「セッションで使う」を押したとき**(`TrainerMaterials`) | 同じもの。**前に作った教材のため** |

- **費用は増えない。** どのみち初回に作られるものを、早めに作るだけ。
  ただし**一度も使わなかった教材のぶんは無駄になる**
  (教材は使い回す前提なので、ふつうは使われる)
- **教材の生成とは別の枠。** 支度のせいで「次の教材を作る」が
  始められないのでは本末転倒である(`generateJob.js` は1枠しかない)
- **止まる条件を持たせる**(CLAUDE.md)。1度に1つ・**やり直さない**・
  **同じ教材は二度やらない**。失敗しても、初めて押したときに作られる
- 進み具合は **`JobBar` に出す**(作っている帯と同じ場所・**同時には出さない**)
- **過去に作った教材も、裏で順に支度する**(2026-09 利用者の指定
  「過去に作成したものも常にバックグラウンドで再生準備を進められないでしょうか？」)。
  教材の一覧を開いたら、そこに出ているものを**まるごと順番待ちに積む**
  (`startPrepareAll`)。
  - **1本ずつしか走らせない。** まとめて投げると、いくらかかったのか
    分からないうちに終わる(**見えない費用は管理できない**)
  - **あと何本かを、いつも帯に出す。**「やめる」はその帯に置き、
    押したら**順番待ちも空にする**(1本だけ止めて次が始まったら意味がない)
  - **切り替えを左のメニューの下に置く**(`eas.prepareAll`・既定は自動)
  - **すでに音声がある教材は、問い合わせだけで終わる**(1円もかからない)
  - 順番待ちは **50 本まで。** 積みきれなかったぶんは、次に開いたときに続きから
- **`npm run test:mp3` が、呼んでいる形まで見る。**
  定義だけあって誰も呼ばなければ、何も起きない
  (`noteFnRev` を定義だけして呼んでいなかったのと同じ落とし穴)

##### **1本に統一した。切り替えは廃止**(2026-09 利用者の指定)

> かなり良くなりました。この仕様でいきましょう。
> １本でというのと、発言毎に分けれる形でしばらく置いておいてください。

- **左のメニューの切り替えを外した**(`wholeOn` / `setWholeOn` / `WHOLE_KEY` ごと)。

  1本を作れないときに**黙って落ちる受け皿**である(鍵が無い・文字数が
  多すぎる・名簿に無い声が混じっている・時刻が本文と合わない)。

###### 段落ごとの Listen は、そのあと廃止した

利用者の確認は、はじめ「**段落ごとのボタンはもちろん残します**」だった。
**2026-09 に「全てのデバイスで廃止」へ改まった**(下の節)。
以下は**そのときの経緯**である。区間で鳴らす仕組みそのものは、
**内容の理解・語句・単語・フレーズ**の Listen で今も使っている。

**「廃止」したのは、段落ごとに別の MP3 を作ること**であって、
ボタンではない。時刻(`alignment`)を控えてあるので、
**その1本の 12.4 秒から 18.9 秒まで**を鳴らせば同じことができる。

| | 前 | いま |
|---|---|---|
| 通しの再生 | 1本 | 同じ |
| **段落ごとの Listen** | **別の MP3 を作る(別に課金)** | **同じ1本の、その区間だけ(0円)** |
| 音 | 段落ごとだけ継ぎ目が出る | **どこを押しても同じ音** |

- 区間を出すのは **`wholeSliceOf()`(`audioPlaylist.js`)1か所。**
  **番号は `audioItemsOf()` で数える** —— 描くときの番号(空の項目も
  混じる)を渡すと、**別の発言が鳴る**
- **本文でなければ `null` を返す**(`isPassageSection` で見る)。
  呼ぶ側に「本文のときだけ渡してください」と約束させると、必ず破られる
- 鳴らすのは `readAloud({ whole })`。**`rangeOf` の終わりで止める**(`stopAt`)
- **渡す画面は4つ**(レッスン表示 / 教材の中身 / 集中モード / 6Steps の③⑤)。
  1つでも抜けると**そこだけ別の MP3 を作って二度課金する**が、
  **音は鳴る**ので気づけない。`npm run test:mp3` が名指しで数えている
  (実際に1つ外して、赤くなることを確かめてある)
- **文ごとの Listen は、これまでどおり別に作る**(ディクテーション・
  Quick Response・スラッシュリーディング)。1本の中の区間は
  **段落 / 発言の単位**でしか控えていない。**言われた場所だけを直す**

##### **今までの形にも戻せる**(利用者の指定)

> 今までの仕様にも戻せるようにしながら一度試してみたいです。

左のメニューの下に「**本文の読み上げ … 1本 / 発言ごと**」を置いた
(`eas.wholeAudio`・既定は「1本」)。トレーナーと管理者にだけ出す。

- **1本を作れなかったときも、黙って今までの形に落ちる**
  (鍵が無い・文字数が多すぎる・v2 の声が混じっている・時刻が合わない)。
  **行き止まりを作らない**
- 効くのは**良い段(記事・会話・会議の本文)の通し再生**だけ。
  ドリル・単語・段落ごとの Listen はこれまでどおり

##### 1本にすると、効かなくなるものがある

| 何 | どうなるか |

(`use: 'narration'`)。`both` のままにすると会話で選べてしまい、

##### 検証(`npm run test:mp3` ⑨)

##### 検証は「値が 1 か」で見ない。**ずれの出どころ**で見る

#### 長さの札(Xing / Info / VBRI)は、**つなぐと嘘になる**

2026-09 実機・利用者の指摘。

> 実際は2分29秒の音声が、プレーヤーでは22秒の音声として表示されます。
> しかし、再生すると、22秒のところで再生バーなどは終了するのに
> 音声だけは続く、時間の表示も22秒で止まったまま再生だけは続く

**22秒は、1つめの発言の長さである。**

**MP3 には、長さがどこにも書かれていない。** だから多くの作り手は、
**いちばん先頭に音の出ないフレームを1枚置き、その中に
「全部で何枚あるか」を書く**(`Xing` / `Info` / `VBRI`)。
再生機はそれを読んで再生バーの長さを決める。

つないだあとも**1本目のその札がそのまま先頭に残っていた。**
だから「1本目の長さ = 全体の長さ」と表示され、そこで
バーも時計も止まる。**音は最後まで鳴る**(フレームは並んでいる)ので、
**壊れているようには見えず、時間だけがおかしい。**

- **全部落とす。** 先頭のものも、中ほどに来るものも
  (中ほどに残ると、そこで数え直す再生機を混乱させる)
- **正しい札を、こちらで1枚だけ作って先頭に置く**(`vbrTagFrame`)。
  長さは「**フレームの枚数 × 1枚ぶんの時間**」で決まるので、
  枚数さえ正しければ再生機は正しい長さを出せる
- **間(ま)の無音も枚数に入れる。** 入れ忘れると、そのぶん短く出る
- **数え損ねたら、札を付けない**(`countFrames` が `null`)。
  **間違った長さを書くくらいなら、書かないほうがよい**
  (そのときは再生機がファイルの大きさから見積もる)
- 名前は、ビットレートが最後まで同じなら **`Info`**、違えば `Xing`
- **本編は1バイトも書き換えていない**(利用者の指定「作り直さない」)。
  足したのは先頭の1枚だけである
- **すでに落とした MP3 は直らない。** もう一度落とし直す

**`npm run test:mp3` が見張っている。** こちらには音も再生機も無いので、
**札に書いた枚数と、実際に並んでいる枚数を数えて突き合わせる。**
実際に「元の札を落とさない」形へ戻して、赤くなることを確かめてある。

実測(1本目 22秒・14発言・間 190ms): 札が言う長さ **2分41秒** =
実際に並んでいる長さ。直す前はここが **22秒**だった。

### 音楽の 0% は「小さくする」ではなく「**止める**」(第5.257節)

2026-09-25 実機・利用者の指摘。

> 設定から音楽の音量を0%にしても音楽が消えません。
> 音量設定はそのまましっかり機能するようにし、
> それに加えて音楽on / offの設定も追加してください。
> on にしたら曲が選べるプルダインも出るように

#### なぜ 0% で消えなかったのか

つまみを 0 にすると `setBgmVolume(0)` が `<audio>` の `volume` を 0 にする
—— **`volume` を受け付ける端末なら、それで消える。**
ところが **iOS は `<audio>` の `volume` を黙って無視する**(CLAUDE.md に
何度も出てくる)。入れても 1 のままで、**そのまま鳴り続ける。**

しかも、その端末かどうかを見分けるはずの `volumeWorks()` が

    const probe = new Audio()     // ← **`src` が無い**
    probe.volume = 0.5
    works = Math.abs(Number(probe.volume) - 0.5) < 0.01

と、**鳴らす前の空の箱**で試していた。あれは iOS でも素直に 0.5 を返す。
つまり **「効きます」と答えてつまみを出しておきながら、
実際に曲を鳴らすと無視される** —— いちばん質の悪い形である。

**「効くかどうかを1回で見分ける」という思いつきが、半分しか当たっていなかった。**
`src` を入れて鳴らしてから試せば正しく分かるが、それは
**「鳴らさないと分からない」**ということで、設定の画面でやることではない。

#### だから、音量に頼らずに止める

**止めるのは、どの端末でも効く。** `pause()` を無視する端末は無い。

- **0 と「小さい」を取り違えない**(CLAUDE.md)。
  0% は「うんと小さくする」ではなく「**鳴らさない**」という指定である
- **塞ぐのは3か所。1つでも抜けると、そこだけ鳴り続ける**
  (しかも音は出るので、聴いた人にしか分からない)

| どこ | 何をする |
|---|---|
| `setBgmVolume()` | 0 になったら、いま鳴っている曲を `pause()` する |
| `play()` | 0 のあいだは、**鳴らし始めない**(次の曲へ移っても) |
| `setBgmVolume()` | 0 から**上げ直したら、また鳴らす**(行き止まりを作らない) |

2つめが要るのは、曲が終わると `ended` → `next()` → `play()` と
**ひとりでに次へ進む**ためである。止めるだけだと、次の曲でまた鳴り出す。

#### オン / オフ は、**新しい鍵を作らない**

「どこで流すか」(`BGM_PLACES`)の**いちばん上が、すでに「流さない」**
だった。別の鍵を足すと、**片方を切ったのにもう片方で鳴る** ——
鳴らすかどうかを見ているのは `bgmPlaysIn()` の側なので、
新しい鍵は**誰にも読まれないまま画面にだけ残る。**

    bgmOn()      … loadBgmPlace() !== 'off'
    setBgmOn(on) … 切るときは、いまの場所を控えてから 'off' にする

**切る前の場所を覚えておく**(`eas.bgmPlaceBack`)。覚えないと、
戻したときに既定(「聞き流しのときだけ」)へ落ちて、
**「ずっと」を選んでいた人の指定が黙って変わる。**
**オフを2回押しても、控えは `off` に上書きしない** ——
上書きすると、次にオンにしたとき**どこへも戻れなくなる。**

#### 設定の画面 —— 「音楽」という名前を2つ置かない

|  | |
|---|---|
| **音楽** | `[オン][オフ]` |
| **曲** | `[ぜんぶ(順不同) ▾]` … **オンのとき・2曲以上あるときだけ** |
| **音楽の大きさ** | `[───●──] 40%` … **オンのとき・音量が効く端末だけ** |

- つまみのほうを **「音楽の大きさ」**と呼び分けた。すぐ上がオン / オフ
  なので、**どちらも「音楽」だと、どちらが何なのか読めない**
  (CLAUDE.md「違うものに同じ名前を付けない」)
- **オフのあいだは、下の2つを出さない**(効かない操作を見せない)
- **曲が1つしか無いときは、えらぶ欄そのものを出さない**(`bgmChoices`)——
  「ぜんぶ」とその1曲は同じもので、押しても何も変わらない
- 曲の数え方は**聞き流しとまったく同じ** `bgmChoices()` / `bgmPickOf()` を通す。
  自前で数えると、**消された曲を握ったまま**になる

**オフにしたら、いま鳴っているものもその場で止める**(`stopBgm()`)。
次に開いたときから効く形にすると、利用者には「切れていない」としか見えない。

`else if` で止まるためで、**だから B が要る** ——
1回の壊し方では、`if / else if` の先のほうしか確かめられない。


### 日本語(Shohei)が英語より大きい —— **窓口で小さく作る**(第5.274節)

2026-09-26 実機・利用者の指摘。

> 日本語と英語のボリュームも調整したいです。
> 今は日本語の shohei の声が英語の声に対して比較的大きいです。

#### なぜ、そろっていなかったか

声ごとの音量をそろえる仕組みは**前からある**(`src/lib/loudness.js`)。
ところがそれは **`<audio>` の `volume` を動かす**もので、

    iOS は `<audio>` の `volume` を黙って無視する

**利用者の端末(iPhone)では、1ミリも効いていなかった。**
だから Shohei と英語の声の差が、そのまま耳に届いていた。
同じ理由で、設定の「英語の音声」「音楽の大きさ」のつまみも
**iPhone では効いていない**(`mixVolume.js` にそう書いてある)。

#### 取らなかった道 ——**音の通り道を変える**

Web Audio(`GainNode`)に通せば iPhone でも効く。
しかし**2026-09 にそれをやって「全部の声でバリバリ雑音」になり、戻した道**
である(`loudness.js` / `mixVolume.js` に経緯が残っている)。
**いちばん高くついた失敗をくり返さない。**

#### 取った道 ——**置くときに、小さくしておく**

**訊いたうえでの答え**である(利用者の選択)。

`fadeMp3Tail`(発言の終わりのプチッを消すもの)と**まったく同じ道具**を使う。
MP3 は「グラニュール」(約13ms)ごとに `global_gain` という 8 ビットの数を持ち、
**1 減らすと 1.5dB 小さくなる**(mp3gain と同じ考え方)。

- **音は1ビットも作り直していない。** ElevenLabs を呼び直さない = **0円**
- **1バイトも増えない。1ミリ秒も削らない**
- **どの端末でも効く**(`volume` を使っていないので iPhone でも)
- 触れない形(MPEG2 = Azure / Google の 24kHz)には**何もしない**

#### すでに置いてある日本語の音声は、**大きいまま**(利用者の判断)

置き場所は(版・段・声の id・英文の指紋)で決まる。
音を小さくしても**指紋は変わらない**ので、
すでにある音声はそのまま使われる。**これから作るものから**小さくなる。
作り直せば全部そろうが、**1本ずつ課金される**ので、しない。

#### 下げ幅(4.5dB)は、**最初の置き場所**である

こちらからは ElevenLabs を呼べないので、**実際の大きさを測れない。**
合わなければ `JA_CUT_DB` の数を1つ直す(1.5dB 刻みに丸まる)。
**測っていないことを、測ったように書かない**(CLAUDE.md)。

#### 見張り(`npm run test:mp3`)

窓口のコードを**ソースから取り出して、実際に走らせる**
(`fadeMp3Tail` と同じやり方。**書き写さない**)。

| 見るもの |
|---|
| ぜんぶのグラニュールが、同じだけ下がっている(終わりだけの `fade` と違う) |
| 書き換えたのは side info の中だけ。**長さも変わらない** |
| MPEG2(24kHz)には何もしない |
| 0 や負を渡したら何もしない |
| **下げ切っても 0 で止まる**(音が裏返らない) |
| 窓口が、**日本語のときだけ**呼んでいる |
| 声の id が、窓口(`JA_VOICE_ID`)と画面(`JA_VOICE`)で同じ |

赤チェックは4本とも赤。
