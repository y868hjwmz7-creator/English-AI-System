# 共通ルール(全プロジェクト)

## 言語と伝え方

**利用者への返答・コミットメッセージ・コード内のコメント・ドキュメントは、すべて日本語で書く。**

利用者はプログラミングの初学者である。

- 専門用語には短い言い換えを添える
- 画面の操作を案内するときは、**メニューの名前をそのまま**書く
  (「設定から」ではなく「Settings → API Keys」)
- 「〜のはずです」で終えない。**確かめられることは確かめてから言う**

### 作業を頼むときは、必ずこの3つを添える

利用者から「説明をなるべく細かく」と要望があった(2026-08)。
手を動かしてもらう前に、次を必ず書く。

| 添えるもの | 例 |
|---|---|
| **これから何が起きるのか** | 「1つの行の1つの欄だけが書き換わります」 |
| **どこまで影響するのか** | 「他のテーブルやデータには一切触れません」 |
| **どうなれば成功か** | 「`Success. Rows returned` と出て、表に1行出れば成功」 |

**「上書きなのか、一部変更なのか」を利用者は判断できない。**
コードやSQLを渡すときは、**それが新規なのか・置き換えなのか・追加なのかを
必ず明示する。** 「これを実行してください」だけで渡さない。

### 手順は「どこで・何を・どうやって」を、番号を振って書く

利用者の指摘(2026-08)。

> これはどこに貼ったら良いのですか?
> 私の作業があるときはどこに、何を、どういう手順で、何をするのか、を
> 明確に説明してください。

**「◯◯を貼り直してください」だけでは足りない。**
リポジトリの中のファイル名を書いても、利用者はそれをどこで開き、
どの画面のどのボタンから実行するのかを知らない。
**書いたこちらは分かっているが、読む側には見えていない。**

手を動かしてもらうときは、**必ずこの型で書く。**

```
## やっていただくこと(全 N ステップ・所要 ◯分)

### ステップ1 … ファイルを開く
どこで: GitHub → リポジトリ → `path/to/file.sql`
何を:   右上の「Raw」を押す → 全部選んでコピー(⌘A → ⌘C)

### ステップ2 … 貼って実行する
どこで: Supabase → 左メニュー **SQL Editor** → **New query**
何を:   貼り付けて、右下の **Run** を押す
何が起きるか: ◯◯という表が2つ増えます。**空から始まります**
どこまで影響するか: 教材・宿題・ゲストの情報には触れません
成功の目安: `Success. No rows returned` と出れば成功
うまくいかないとき: 赤い字が出たら、その文章をそのまま貼ってください
```

**守ること。**

- **画面の名前は、そのまま書く。**「設定から」ではなく
  「Supabase → 左メニュー **SQL Editor**」
- **番号を振り、1ステップ = 1つの操作**にする。
  「コピーして貼って実行」は3ステップである
- **ステップごとに「成功の目安」**を書く。
  最後にまとめて書くと、途中で失敗したときに気づけない
- **所要時間とステップ数**を先に出す。終わりが見えないと始めにくい
- **うまくいかないときの逃げ道**を必ず書く
  (「その文章をそのまま貼ってください」)
- **こちらでできることは、こちらでやる。** 利用者に頼むのは、
  環境の制約でこちらが実行できないものだけにする

#### ファイルの場所は「どこのファイルか」から書く。押せる URL を渡す

利用者の指摘(2026-08)。

> supabase のapplyってどこですか?何がどこにあるか、は徹底して教えてください。

`supabase/apply/…` と書いたが、これは **GitHub のリポジトリの中のフォルダ**で
あって、Supabase の画面の中には存在しない。**同じ名前のものが2か所にあると、
利用者は必ず取り違える。** 書いたこちらだけが区別できている。

- **「どこのファイルか」を必ず先に書く。**
  「GitHub のリポジトリにある `supabase/apply/xxx.sql`」
  「Supabase の 左メニュー **SQL Editor**」
- **押せる URL を書く。** リポジトリの中の道順を言葉で説明しない。
  ブランチ名まで入った URL を、そのまま貼れる形で渡す
- **貼る中身が短いなら、チャットにそのまま貼る。** ファイルを探させない

#### やり直しを頼むときは、手順を最初から丸ごと書き直す

利用者の指摘(2026-08)。

> その後の作業も丸々もう一度まとめて指示してもらわないと
> 戻って作業手順を確認すると間違いの元です。

**「◯◯だけもう一度」と書かない。** 前のメッセージまで戻って読み直すのは、
それ自体が間違いのもとである。少しでも手順が変わったら、
**ステップ1から最後まで、その回のメッセージだけで完結するように書き直す。**
繰り返しになっても構わない。**短く書くことより、間違えないことが先。**

#### 相手はコーダーではない

利用者はプログラミングの初学者である(このファイルの冒頭)。
**「ファイル名を書けば分かるはず」「ここまで言えば察せるはず」は成り立たない。**
分かっているのは書いたこちらだけである。
- 略さない。`supabase/apply` ではなく、どこの何かを毎回書く
- 画面の名前・ボタンの名前を、見えているとおりに書く
- **こちらで代われる作業は、一つも残さない**

## 事実の扱い

- **推測で断言しない。** 確かめていないことは「確認していない」と言う
- **できないことは、できないと言う。** 環境の制約で実行できない作業は、
  ごまかさずに伝え、利用者側で何をすればよいかを示す
- 自分の誤りは、言い訳せずに1〜2文で述べて直す。長い反省は書かない

## 検証してから渡す

**利用者に「試してください」と渡す前に、自分で確かめられる範囲は必ず確かめる。**

- 手元で実行できるもの(SQL、スクリプト、ビルド)は実行して通してから渡す
- 実行できない場合は、**実行できる形を先に作る**
  (例: Supabase に接続できないなら、手元の PostgreSQL で検証する仕組みを用意する)
- **同じ検証を次回も自動で回せる形にする。** その場限りの確認で終わらせない

### 版が分かるようにしてから確認を依頼する

「直したはずの不具合が直っていない」の原因が、
**ブラウザやキャッシュに残った古い内容**だったことが繰り返しあった。
実機での確認を依頼するときは、
**どの版を見ているか機械的に分かるようにしてから**依頼する。

## 別々の物を、すき間ゼロでくっつけない(どのアプリでも)

2026-09 実機・利用者の指定。**プロジェクトを超えた決まり**である。

> 大きく表示のボタンとその上の3つのボタンが隙間がなく接触しています。
> ダサいのですぐ直してください。他にもこういう場所がありました。
> 全て探して直してください。プロはこんなデザインは作りません。
> これはこれからどんなアプリを作る時も共通のルールにしてください

**縦に並ぶ「別々の物」のあいだには、必ず目に見える隙間を置く。**
ここで言う「物」は、**押せるもの(ボタン・入力欄・プルダウン)と、
枠や地色で囲われた箱**である。

### 隙間は、`gap` で作る。余白で作らない

| | |
|---|---|
| ○ | 親を `flex` / `grid` にして **`gap`** で離す |
| × | 子に `margin-bottom` を付けて回る |
| × | **「次に何が来るか」で決める**(`.a + .b { margin-top }`) |

**いちばん危ないのは3つめである。** 実際に起きたのはこれだった。

    .card-tools { margin-bottom: 0 }        /* 自分の余白を消して */
    .card-tools + .btn-row { margin-top: 8px }  /* 次が .btn-row なら戻す */

下に来るものが**素の `<button>` に変わった日**から、この指定は
**どこにも当たらなくなり、隙間が 0 になった。**
CSS も JSX も1行も壊れていないので、**画面を開くまで誰にも分からない。**

- **`gap` なら、下に何が来ても・いくつ増えても離れる**
- 親を `flex` にするときは **`align-items` を必ず確かめる。**
  前の宣言に `center` が残っていると、
  縦積みにしたとたん**行が中身なりの幅に縮んで、左端がぎざぎざになる**
  (実際にそうなった)

### 「わざと接している」ものだけを、名指しで外す

一覧の行(`li + li { border-top }`)のように、**線を接して1つに
見せる**作りは正しい。**外すときは、必ず理由を書き残す。**

### 見つけ方 — **DOM の兄弟では測れない**

はじめ「兄弟どうしの隙間」を測る検証を書いたが、**素通りした。**
ボタンを束ねている行は**枠も地色も持たない透明な入れ物**なので、
「物」として数えられないためである。

**描かれている物(いちばん内側)だけを拾って、縦と横の両方で測る。**

- 浮いているもの(`fixed` / `sticky` / `absolute`)は数えない ——
  あちらは流れの中にいない。**ただ上に重なっているだけ**である
- **狭い画面と広い画面の両方で測る。** 接するのはたいてい狭いほうである
- **畳んであるものは開いてから測る**(閉じた箱は測れない)

#### **縦だけ測らない。横に並ぶ組も測る**

2026-09 実機・利用者の指摘(2度目)。

> 「聞き流す」と「印刷・PDF」ボタンの間に隙間がありません。
> これは PC での表示ですが、**すべてのデバイスでこれが起こらないように
> 徹底してください。**

見張りのはじめの1行が

    if (b.top < a.bottom - 0.5) continue        // 横に並んでいる

で、**横に並ぶ組をまるごと読み飛ばしていた。** だから接していても緑だった。
出どころも同じ根で、その行は **`margin-top` だけ**を持っていた ——
**余白は縦にしか効かない。横に並べるなら、並べる側(親)が `gap` で離す。**

- **「徹底する」とは、測るものを増やすことである**
- 横は「**同じ行にいて**(縦に 4px 以上かぶっていて)、**あいだが 4px 未満**」
- **わざと接している横の組は、別の一覧で名指しに外す**
  (錠剤・段を送る欄・選んでいる印の帯のように、
  **継ぎ目を無くして1つの部品に見せる**作り)。
  **「並んでいるから」では外さない** —— それをやると何も守らなくなる
- **重なっているものは数えない。** 別々に置いた物ではなく、
  上に載せた飾りのことが多い

#### **畳んである箱は、本当に畳まれているか**(2026-09 実測)

`<details>` **そのものに `display: grid`(や `flex`)を書くと、
畳んでいても中身が場所を取り続ける。**
見た目は畳まれているのに、中の札が**下の物と重なったまま**になる ——
画面を見ても分からず、**測って初めて出てくる。**

    <details className="…">      ← ここに display を書かない
      <summary>…</summary>
      <div className="…-body">   ← 並べるのは、この入れ物の役目
        …
      </div>
    </details>

実際に「型シフト」の絞り込みでこれが起き、
素の文の箱と札が **0.1px** で接していた。**見張りが捕まえた。**

### 検証の骨組みは、**本物と1文字も違えない**

この不具合が長く残った本当の理由はこれである。
検証用の骨組みだけが「セッションで使う」を `.btn-row` で包んでいたので、
**骨組みでは 8px 空き、本物では 0px** だった。
**骨組みが本物と食い違うと、検証は何も守らない。**
実際に骨組みだけを元に戻すと、CSS のバグを戻しても**緑のまま**になる。

## 赤チェックで「素の文字列」を置き換えるときは、先に数える

2026-09 に**3度**同じところで転んだ(どのプロジェクトでも起きる)。

見張りを1本ずつ壊して「本当に赤くなるか」を確かめるとき、
**同じ言葉がほかにも書いてあると、先に出てくるほうに当たる。**
壊したつもりのところは無傷なので、**緑のまま**になる。

| 実際に当たっていた先 | 狙っていた先 |
|---|---|
| 説明(JSDoc)の中の同じ語 | ボタンの文字 |
| 別の骨組み(`?screen=shelf`)に書いた同じ冊名 | 測りたい画面の冊名 |
| 別の関数の中の同じ1行 | 直した関数の中の1行 |

- **置き換える前に `grep -n` で数える。** 2つ以上あれば、
  **その行ごと**(前後を含めて)狙う
- **赤くならないのは「壊し方が違う」という知らせ**である。
  見張りが甘いと決めつける前に、まず**当たった場所**を確かめる

## 違うものに、同じ名前を付けない(「呼び名を2か所に書かない」の裏返し)

2026-09。新しい行に `.qr-head` と名付けたが、**その名前はもう
別の画面で使われていた。** 見た目の決まりがそのまま流れ込み、
**言われていない画面まで変わっていた。**

- **名前を作る前に `grep -n` で探す。** 在ったら、別の名前にする
- 「同じものを2つの名前で書くな」と**同じくらい**、
  「**違うものに同じ名前を付けるな**」も守る

## 余計な説明書きを置かない(2026-09 利用者の指定・**全プロジェクト共通**)

> 余計な説明書きは全て排除です。これは共通のルールにしてください。
> 直感的な UI、UX、UDが基本です

**画面の使い方を、文章で説明しない。**
説明が要るのは、**作りが分かりにくい**からである。
文章を足して補わない。**作りのほうを直す。**

| 置かない | かわりに |
|---|---|
| 「〜できます」「〜すると〜が出ます」 | **押せば分かる形**にする |
| 箱の上に置く前置き | **見出しと並び**で示す |
| 操作の手順書き | **次にすることを、その場に1つだけ**置く |
| 「(任意)」「※」などの但し書き | 要らない欄は、そもそも出さない |

**残してよいのは、次の3つだけ。**

- **いまの状態**(「保存しました」「まだありません」「12 語」)
- **失敗の知らせ**(その操作をした場所に出す)
- **取り返しのつかない操作の確認**(消す・課金する)

### 見た目も、既にある形から選ぶ

**白い箱を新しく作らない。** 押せるものの見た目は、
そのアプリに**すでにある3つ**から選ぶ。

| | 何に使うか |
|---|---|
| **青(塗りつぶし)** | **次に進む**もの。1つの画面に1つだけ |
| **灰(塗りつぶし)** | **ならぶ**もの(一覧・選ぶもの) |
| **枠線だけ** | 控えめなもの(送る・戻す・開く) |

**既定のボタン(地の色のまま)は、白い紙の上で「押せるもの」に見えない。**
実際にそう言われた(2026-09)。**色を決めずに置かない。**

### 長い一覧は、**開くまで羅列しない**

語・履歴・候補のように**何十個にもなるもの**は、
数だけ出して畳んでおく(「印を付けた語 12 語」)。
そのまま並べると、**その下にあるものが画面の外へ押し出される。**

**`<details>` そのものに `display: grid` / `flex` を書かない** ——
畳んでいても中身が場所を取り続ける(このファイルの上の節)。

#### 押すものは、**一覧の末尾に置かない**(2026-09 利用者の指定)

> 単語のリストがあって、その一番下に青いボタンではなく、
> ボタンをリストよりも一段上の層においてください

**一覧の末尾に置くと、中身が増えるほど下へ流れて見つからない。**
**見出しの行**(畳みの札と同じ行)に置く。そこなら
**畳んでいても押せて、場所が中身の数で動かない。**

畳みの札と押すものを同じ行に並べるなら、**`<details>` はやめる。**
`<summary>` の中に別のボタンを置くと、**押すたびに畳みが動く。**
状態を1つ持ち(`◯◯Open`)、**畳んでいるあいだは中身を描かない。**

## 記録を残す(セッションをまたぐ唯一の手段)

Claude にはセッションをまたぐ記憶がない。**覚えているのはリポジトリだけである。**

| 残す先 | 何を |
|---|---|
| 仕様書(`docs/` 配下) | **判断とその理由。** 何を選び、何を選ばなかったか |
| `CLAUDE.md` / `.claude/rules/` | 次回も守るべき決まりごと、繰り返した失敗 |
| テスト | **忘れない記憶。** 一度塞いだ穴を二度と開けないための仕組み |
| コミットメッセージ | **何を変えたかだけでなく、なぜそう判断したか** |

同じ失敗を2度したら、その場で `CLAUDE.md` に書き足す。

## 鍵と秘密情報

| 種類 | 扱い |
|---|---|
| 公開前提の鍵(Supabase の `anon` / `publishable`) | アプリに埋め込んでよい。チャットに貼ってもらってよい |
| 管理者の鍵(`service_role` / `secret` / API キー全般) | **絶対に扱わない。チャットに貼らせない。** `.env` か GitHub Secrets に利用者が直接書く |

- `.env` は必ず `.gitignore` に入れる。見本は `.env.example` に空で置く
- **公開前提の鍵が安全なのは RLS などの制限があるからである。**
  その制限を外す変更は行わない

## Git

### 作業を始める前に、必ず最新を取り込む

利用者は **クラウドのセッション(会社PC・iPhone・Mac)と、Mac のローカル**を
使い分ける。どちらで作業してもリポジトリは同じだが、**自動では同期されない。**

**セッションの最初に必ず `git fetch` と `git status` で、
手元が最新かどうかを確かめる。** 遅れていれば取り込んでから作業を始める。
これを飛ばすと、片方で作った変更が無い状態で進み、あとで衝突する。

同じ理由で、**作業の区切りごとに push する。** 手元にだけある変更は、
もう一方の環境からは存在しないのと同じである。
クラウドのセッションは終了時に環境ごと捨てられるため、
**push していない変更は失われる。**

- 指定された作業ブランチで作業する。`main` に直接 push しない
- Pull Request は**明示的に頼まれたときだけ**作る
- push に失敗したら、2秒・4秒・8秒・16秒と待って最大4回まで再試行する

## 直すのは、言われた場所だけ

利用者の指定(2026-08)。

> これからは「同じ仕様の部分全てに適用してください」と言ったとき以外は
> 該当の場所のみの変更にしてください。

**「ついでに、同じ作りの他のところも」を、こちらの判断でやらない。**
似ているという理由で手を広げると、**利用者が見ていないところが変わる。**
気づくのは、次にその画面を開いたときである。

- 直すのは、**言われた画面・言われた部品だけ**
- ほかにも同じ作りの場所があると気づいたら、**直さずに、報告する**
  (「◯◯にも同じところがあります。直しますか」)
- **例外は、利用者が「全部に適用して」と言ったときだけ**
- 作りを共通化するとき(部品を1つにまとめるなど)は、
  **見た目と振る舞いが変わらないことを確かめてから**にする。
  1か所に寄せること自体は良いが、**寄せたついでに直さない**

**すでに動いているものを、頼まれてもいないのに消さない・変えない。**
実際、スラッシュリーディングを作り直したときに、
**段落ごとに訳を出す機能を意図せず落とした**(2026-08)。

## 勝手に広げない・勝手に狭めない

- 頼まれた範囲を仕上げる。**思いつきで機能を足さない**
- 一部が難しくても、**残りを全部仕上げてから**「ここだけできなかった」と言う。
  黙って縮めない
- 方針の転換にあたる変更(データの置き場を変える、制限を外すなど)は、
  勝手に行わず必ず確認する
